## 1. 概述（Overview）

### 1.1 背景与动机

当前大语言模型（LLM）驱动的 Agent 在复杂任务决策中面临三大核心挑战：

1.  **上下文窗口限制**：无法一次性加载大规模知识图谱，导致"Lost in the Middle"现象。
2.  **多跳推理效率低下**：纯 LLM 逐步推理（Chain-of-Thought）在深层依赖链上容易迷失方向，且 token 成本随推理深度线性增长。
3.  **缺乏可解释性与约束**：黑盒生成难以满足企业级场景对逻辑正确性、合规性和可追溯性的要求。

### 1.2 设计目标

本方案旨在构建一个**分层图谱增强型 Agent 决策系统**，通过以下机制解决上述问题：

- **分层知识表示**：本体图谱（Schema 层）+ 实例图谱（Data 层，全局/项目级）。
- **LLM 引导的多图联合最短路径查询**：利用 LLM 的语义规划能力引导图搜索，减少组合爆炸。
- **POMDP 决策循环**：将多次查询建模为部分可观测环境下的序贯决策过程，实现"感知→规划→行动→观测→更新"的闭环。

### 1.3 适用范围

本设计适用于需要强逻辑约束、多跳推理和可解释决策的企业级场景，如：

- 复杂代码库重构与依赖分析
- 供应链风险归因与路径追踪
- 企业知识库的多跳问答与合规审查
- 项目管理中的依赖链推理与风险预警

### 1.4 全文结构

全文按“问题—架构—知识—检索—决策—工程—风险”展开：

- **第 2 章**：三层架构、组件职责与选型边界。

- **第 4 章**：多图联合最短路径的查询编译、剪枝、评分与缺失路径诊断。
- **第 5 章**：POMDP 决策循环、动作空间、奖励函数与 Belief 更新。

## 3. 知识层设计（Knowledge Layer）

### 3.1 本体图谱（Ontology KG）

本体图谱作为 Schema 层，定义系统的概念骨架和逻辑约束。在本系统中，它不是一份静态 schema 文档，而是检索层、规划器和实例层共同遵守的契约：有哪些概念、概念之间允许什么关系、每个概念可以拥有哪些属性，并且这些回答要能被机器校验、被查询编译器消费、被实例层回填。

#### 3.1.1 领域概念骨架

在本系统中，本体首先落地为一组可被查询和校验的领域概念。下面的概念清单沿用前文的 Task、Resource、Constraint、Risk、Decision 五类概念，它们既是检索层的类型系统，也是实例层的挂载点。概念名可以替换为具体业务词，但“类只表达 is-a、关系必须有签名、属性必须声明”的约束不变。

**节点类型（Concept）**：

- `Task`：任务/目标
- `Resource`：资源（人、设备、代码模块等）
- `Constraint`：约束条件（时间、预算、合规要求等）
- `Risk`：风险类型
- `Decision`：决策节点

**关系类型（Relation）**：

- `depends_on`：依赖关系（传递性）
- `requires`：资源需求
- `constrained_by`：约束关联
- `mitigates`：风险缓解
- `leads_to`：因果/结果导向

**本体规则示例**：

```cypher
// 规则1：依赖关系具有传递性
MATCH (a:Task)-[:depends_on]->(b:Task)-[:depends_on]->(c:Task)
CREATE (a)-[:depends_on {derived: true}]->(c)

// 规则2：任务必须满足所有约束
MATCH (t:Task)-[:constrained_by]->(c:Constraint)
WHERE c.status = 'violated'
RETURN t, c  // 触发风险预警
```

#### 3.1.2 本体的形式化定义与契约

把本体记作四元组 T = (C, ≺, R, A)：C 是类集合，≺ 是由父类函数决定的继承闭包，R 是关系签名集合，A 是属性声明集合。实例层的一切合法性判断都归约到这三个成员关系上。

$$
T = (C, \prec, R, A)
$$

$$
R \subseteq C \times \text{RelationName} \times C, \quad A \subseteq C \times \text{AttributeName} \times \text{ValueType} \times \{\text{required}, \text{optional}\}
$$

给定实体 e、属性赋值 e.a = v、关系边 e₁ -r-> e₂，合法性定义为：

$$
\text{valid}(e) \iff \text{type}(e) \in C
$$

$$
\text{valid}(e.a = v) \iff \exists c' \in \text{anc}(\text{type}(e)) : (c', a, \tau) \in A \land v \models \tau
$$

$$
\text{valid}(e_1 \xrightarrow{r} e_2) \iff \exists (d, r, g) \in R : d \in \text{anc}(\text{type}(e_1)) \land g \in \text{anc}(\text{type}(e_2))
$$

其中 anc(c) 是包含 c 自身的祖先闭包，v ⊨ τ 表示值 v 满足值类型 τ 的语法约束。校验采用封闭世界假设：当前快照里未声明的类、属性或签名一律视为非法，不依赖外部推理机补全。

本系统不引入完整的 OWL DL 推理机，而采用“属性图 + 显式闭包”的轻量契约。原因有三点：继承闭包和签名放行可以在编译期或查询期精确计算，结果可复现；规则以元模型实例承载，变更不需要重新部署推理服务；物理结构与现有 Neo4j 脚本、应用读取格式保持同构。OWL 适合开放世界语义交换，而 Agent 决策需要的是可审计、可拒绝执行的封闭契约。

**表 3-1 本体图谱的构成与约束**

| 构件 | 数据形态 | 必须满足的约束 | 在系统中的用途 |
|----|----|----|----|
| 类 C | {name, comment, parent} | 全局唯一；父类已声明；无自环、无继承环；单根优先 | 概念检索、类型校验、UI 分组、权限范围 |
| 子类关系 ≺ | (:类)-[:子类]->(:类) | 只表达 is-a，不表达部门上级、合同归属等业务层级 | 计算祖先闭包；放行子类属性与关系签名 |
| 关系类型 | {name} + 定义域/值域边 | 至少一条签名；同一关系名可有多条签名，但语义要收敛 | 查询关系白名单、动作模板绑定、路径剪枝 |
| 关系签名 | (domain, relation, range) | 两端必须是已声明类；沿继承闭包匹配 | 实例边校验、路径可达性判断、覆盖统计 |
| 属性声明 A | {domain, attribute, value_type, required} | 属性名非 id/name/名称；值类型在允许枚举内 | 字段映射、值类型校验、必填回填、覆盖评估 |
| 规则层 | 规则 + 类定义/关系定义/属性定义 + 约束 边 | 约束对象必须能解析到具体定义，unresolved = 0 | 承载归属、唯一性、白名单、兜底等执行纪律 |

#### 3.1.3 建模规则与反模式

建模规则决定本体能不能长期维护。以下规则按类、命名、关系、属性、最小化五组执行；它们不是风格偏好，而是直接影响查询能力、实例覆盖率和后续变更成本。

- **类与层级**：默认单根（事物）；父类必须显式声明；类只表达 is-a；同层粒度一致；只有 0–1 个属性且没有独立关系的类并到父类；不为字面量建类；不做“其他/杂项”桶。
- **命名**：类用 2–8 字业务名词，不用复数、不带“表/字段/信息”后缀；关系用动词或动宾短语；属性用名词短语；id/name/名称 是保留键，不能作为业务属性。
- **关系签名**：每个关系至少一条 domain-relation-range 签名；两端必须是已声明类；同一关系名承载的语义不超过 3 种；继承闭包放行的组合数不超过声明签名数的 2 倍；能被子类继承覆盖的签名不重复声明；反向关系不单独建。
- **语义纪律**：组织挂靠、签约归属、行业归类、主从挂载、权属归属是不同语义，不能都塞进一个“属于”；实例层兜底改写不得优先使用“属于/关联”这类万能泛化词；无具体关系可换时丢弃并报缺口，不硬改。
- **属性**：只声明能从数据取到的字段；一个字段一个值类型；数值/金额/比例必须可解析为数；日期以 4 位年开头；属性可声明在父类，子类实例直接可用；同类字段不要父子重复声明。
- **最小化**：先问“能不能并”，再问“要不要加”；关系类型数/类数建议 ≤ 1.5；属性声明数/类数建议 ≤ 15；只被一个实例使用的类优先并到父类；值域是根类的关系签名要检视是否该写具体类。
- **同义合并**：痛点/业务痛点、价值/业务价值、实施周期/上线周期 先合并再建模；但含税/不含税、实际/预设、签约客户/立项客户/实际用户、行业/行业大类/行业细分不能因为名字像就合并。

**表 3-2 常见建模反模式与修正**

| 反模式 | 后果 | 正确做法 |
|----|----|----|
| 为字面量建类（“2024-01-01”“高”） | 类爆炸，无法复用，查询语义混乱 | 作为属性的 value_type；确需检索的枚举建维度类 |
| 用继承表达业务层级（部门上级） | 继承闭包被业务层级污染，类型判断失真 | 用关系 部门-上级部门->部门，并在规则层约束唯一性 |
| 一个“属于”承载 5 种语义 | 查询无法表达意图，实例层只能靠猜 | 拆成行业归类/签约归属/组织挂靠/主从挂载等具体动词 |
| 关系只给名字，不给 domain/range | 实例边无法校验，路径剪枝失效 | 每个关系至少声明一条签名，端点写已声明类 |
| 同义属性建两份 | 空置率升高，指标口径分裂 | 同类内先合并，保留规范名，其余写进说明 |
| 父类重复声明子类已有属性 | 统计重复，继承语义冲突 | 只在最近公共父类声明一次 |
| “其他/杂项/未知”桶类 | 噪声固化，长尾类永远空置 | 并入最近父类；确需保留时标预留并写数据源计划 |

#### 3.1.4 校验、交付与物理结构

本体库的输入是一份结构化 spec。模型负责理解和命名，脚本负责校验和写出；任何产物必须先通过校验，校验不通过不写库、不导出。

```json
{
  "name": "Agent 决策本体",
  "version": "1.2",
  "root": "事物",
  "classes": [
    {"name": "事物", "parent": "", "comment": "根类"},
    {"name": "Task", "parent": "事物", "comment": "任务/目标"},
    {"name": "Resource", "parent": "事物", "comment": "资源"}
  ],
  "relations": [
    {"domain": "Task", "relation": "depends_on", "range": "Task"},
    {"domain": "Task", "relation": "requires", "range": "Resource"}
  ],
  "attributes": [
    {"domain": "Task", "attribute": "优先级",
     "value_type": "数值", "required": true},
    {"domain": "Task", "attribute": "截止日期",
     "value_type": "日期", "required": false}

```

交付前先跑 --validate-only，修到 0 ERROR；WARNING 逐条判断。正式写出时按目标选择 JSON 三件套或 Neo4j；Neo4j 默认 MERGE，只有用户明确要求重建时才加 --wipe。

```bash
# 只校验，不写任何产物
python3 scripts/build_tbox.py \
  --spec "$WORK/spec/tbox.json" \
  --validate-only --strict

# 写 JSON 三件套
python3 scripts/build_tbox.py \
  --spec "$WORK/spec/tbox.json" \
  --out "$WORK/tbox" --report "$WORK/tbox-report.json"

# 写 Neo4j（密码只走环境变量）

  --spec "$WORK/spec/tbox.json" --target neo4j \
  --uri "$NEO4J_URI" --user "$NEO4J_USER" \
  --password "$NEO4J_PASSWORD" \
  --database "$NEO4J_DATABASE"
```

**表 3-3 本体库校验规则与处置**

| 检查项 | 级别 | 处置 |
|----|----|----|
| 类名重复 | WARNING | 保留首条，去重并记录 |
| 父类未声明 / 自环 / 继承成环 | ERROR | 拒绝交付，补父类或断开环 |
| 没有根类 | ERROR | 补根类；多根只给 WARNING，需确认 |
| 关系 domain/range 未声明 | ERROR | 补类声明或修正端点 |
| 关系签名重复 | WARNING | 去重，保留首条 |
| 属性所属类未声明 | ERROR | 补类声明 |
| value_type 不在允许集合 | ERROR | 改为文本/数值/金额/日期/比例/标识符/版本号/时长/频率/其他 |
| 属性名为 id/name/名称 | ERROR | 改名；实例名由系统单独存 |
| 属性声明重复 | WARNING | 去重，保留首条 |
| 没有任何关系或属性 | WARNING | 确认是否纯分类本体；否则补最小关系与属性 |

JSON 产物与现有脚本完全同构，可直接被实例生成脚本和应用读取：

```text
out/ontology/
  classes汇总.json
    {"classes": [{"name","comment","parent"}]}
  relations汇总.json
    {"relations": [{"domain","relation","range"}]}
  attributes汇总.json
    {"attributes": [{"domain","attribute","value_type","required"}]}
  tbox.json
    三份合一的副本，便于审阅
```

Neo4j 侧与现有库同构：概念用 :本体:类，继承用 子类 边，属性声明用 :本体:属性 加 具有属性 边，关系类型用 :本体:关系类型 加 定义域/值域 边。属性 datatype 由值类型映射：文本/标识符/版本号/时长/频率/其他 → string，数值/金额/比例 → number，日期 → date。

```cypher
MERGE (c:`本体`:`类` {name: "Task"})
SET c.comment = "任务/目标"
MATCH (a:`类` {name:"Task"}), (b:`类` {name:"事物"})
MERGE (a)-[:`子类`]->(b)
MERGE (p:`本体`:`属性` {id:"Task.优先级"})
SET p.name = "优先级", p.datatype = "number",
    p.`必填` = true
MATCH (c:`类` {name:"Task"})
MERGE (c)-[:`具有属性`]->(p)
```

关系类型与签名用同一条路径写入，端点都用已声明的类：

```cypher
MERGE (rt:`本体`:`关系类型` {name:"depends_on"})
MATCH (rt:`关系类型` {name:"depends_on"}),
      (c:`类` {name:"Task"})
MERGE (rt)-[:`定义域`]->(c)
MERGE (rt)-[:`值域`]->(c)
```

安全规则：有 ERROR 时脚本不写任何产物并以退出码 2 结束；--strict 把 WARNING 也视为失败；连接信息只从环境变量读取；--wipe 属于破坏性操作，必须再次确认。

#### 3.1.5 规则层：把处理纪律变成可执行本体

有一类知识不适合写进类、属性或关系签名：某组织的成员必须来自权威花名册、每个人只能有一条任职边、A→B→C 已表达时不再写 A→C、行业归类必须命中白名单。这些是“针对具体对象的处理规则”，如果硬编码在抽取脚本里，规则变更就要改代码、重新部署，且无法审计。

本系统把这些规则建成本体的一部分：四个元类 规则/类定义/关系定义/属性定义，每个业务类、每条签名、每条属性声明各生成一个元实例，规则实例通过 约束 边挂到被约束对象上。实例生成前先从图上加载规则，按规则类型分派执行；新规则只改本体，不改编译代码。

```text
(:规则 {规则名, 规则类型, 约束对象, 判定逻辑, 失败动作, 正例, 反例})
(:类定义 {类名})
(:关系定义 {关系名, 定义域, 值域})
(:属性定义 {属性名, 所属类, 值类型})
(:规则)-[:约束]->(:类定义 | :关系定义 | :属性定义)
```

规则 JSON 只描述语义，脚本做机械转换：解析约束对象、生成元实例、建立约束边、幂等合并进实例三件套。约束对象可以是类名、完整签名 定义域 关系 值域、裸关系名（命中该关系全部签名）或 类.属性。任何约束对象解析不到具体定义，都算 unresolved，必须为 0。

```json
[
  {
    "规则名": "任职关系唯一",
    "规则类型": "唯一性",
    "约束_关系定义": ["人员 任职于 部门"],
    "判定逻辑": "每人只保留一条任职边；同名不同部门视为不同人",
    "失败动作": "拆分实体或拦截，并记入缺口报告",
    "正例": "张三·研发部 任职于 研发部",
    "反例": "张三 同时任职于 研发部 与 市场部"
  }
]
```

```bash
python3 scripts/build_rule_layer.py \
  --tbox "$WORK/tbox" --inst "$WORK/instances" \
  --rules "$WORK/spec/rules.json"

# 只检查约束对象能否解析，不写文件
python3 scripts/build_rule_layer.py \
  --tbox "$WORK/tbox" --inst "$WORK/instances" \
  --rules "$WORK/spec/rules.json" --validate-only
```

**表 3-4 规则层的规则类型**

| 规则类型 | 判定语义 | 失败动作 |
|----|----|----|
| 归属事实源 | 组织成员必须来自该组织的权威源（部门树/花名册） | 拦截并报告缺口 |
| 唯一性 | 每人/联系人只一条任职边；同名不同部门拆成多个实体 | 拆分或拦截 |
| 可推导 | A→B→C 已表达时，不写 A→C 冗余边 | 丢弃冗余边 |
| 白名单 | 行业、产品、人名等只认白名单或结构列精确值 | 丢弃并记录 |
| 分类映射 | 枚举值按映射表落到维度实体 | 映射失败转待确认 |
| 匹配纪律 | 实体提及必须显式编码/全名，避免子串误匹配 | 降级或丢弃 |
| 兜底纪律 | 越界关系改写不得优先万能泛化词 | 丢弃并报缺口 |
| 层级完整性 | 层级属性与层级边只保留一条路径 | 升边并删除同名属性 |
| 预留标注 | 无源签名标预留，不计入缺口 | 标记，不造值 |
| 度量 | 九项度量的阈值与动作 | 生成本体待修清单 |

规则层让“治理口径”和“业务本体”共享同一套版本与审计机制：规则可以双向查询，规则变更可以 diff，违规条目可以回放到具体约束对象。

```cypher
// 某规则约束了什么
MATCH (rule:规则 {name:"任职关系唯一"})-[:约束]->(def) RETURN def;
// 某签名被哪些规则约束
MATCH (rule:规则)-[:约束]->(def:关系定义 {name:"人员 任职于 部门"}) RETURN rule;
```

#### 3.1.6 本体质量评估与迭代闭环

本体不是一次写完的 schema。每轮都要经过“需求范围 → 规划类 → 规划属性 → 理解基础数据 → 生成实例 → 评估 → 优化”的闭环，直到评估指标达到预期，或继续优化的收益低于成本。评估不只看定义数量，而要看需求满足度、实例对原始数据的覆盖率、原始数据使用程度、定义空置率和结构合理性。

需求满足度分 Schema 与数据两个标签：full/partial/none。联合交付度按 0.4 × Schema 覆盖 + 0.6 × 数据覆盖 计算，避免 Schema 100 分、数据 0 分却被判为完成。属性空置率是“定义有效率”的补数，不是数据覆盖率；声明了但 0 值的字段只能算 Schema 覆盖。

联合交付度 = 0.4 × Schema覆盖率 + 0.6 × 数据覆盖率

**表 3-5 本体结构度量（构建期）**

| 度量 | 公式 / 口径 | 阈值 | 命中后的动作 |
|----|----|----|----|
| 类使用率 | 有实例的业务类 / 业务类总数 | < 60% 关注 | 并类、补数据或标预留 |
| 签名使用率 | 闭包命中的签名 / 签名总数 | 零实例关系类型 > 40% | 三分类：有源未抽 / 同端点重复 / 无源预留 |
| 闭包膨胀率 | 单关系放行组合数 / 声明签名数 | > 2.0 | 收窄值域或把签名下沉到子类 |
| 可推导签名 | 存在 A→B→C 且声明 A→C 的三元组数 | > 0 | 删冗余签名，或改成更具体的动词 |
| 同端点多父 | 同 (定义域, 值域) 有 ≥2 个关系名；同头同关系 ≥2 尾且为别名变体 | > 0（分类多值除外） | 别名归并、删重复签名 |
| 归属错挂率 | 非权威源成员 / 有归属成员 | > 0 | 白名单拦截、改挂真实所属、写成规则实例 |
| 语义过载 | 单关系签名种数 / 人工判定的语义类别数 | ≥ 5 或 ≥ 3 | 按语义拆成具体动词 |
| 层级完整性 | 层级属性条数 vs 层级边数 | 属性 > 0 且边 = 0 | 加层级签名，把属性升为边并删同名属性 |
| 多路径归一 | 同 (头类, 尾类) 有 ≥2 个关系名，或存在反向对 | ≥ 2 或存在反向对 | 统一入口关系名，删反向重复 |

这些是构建期指标，回答“定义是否有数据、结构是否健康”；4.6 节的指标是运行期指标，回答“路径是否查得通、证据是否可信”。两者共用同一套质量问题队列，但分母不同，不能混算。九项度量由脚本读本体库与实例三件套直接算出，不靠临时查询：

```bash
python3 scripts/metrics.py \
  --tbox "$WORK/tbox" --inst "$WORK/instances" \
  --out "$WORK/instances/度量.json"
```

**表 3-6 本体迭代闭环的阶段与门禁**

| 阶段 | 输入 | 输出 | 门禁 |
|----|----|----|----|
| 1 需求范围卡 | 业务问题、使用者、必须回答的问题、指标/维度、数据源、边界、成功标准 | requirements.md 或对话范围卡 | 写不出范围卡不进入类规划 |
| 2 规划类 | 需求名词、现有类表 | 类清单 + 父子关系 + 每类需求来源 | 每类至少满足：独立属性 / 独立关系 / 查询对象 |
| 3 规划属性 | 需求问题、源字段 | 属性清单 + 字段映射 + 预留清单 | Schema 支持与数据可用分开标注 |
| 4 盘点数据 | 原始文件/表/接口 | source-inventory.md + 字段映射 | 空模板、编码、主键、行数已确认 |
| 5 生成实例 | 当前本体库、映射表 | 实例库三件套 + 校验报告 | 实体类/属性声明/关系签名三类缺口 = 0 |
| 6 评估 | 本体库、实例库、原始目录 | 评估报告 + 指标 JSON | 数字全部现算，不手写 |
| 7 优化 | 评估命中项 | 变更清单 + dry-run + 冲突统计 | 只改命中项；冲突不为 0 不写库 |
| 8 停止 | 指标、成本、剩余缺口 | 停止记录 + 下一轮触发条件 | 不用定义数量增加冒充能力提升 |

每轮变更都按同一顺序执行，缺一步不算交付：备份当前本体与数据基线；dry-run 输出变更清单、受影响定义、源实例值和冲突数；只用精确 (类, 属性) 或精确签名做删除/合并；--validate-only --strict 达到 0 ERROR / 0 WARNING；默认 MERGE 写库；从 Neo4j 重导出基线；文档与统计从基线现算；最后写变更摘要。

停止条件满足任一即可：约定目标达到；当前数据源已挖尽；边际收益低于变更成本；用户接受剩余缺口并记录原因。停止时写清本轮改了什么、指标 before→after、哪些指标没动及原因、剩余缺口和下一轮触发条件。

- **需求有、Schema 无**：补类/属性/签名，先写需求范围卡，不为凑指标造类。
- **Schema 有、数据无**：找源数据或修抽取；无源则标预留，不把 Schema 覆盖当数据覆盖。
- **属性同义/近义**：同类内合并，保留规范名；跨口径、跨状态、跨角色、跨粒度不合并。
- **关系类型零边**：三分类处置，不直接删需求内关系。
- **类零实例**：并类、补数据或标预留；不为每个名词建类。
- **原始文件未使用**：先盘点格式与字段，再决定抽取或放弃；未读文件不能宣称“无数据”。

### 3.2 实例图谱（Instance KG）

实例图谱作为 **Data 层**，存储具体实体及其关联。采用**全局 + 项目级**双层结构。

#### 3.2.1 全局实例图谱

- **范围**：跨项目、跨部门的通用实体（如员工、客户、产品、代码仓库）。
- **更新频率**：低频（天/周级），通过 ETL 管道同步。
- **存储策略**：分布式图数据库集群，按实体类型或业务域分片。

#### 3.2.2 项目级实例图谱

- **范围**：特定任务或项目上下文中的实体与动态状态（如当前 Sprint 的任务依赖、临时风险评估）。
- **更新频率**：高频（分钟/小时级），由 Agent 决策循环直接写入。
- **存储策略**：可与全局图谱同库（通过标签/命名空间隔离）或独立轻量级存储。

#### 3.2.3 图谱对齐机制

- 项目级实体通过 `same_as` 或 `instance_of` 关系链接到全局实体，确保语义一致性。
- 本体图谱中的概念通过 `rdf:type` 或 `is_a` 关系映射到实例节点。

对齐层是多图查询能否跨图的前提。对齐关系本身也要作为实例边管理：它需要置信度、溯源、有效期和冲突仲裁，不能靠一次脚本永久写死。

**表 3-7 跨图对齐关系**

| 关系 | 方向 | 语义 | 写入策略 |
|----|----|----|----|
| same_as | 对称，可传递 | 同一个人/企业/产品在全局图与项目图中的身份等价 | 默认写入对齐层；置信度 ≥ 0.85 才用于路径桥接 |
| instance_of | 项目实体 → 本体类 | 项目实体的类型归属 | 由实例生成脚本写入；类型必须在本体库中已声明 |
| belongs_to_scope | 项目实体 → 项目/租户 | 项目级隔离与权限边界 | 随项目实例写入；查询时强制作为过滤条件 |
| derived_from | 实例/边 → 源记录 | 证据溯源，指向原始文件、行号或接口 | 随实体/边写入；缺失时降低置信度 |

- same_as 写入前先查冲突：一个项目实体只能指向一个全局实体；出现一对多时进入人工仲裁，不自动合并。
- 对齐置信度低于 0.85 的候选只进候选队列，不参与跨图最短路；查询命中歧义实体时返回 ambiguous_entity 质量标志。
- 全局实体是规范名，项目实体保留原名称与 provenance；合并时把旧名称写入别名属性，不覆盖规范名。
- 对齐边的有效期独立于业务边；源系统主数据变更时，旧对齐边软删除并保留审计记录。

**对齐候选生成的两个必要环节（v1.12）**

表 3-7 只规定了写入规则，没有规定候选怎么来。补两条实现约束：

- **高频键裁剪**：以属性值做阻塞键时，必须给块大小设上限（建议 200 个实体）并排除类型键（类型只用于一致性检查，不用于判别）。裁剪掉的高频键等价于阻塞阶段的停用词；不裁剪时实测平均 142 个候选/实体，k=1 时精度 0.002。
- **打分只排序，裁决定精度**：候选打分（共享键计数 / IDF 加权 / 块大小分摊）单独取最高分时，精度上限 0.833，够不到 0.85；引入“只接受唯一最高分，其余进候选队列”后精度 0.951、覆盖 0.669。配置对齐模块时必须同时报告**覆盖率**，只报精度会掩盖“三分之一的实体没有对齐结果”。

**第三个必要环节：值单独通道（v1.36）**

- **诊断**：4,500 个待对齐实体中有 741（16.5%）进不了候选；其中 **473 个与配对实体存在相同的规范化属性值**，只是谓词映射没对上也进不了同一个块（例如 zh `外文名稱` / `原文名` 与 en `originalName`）。
- **做法**：在 (映射谓词, 值) 之外，再建一条**只用值**的阻塞通道，块大小上限取 **50**（20/50/100 三档覆盖差异 <0.5pp，不敏感）；两条通道不重复计分。
- **效果**：候选上限（金标在候选内）0.724→**0.832**，覆盖 0.669→**0.772**，精度 0.951→**0.937**，**正确覆盖 0.637→0.723**。裁决沿用**单向唯一（并列判歧义）**。
- **不要用双向唯一**：它在去掉顺序依赖后是精度 0.964 / 覆盖 0.738，按正确覆盖（0.711）不如单向唯一（0.723）。v1.36 曾写"双向唯一多 0.5pp 覆盖"，那是并列最高分被 set 顺序随意裁决造成的假象。
- **判据必须与遍历顺序无关**：并列最高分一律判歧义；任何"每个谓词只计一次"的累计也要先排序再累计。否则同一份数据每次跑出的接受数不同（实测 994 / 1006 / 1010），回归门禁会随机变红。
- **不要的做法**：用 train 锚点做关系邻居传播（结构传播）只把候选上限抬 0.4pp，覆盖 0.756、精度掉到 0.916 —— **不采纳**；但这只说明在关系映射仅 502 条的条件下无效，属未充分测试，不是已证伪。
- **实施前提（硬）**：值通道能成立，是因为 DBP15K 两侧的属性值**未被翻译**（面积、坐标、日期、人口、图片文件名、外文名）。若源数据把属性值本地化，该通道退化，覆盖率回到 0.669，必须改用人工仲裁或嵌入。部署前必须抽查属性值语言分布。
- **必报三个数**：精度、覆盖、**正确覆盖（= 精度 × 覆盖）**。三者会同时变动，只报一个必然误导。
- **嵌入是第二位手段（v1.37 实测）**：多语言嵌入（`paraphrase-multilingual-MiniLM-L12-v2`，384 维，CPU/ONNX）在残差 1,028 个实体上 top-10 召回 0.351、**top-100 召回 0.564**；在 0.85 精度约束下只接受 34 个，整体覆盖只从 0.772 到 **0.779（+0.7pp）**。因此顺序必须是：先阻塞与裁决（便宜、可解释），再考虑嵌入；剩余 22.8% 主要靠跨语言链接或人工仲裁。换更大模型未测。

#### 3.2.4 实例身份与三类约束

实例层只做三件事：实体要有类、属性要已声明、关系要满足定义域/值域。

> **v1.12 修正**：真实跨源数据里类槽位普遍缺失（DBP15K zh_en 仅 966/15,000 实体带类型属性，可比对样本上类一致率 0.738），因此“实体要有类”应实现为**降权 + 质量标记（`untyped_entity`）**，不能作为硬门禁，否则会拒掉九成以上实体。把这三件事写成判定式，就是实例生成脚本和独立复验脚本共同执行的契约：

$$
\text{valid}(e) \iff \text{type}(e) \in C
$$

$$
\text{valid}(e.a = v) \iff \exists c' \in \text{anc}(\text{type}(e)) : (c', a, \tau) \in A \land v \models \tau
$$

$$
\text{valid}(e_1 \xrightarrow{r} e_2) \iff \exists (d, r, g) \in R : d \in \text{anc}(\text{type}(e_1)) \land g \in \text{anc}(\text{type}(e_2))
$$

身份规则由脚本统一执行，spec 里只写名称原文，不手拼 id、不手改清洗结果：

- 实例 id 固定为 {类}.{名称}，例如 Task.需求评审、Resource.张三；同名不同类是两个实例。
- 名称清洗：非空；剔除换行、制表、零宽等控制/格式字符；连续空白折叠为一个空格；去首尾空白；长度 ≤ 80，超出截断加“…”；同类同名只保留一条，docs 取最大值。
- 显示名存节点属性 name；名称 不是业务属性，写进 spec 会被当保留键处理。
- provenance 可选，建议保留 {source, row, page} 定位；docs 表示被多少来源断言，同一事实多次出现累加。
- 必填属性按本体库的 required 处理：名称/全称/姓名缺失时用实体名回填（姓名去掉「·部门」消歧后缀）；编号/编码/代码/标识符/ID 类只在实体名本身就是编码时回填；回填不出来的记 required_missing，不写空值。
- 同一实例同一属性多个值写多条，脚本合成列表；不要用逗号拼接。多值要看语义：多个“曾用名”是列表，“成立日期”出现两个值说明数据冲突，先确认再写。
- 自环 A-关系->A 默认允许，但要在报告中点出确认是否符合业务；同一头尾同关系的重复边自动去重。

**表 3-8 实例层三类约束与校验**

| 检查项 | 规则 | 失败处置 |
|----|----|----|
| 实体类型 | type 必须是本体库已声明的类（推荐写最具体叶子类） | ERROR：丢弃该实体或改类型 |
| 实体名称 | 非空；清洗后 ≤ 80；同类同名唯一 | ERROR / WARNING：清洗、去重 |
| 属性声明 | 属性必须声明在实例类或其任一祖先类上 | WARNING（--strict 为 ERROR）：丢弃该行或先补本体 |
| 值类型 | 数值/金额/比例可解析为数；日期以 4 位年开头；其余非空 | WARNING：改值、改声明或确认保留 |
| 关系签名 | 起点/终点的祖先类必须满足某条 domain/range 签名 | WARNING（--strict 为 ERROR）：换关系、改端点或丢弃 |
| 关系端点 | 头实体和尾实体必须已存在于本次 entities 中 | ERROR：补实体或删边 |
| 重复事实 | 同 (类, 名称)、同 (头, 关系, 尾)、同 (实例, 属性) 去重 | 自动去重；多值属性合并为列表 |
| 必填属性 | 只约束本类声明，不上卷到子类 | 回填或记 required_missing；--strict 下按错误处理 |

#### 3.2.5 从原始数据到实例的映射流水线

“生成实例”不是重跑一次脚本，而是按当前本体库重新走一遍映射。流水线分六步，每一步都留下可复跑的产物：

- **盘点原始数据**：列文件/表路径、格式、行数、字段、主键、空值、编码、是否空模板；先判断哪些来源能支撑哪些类/属性/关系，标不出就写“未使用原因”。
- **读当前本体库**：只写已声明的类/属性/签名；旧字段名、已合并字段名不能再用。
- **先小样本映射**：确认列名、全角括号、HTML 表格、合并单元格、同名实体等陷阱，再全量跑。
- **生成 spec**：输出实体、关系、属性三类记录，保留 docs/provenance；不确定的列列成“待确认清单”，不静默丢弃。
- **归一与对齐**：公司全称/简称、产品版本别名归一到规范名；项目实体通过 same_as 挂到全局实体；同名不同部门的人用「姓名·部门」拆成多个实体。
- **校验与交付**：build_abox.py --validate-only --strict 0 ERROR；validate_abox.py PASS；再按目标写 JSON 或 Neo4j。

**表 3-9 表形态到实例的映射**

| 表形态 | 映射方式 | 注意 |
|----|----|----|
| 一行一个实体 | 每行一个实体，其余列作为属性 | 主键列做名称/标识符；不要把序号当实体 |
| 一行一条关系 | 起点/终点两列各生成实体，行生成关系 | 端点类型由本体签名决定，不靠列名猜 |
| 宽表 | 行主键做实体，其余列做属性；同义多列合成多值 | 电话1/电话2 合并；空值不写，不用逗号拼接 |
| 层级表（parent） | 子实体 + 属于/包含 关系 | 不用继承表达业务层级；同名节点用「名称·父节点」消歧 |
| 枚举列 | 枚举值作为维度类实体（行业、区域等） | 不要塞进属性字符串；无源枚举标预留 |
| 文档 / HTML 表格 | 先按整段 `<table>` 提取，再解析行列 | 全角括号 NFKC 归一；合并单元格先展开 |
| JSON / API | 按字段路径映射，保留 provenance | 数组字段展开为多值；派生字段写清计算规则 |

工程上最常见的四类陷阱要提前处理：Excel 表头带全角括号，NFKC 归一后对不上，列名匹配前统一把 （） 换成 ()；openpyxl read_only 对无默认样式的 CRM 快照可能只读到表头，直读数据用普通 load_workbook；MD/HTML 表格按 `<tr>` 逐行匹配拿不到整表，要先整段提取；转写/脱敏副本可能只剩表头，开工前先数真实数据行。

如果原始数据已经是逐条事实（facts JSONL），可以直接走 build_abox_from_facts.py：必填属性按本体库回填，缺口只报告，不阻断交付。重建说明用 report_abox.py 生成 before/after，数字从三件套现算，不手写。

映射结果写成 spec，实体、属性、关系分开，便于校验和增量合并：

```json
{
  "entities": [
    {"name": "需求评审", "type": "Task", "docs": 2,
     "provenance": {"source": "sprint.xlsx", "row": 12}},
    {"name": "张三", "type": "Resource"}
  ],
  "attributes": [
    {"head": "需求评审", "head_type": "Task",
     "attribute": "优先级", "value": "3"},
    {"head": "需求评审", "head_type": "Task",
     "attribute": "截止日期", "value": "2026-11-30"}
  ],
  "relations": [
    {"head": "需求评审", "head_type": "Task",
     "relation": "requires",
     "tail": "张三", "tail_type": "Resource"}
  ]
}
```

docs 表示被多少来源断言，默认 1；同一三元组多条会自动去重。provenance 建议保留 {source, row, page}，出问题能回溯。派生字段（由其它事实算出来的）要能说清计算规则，不要当原始事实写入。

红线：不发明数据里没有的实体或属性值；不确定的列列成“待确认清单”，不入库；类、属性、关系必须已在本体声明，未声明先回本体补，不要为了让校验通过而删数据或改本体。

#### 3.2.6 校验、合并与写库

校验分两层：build_abox.py --validate-only 在生成前检查 spec，validate_abox.py 在三件套落盘后逐条对本体库独立复验。前者可以修 spec，后者是交付前的最后一道门；退出码非 0 即失败。

```bash
# 生成前校验，ERROR 必须清零
python3 scripts/build_abox.py \
  --spec "$WORK/spec/abox.json" --tbox "$WORK/tbox" \
  --validate-only --strict

# 写 JSON 三件套 + 报告
python3 scripts/build_abox.py \
  --spec "$WORK/spec/abox.json" --tbox "$WORK/tbox" \
  --out "$WORK/instances" --report "$WORK/abox-report.json"

# 落盘后独立复验 + 覆盖统计
python3 scripts/validate_abox.py \
  --tbox "$WORK/tbox" --inst "$WORK/instances"
python3 scripts/coverage.py \
  --tbox "$WORK/tbox" --inst "$WORK/instances"
```

合并语义固定：默认 MERGE，已存在的实例/边不重复创建；属性会覆盖为本次值；同一实例多值属性合并为数组；关系用原关系名建边；实例 id 有唯一约束。--wipe-instances 只删 :实例 节点及其边，不动本体库，属于破坏性操作，必须用户明确确认。

```text
out/instances/
  entities汇总.json
  relations汇总.json
  attributes汇总.json
  复验.json
  覆盖.json / 实例覆盖.md / 属性覆盖.csv
```

**表 3-10 实例写库前的质量门禁**

| 门禁 | 标准 | 不通过时的动作 |
|----|----|----|
| 本体库校验 | --validate-only --strict 0 ERROR / 0 WARNING | 不写库，先修本体 |
| 实例库校验 | 0 ERROR；WARNING 逐条有解释 | 不写库，修 spec 或抽取 |
| 三类缺口 | 实体类、属性声明、关系签名缺口 = 0 | 回本体补定义，或改映射 |
| 必填缺口 | 0，或用户书面接受剩余缺口 | 回填；确认无法回填的记报告 |
| 关系越界 | 0；被丢弃的越界边有清单且已确认 | 换关系、改端点或补签名 |
| 备份 | ontology_baseline/、data_baseline/、docs/ 已备份 | 先备份再写 |
| 写库模式 | 默认 MERGE；--wipe/--wipe-instances 有明确确认 | 去掉 wipe 或再次确认 |
| 写后重导出 | 从 Neo4j 重导出实例库三件套作为新基线 | 不用内存对象当基线 |

写库报告至少包含这些计数，向用户回报时用同一组数字，并列出被丢弃条目的类型与原因：

```json
{
  "entities": 120, "relations": 340, "attributes": 560,
  "value_mismatch": 3, "relation_violation": 5, "entity_dup": 2,
  "required_autofill": 18, "required_missing": 4,
  "errors": [], "warnings": ["..."], "target": "neo4j"
}
```

#### 3.2.7 覆盖评估与缺口回灌

覆盖评估回答三个问题：原始记录有没有落成实例、关键字段有没有值、业务链有没有边。三个口径的分母必须来自源数据或本体定义，不能拿实例数当“原始应有数”。

实体记录覆盖率 = min(实例数 / 原始应有数, 1)

字段覆盖率 = 有值实体数 / 该类实例数

链接覆盖率 = 有目标边的头实体数 / 应有头实体数

**表 3-11 实例覆盖的统计口径**

| 维度 | 公式 / 口径 | 数据来源 | 失败动作 |
|----|----|----|----|
| 实体记录覆盖 | min(实例数 / 原始应有数, 1) | 花名册、合同号去重数、文档数 | 补抽取或补源数据 |
| 关键字段覆盖 | 有值实体数 / 该类实例数 | 需求核心字段清单 | 修抽取或改映射 |
| 关系链接覆盖 | 有目标边头实体数 / 应有头实体数 | 业务链定义（任务→资源等） | 补边、补签名或标无源 |
| 类覆盖 | 有实例业务类 / 业务类总数 | 实例库 | 并类、补数据或标预留 |
| 关系类型覆盖 | 有边关系类型 / 业务关系类型 | 实例库 | 三分类处置 |
| 签名覆盖 | 有边签名 / 签名总数 | 实例库 | 补抽取或删重复签名 |
| 属性覆盖 | 有值属性 / 业务属性总数 | 实例库 | 收敛核心字段，预留字段单列 |
| 必填缺口 | 必填缺失实例数 / 必填声明数 | 实例库 | 回填或报告缺口 |

coverage.py 同时输出机器可读的 覆盖.json、人读的 实例覆盖.md 和逐条属性明细 属性覆盖.csv；validate_abox.py 输出 复验.json，包含三类缺口、必填缺口和按类/关系的计数。

除覆盖率外，还要看结构合理性：业务关系密度（业务边/业务实体）过低说明链接不足；孤儿实体（度数为 0）和零属性实体占比高说明抽取只做了“点”没做“边”；Top3 类集中度过高说明长尾类空置；关键断链（任务无资源、决策无证据、风险无缓解）要单列。

缺口分三类回灌，不能混写：**本体缺定义**回本体生成流程补类/属性/签名；**有源未抽**回抽取脚本修映射；**无源**标预留，不造值。把数据缺口写成“本体已支持”，会让下一轮评估继续误判。

**收敛轮数（v1.33 重标定，取代 v1.18 的"约 6 轮"）**：把属性批切成 20 轮（每轮 3 万条）写入，按实体粒度重算工单，覆盖率 **0 → 0.730 → 0.895 → 0.952 → 0.976 → 0.989 → 0.994 → … → 1.000**，工单 **14,886 → 45（第 7 轮）→ 22（第 8 轮）→ 1（第 13 轮）**。

三条停止规则的触发轮次（实测）：

| 规则 | 触发轮 | 触发时剩余工单 | 评价 |
|----|----|----|----|
| 连续 2 轮覆盖率增量 <1%（v1.18 采用） | **7** | 45 | ❌ 停太早：覆盖率 99.7% 时长尾还占 3% |
| 连续 2 轮开放工单 <50 | **8** | 22 | ✅ 工程默认 |
| 连续 2 轮关闭率为 0 / 关闭率 <10% | **15** | 1 | ✅ 审计默认（确认"确实没料了"） |

**关键**：第 13 轮工单降到 1 之后，第 14–20 轮每轮仍写入 2.9–3 万条属性、**关闭数恒为 0**，合计约 **20 万条无效写入**。这个 1 是源数据里根本没有属性的实体。

**因此停止条件改为双判据**：`开放工单 < 50` **或** `连续 2 轮关闭数为 0`，先到先停；停下后把残余工单标 `source_gap` 并**移出循环**，转外部源/人工核实队列，不得留在下一轮重试。覆盖率增量只作观测指标，不再作停止条件。

**工单粒度与收敛条件（v1.16，实测）**：20 万条属性回灌后，按**关系**聚合出的 10 条"实体缺属性"工单**一条都没关闭**——因为回灌只补了 6,744 个属性，而工单要求"该关系下全部实体都有属性"，粒度不匹配就永远关不掉。因此规定：① 工单必须按**实体粒度**生成（一条工单 = 一个实体的一项缺口），关系级只作为统计视图；② 收敛条件写成"连续两轮覆盖率增量 < 1% 或该工单涉及实体数降为 0"，超过 3 轮未收敛的工单转人工判定是否标预留。

重建前后必须输出 before/after：实体、关系、属性、分类计数、哈希、delta。计数不变时说明原因：数据本来一致、抽取规则未变、还是新 Schema 无源。三者都没有，计数不变是正确结果，不要为了“有变化”硬造实例。

#### 3.2.8 重建、版本化与增量更新

按当前本体库重建实例，按固定九步执行：备份基线 → 盘点原始数据 → 读当前本体库 → 小样本映射 → 全量生成 spec → --validate-only --strict → 默认 MERGE 写库 → 从 Neo4j 重导出 → 跑 coverage.py 与九项度量并回灌缺口。任何一步失败都停在上一步，不带病写库。

版本化用快照标识把本体库与实例库绑定：snapshot_id = hash(本体库) + hash(实例库) + timestamp。查询请求携带 tbox_hash 与 abox_snapshot；两者与当前服务快照不一致时拒绝编译并刷新索引，避免“新 schema 查旧实例”或“旧查询命中新类型”。

- **增量更新**：默认按实例 id upsert；源记录消失时软删除（保留 valid_to 与 tombstone 30 天），不做物理删除。
- **全量重建**：只在本体库发生破坏性变更（删类、改签名、改属性类型）或需要重新计算派生字段时执行。
- **id 稳定**：实例 id 一旦生成不再改名；实体改名通过别名属性与 same_as 迁移，旧 id 保留映射，不把边全部重写。
- **假设边**：链接预测/补全产生的边默认写影子图，带 TTL（默认 30 天）；外部证据确认、N=2 个独立来源一致或人工审核通过后才晋升主图。
- **质量门禁**：只有通过校验和覆盖评估的实例进入检索索引；HYPOTHESIZED 边不得用于终止决策，只能作为候选路径。

### 3.3 知识层快照与对外契约

检索层和决策层消费的不是“永远在变的库”，而是带版本的知识层快照。快照把本体库契约、实例库事实、对齐关系和规则层绑定在一起，保证同一次查询里的类型判断、边校验和证据回溯使用同一份语义。

本体库快照至少包含：tbox_hash、版本号、类表与父类闭包、关系签名白名单、属性声明与值类型、必填标记、规则层版本。查询编译器只接受快照内的类、关系和属性；LLM 输出的动态枚举也由快照生成，避免模型编造不存在的关系。

实例库快照至少包含：abox_snapshot、实体索引（id、规范名、别名、类型）、属性值、关系边（关系名、端点、provenance、置信度、valid_from/valid_to）、项目/租户作用域、对齐边、影子边。路径搜索的邻接表、边权和证据链都从这里构建。

**表 3-12 知识层对外契约**

| 消费方 | 需要的契约 | 快照来源 | 失效模式 |
|----|----|----|----|
| 查询编译器 | 类闭包、签名白名单、属性类型、关系方向 | 本体库快照 | 快照不匹配 → 拒绝编译并刷新 |
| 实体链接 | 规范名、别名、类型、候选分数 | 实例库实体索引+对齐层 | 索引过期 → 降级到离线索引并报 stale_index |
| 路径搜索 | 邻接表、边权、provenance、置信度 | 实例库关系边 + 补全边 | 关键边缺失 → 诊断码 E03/E05 |
| 计划生成 | 关系→动作模板、审批门禁 | 本体库规则层 + 4.5 映射 | 模板缺失 → 降级为验证动作 |
| 质量评估 | 路径质量标志、覆盖率、空置率 | 3.1/3.2 指标 + 4.6 日志 | 指标异常 → 进入质量问题队列 |

一致性规则有三条：第一，查询请求携带 tbox_hash 与 abox_snapshot，服务端比对后再执行；第二，每条证据路径记录快照标识，回放时能定位到当时的类和边；第三，写路径只允许经过校验的实例库进入主索引，影子边、候选对齐和未确认补全边留在影子层，不能与主图混算。

**快照必须不可变（v1.13）**：快照发布即冻结，实现上对 TBox/ABox 做深拷贝。否则会出现一种隐蔽故障——快照对象与调用方共享引用，后续业务写入改掉了已发布快照的内容，而 `tbox_hash` 是构建时算出来的，消费者按 hash 缓存就会拿到与 hash 不符的数据（本约束由契约演练的失败用例直接暴露：13/14，同内容两次构建 id 不一致）。

这样，第 4 章的路径查询可以明确区分“本体不允许”“实例不存在”“证据不足”三类失败；第 5 章的规划器也能判断一个动作模板是来自当前本体，还是来自已过期的缓存。知识层因此不只是存储，而是可版本化、可校验、可回滚的决策基础设施。

### 3.4 本体记忆与 LLM 参数化知识的协同

本体图谱是系统显式维护的结构化记忆，而大语言模型在预训练中已内化了大量领域概念与关系。两者不是替代关系：显式记忆承载“契约”，模型记忆承载“语义”。凡是被机器校验、剪枝、审计的判断必须进本体；凡只影响提示质量、不参与校验的判断留给模型。本节给出职责边界、入本体门禁、运行时裁决与回灌闭环四部分。

#### 3.4.1 职责边界

**表 3-13 显式本体记忆与 LLM 参数化认知的职责边界**

| 维度 | 本体记忆（本体库/规则层） | LLM 参数化认知 |
|----|----|----|
| 判定性质 | 二值判定，封闭世界假设 | 概率分布，开放世界假设 |
| 可复现性 | 绑定 tbox_hash，跨请求一致 | 同一提问可能得到不同回答 |
| 可审计性 | 每条定义带正例/反例，可回放 | 无法给出可回放的判定依据 |
| 覆盖范围 | 仅声明过的概念与签名 | 广，含常识与长尾知识 |
| 错误代价 | 校验拒绝、可拦截可修复 | 静默出错，难以定位 |
| 变更成本 | 需建模、校验、版本化 | 换模型或微调，粒度不可控 |

按此边界，具体职责分派如下：

- **入本体记忆**：类层级与祖先闭包（类型判断）、关系签名与白名单（路径剪枝）、属性声明与值类型（实例校验）、意图到路径模式映射（编译器消费）、关系类型到动作模板映射（计划生成）、同义合并与规范化口径（实例一致性）、规则层治理规则（唯一性、白名单、可推导性等）。
- **留给 LLM**：提及检测与候选打分（最终裁决在闭包兼容检查）、自然语言到 TaskFrame 的抽取、航点与概念路径建议（本体校验后采用）、查询结果的解释文本生成、长尾别名与缩写的召回提示。

两条红线：第一，LLM 能稳定答对的常识不入本体，否则类使用率与属性空置率指标会暴露过度建模；第二，同一治理口径不得双写，prompt 中的文字约束必须由本体库快照投影生成，不允许人工另写一份。

#### 3.4.2 入本体判定：六问门禁

一条领域定义是否需要进入本体记忆，按以下六个问题顺序判定，命中即停：

**表 3-14 定义入本体与否的六问门禁**

| 序 | 问题 | 命中后的处置 |
|----|----|----|
| Q1 | 该定义是否出现在校验、剪枝或审计的代码路径上？ | 必须入本体（如关系签名用于路径剪枝） |
| Q2 | 是否被查询编译器、链接器或计划生成器机器消费？ | 必须入本体（如意图到路径模式映射） |
| Q3 | 判断错误会污染主图或触发合规风险？ | 入本体并写规则层（如唯一性、白名单） |
| Q4 | 是否要求跨请求、跨用户、跨项目的一致口径？ | 入本体（如同义合并规则） |
| Q5 | 能否写出封闭的正例与反例？ | 入规则层（3.1.5 的规则 JSON 形态） |
| Q6 | 以上全否 | 留给 LLM，运行时打点留痕 |

门禁的输入不是抽象判断，而是分歧证据：如果一条“LLM 隐性使用但本体未声明”的关系反复出现在拒绝日志里，它天然满足 Q1 或 Q2；反之，如果一条本体定义从未被任何查询、校验或计划消费，它连 Q1 都不满足，是修剪候选。

**自动挡覆盖率（v1.28 重算，取代 v1.16 的 65.4%）**：v1.16 的 65.4% 是用 LLM 判定算出来的，而 300 题核对已证明模型判否的错误率 **60.4%**（假接受 1–3 条、假拒绝 53–83 条），该数字作废。重算口径改为**结构化信号优先、LLM 只保留放行权限**：

| 门禁设计 | 自动放行 | 错误放行（/300） | 工单率/千 | 工单白干率 | FTE@1万/日 |
|----|----|----|----|----|----|
| 纯 LLM（旧） | 46.0% | 3（2.17%） | 540.0 | 61.7% | 44.9 |
| 纯结构化 | 22.7% | 2（2.94%） | 356.7 | 86.0% | 42.7 |
| **混合-保守（默认）** | **52.3%** | 5（3.18%） | **143.3** | 69.8% | **16.7** |
| 混合-宽松 | 58.3% | 8（4.57%） | 83.3 | 72.0% | 9.7 |

三个出口：`auto_pass`（自动放行）、`clarify`（自动澄清，不占人工）、`ticket`（转人工）。**验收口径是工单率与错误放行率，不是"自动判定率"**——后者可以被"把多答案全推给人工"刷高，代价是工单白干率 86%。

**人力换算式（不许口头估算）**：日工单 = 日查询量 × 工单率；FTE = 日工单 ÷ (有效工时 6h ÷ 单均时长)。按 1 万查询/日、4 min/单、hop1 为主流量：混合-保守需 16.7 FTE（配置 20 人含余量），纯 LLM 需 44.9 FTE。**人手只配到需求的 80% 时，第 30 天积压 3.2 万单且线性发散**，因此配置口径是按峰值、不留缺口。

**门禁的落地形态仍是半自动**：自动挡负责分流与打标，人工只处理 `ticket` 那一档；对外描述不得写成"六问可机器判定"。

#### 3.4.3 运行时裁决：三级规则

查询与决策过程中，LLM 的判断与本体契约的关系按三级裁决：

- **一致则放行**：LLM 使用的概念、关系与闭包兼容，直接执行，置信度取本体 provenance，不额外调用模型。
- **未定义则降级**：本体未声明但 LLM 高置信的判断，只能进影子层：候选边带质量标志与缺口码，供后续评审；不得进入主图参与决策。
- **冲突则拒绝**：LLM 判断与本体签名或规则冲突时，本体赢；拒绝执行并返回结构化错误码，不做“软修复”重试。

三个机制支撑这套裁决：S2/S4 的“LLM 提议、本体裁决”（4.3.2）；LLM 输出契约中的动态枚举由快照生成（4.3.4），从源头防幻觉与防注入；影子边治理（3.2.6/4.4.5）保证 LLM-only 判断永不直写主图，晋升必须外部证据或人工审核。

**L2 分支的启用前提（v1.16，实测）**：三级裁决里“未定义则降级”这一级依赖"关系名是否在白名单内"来分流。在 180 条断言上（60 图内真、60 图外真、60 扰动假）：图内真 60/60 进 L1、扰动假无一被 L1 接受；但 **L2 分流数完全取决于白名单与实例层命名是否对齐**——直接用 schema.org 白名单时 L2=0（120 条全部升级人工），换成与实例层对齐的白名单后 L2=120。**结论：3.2.3 对齐/3.2.5 映射未完成时，不得启用 L2 分支**，否则治理流量会全部压到人工队列。

#### 3.4.4 回灌闭环：双向收敛

“哪些定义该入记忆”不是建模期一次性决定，而是运行期持续收敛的双闭环：

**表 3-15 分歧捕获与回灌协议**

| 步骤 | 动作 | 执行方 | 产物 |
|----|----|----|----|
| 捕获 | 编译器拒绝 LLM 使用未声明概念/关系时写分歧日志 | 查询编译器 | PathQueryLog 的缺口码 |
| 聚合 | 按概念/关系/属性聚类，统计频次、意图分布、项目分布 | 质量评估管道 | 分歧簇报告 |
| 触发 | 同一未声明关系出现 ≥20 次且涉及 ≥2 种任务意图 | 阈值门禁（可按基准校准） | 评审队列 |
| 评审 | LLM 生成候选 domain/range 与正例反例，人工确认 | 本体工程师 + LLM | 定义评审单 |
| 入库 | 走 build_tbox.py 门禁（0 ERROR），tbox_hash 更新 | 构建脚本 | 新版本本体库 |
| 重建 | 破坏性变更触发实例库重建评估（3.3 一致性规则） | 变更管理 | 重建任务 |
| 修剪 | 本体中连续空置的定义（类使用率 < 60%、属性空置）评审后并类或删除 | 质量评估 + 本体工程师 | 修剪工单 |

两个方向合起来：LLM 的隐性分歧回灌成显式契约，显式契约的长期空置收回给 LLM 处理。前者防止记忆缺失，后者防止记忆膨胀。回灌频度建议与 4.6.10 的持续运营节奏对齐，每月一次评审，不随每次分歧实时改本体。

### 3.5 本体库更新算法

3.4.4 定义了“何时评审”，本节给出“评审通过后如何安全落地”的完整算法。本体更新不是执行一条 MERGE，而是一个把变更分类、依赖分析、重建决策、写库与验证串联起来的有向流程；输入是运行期信号（分歧日志、空置度量、查询命中率），输出是带新 tbox_hash 的可交付本体库版本。

#### 3.5.1 变更分类：破坏性判定

任何变更先归类，不同类别的写库路径与门禁强度不同：

**表 3-16 本体库变更类别与判定**

| 变更类别 | 判定 | 写库路径 | 对实例库的影响 |
|----|----|----|----|
| C1 新增类/属性/签名 | 只增不删不改语义 | 直接走 build_tbox.py MERGE | 无影响 |
| C2 语义收窄（改 range、加必填） | 已有实例可能越界 | MERGE + 新增门禁全量复验 | 部分实例变非法，进待修清单 |
| C3 语义改写（改 parent、改值类型） | 闭包/签名兼容性变化 | MERGE + 破坏性变更流程（3.5.3） | 实例重映射或重建 |
| C4 删除/停用定义 | 零实例或已标预留 | 软删除（停用标记）+ 观察期 | 无影响；观察期内可回滚 |
| C5 元信息变更（comment、正例反例） | 不影响判定逻辑 | 直接 MERGE | 无影响 |

判定由脚本自动完成：比对新旧本体库三件套的 diff，按上表规则归类；一批变更跨类别时按最高风险类别走全流程，不拆包降门禁。

#### 3.5.2 增量更新算法（C1/C5）

低风险变更走快速路径，但每一步仍可验证、可回滚：

```python
def tbox_incremental_update(change_set, tbox_dir):
    """C1/C5 类变更：新增定义与元信息修改。"""
    # 1. 冻结当前基线
    baseline = load_and_hash(tbox_dir)          # tbox_hash_v

    # 2. 幂等合并：以 spec 为准重建三件套，MERGE 语义
    new_spec = merge_spec(load_spec(tbox_dir), change_set)

    # 3. 门禁：0 ERROR 才写（--strict 下 WARNING 也不放过）
    r = run("build_tbox.py --spec new_spec --validate-only --strict")
    if r.errors: return reject(r.errors)        # 不落盘

    # 4. 写库：MERGE，不 --wipe
    run("build_tbox.py --spec new_spec --out tbox_dir")

    # 5. 验证：新哈希 + 差量报告 + 结构度量不回退
    after = load_and_hash(tbox_dir)             # tbox_hash_v+1
    metrics = run("metrics.py --tbox tbox_dir")
    if metrics.regressed(baseline_metrics):
        rollback(tbox_dir, baseline)            # 哈希回滚
        return review_required(metrics.delta)

    # 6. 发版：新快照对齐（3.3），查询绑定新 tbox_hash
    return publish(after, delta=diff(baseline, after))
```

增量更新的安全前提：**不改旧定义，只加新定义**。任何触碰旧语义的变更都必须升级到 3.5.3。

#### 3.5.3 破坏性变更算法（C2/C3）

语义变更先评估爆炸半径，再决定重建策略：

```python
def tbox_breaking_update(change_set, tbox_dir, abox_dir):
    """C2/C3 类变更：收窄/改写语义。七步，任何一步失败停在上一步。"""
    # 1. 影响分析：哪些实例/边会变非法
    impact = analyze_impact(change_set, tbox_dir, abox_dir)
    if impact.entity_violations > threshold or impact.edge_violations > threshold:
        return review_required(impact)          # 人工评审爆炸半径

    # 2. 备份双基线（本体库 + 实例库）
    backup(tbox_dir, abox_dir)

    # 3. 重建实例库（走 3.2.8 九步流程），MERGE 写回
    rebuilt = rebuild_abox(tbox_dir_with_changes, sources=True)
    r = run("validate_abox.py --tbox new --inst rebuilt")
    if r.errors: return abort_with_backup()      # 原基线未动

    # 4. 双写切换：新本体库 + 重建实例库作为候选基线
    candidate = snapshot(new_tbox, rebuilt)     # 候选快照

    # 5. 影子验证：抽生产查询在候选基线重放，对比指标
    replay = replay_queries(sample=0.05, baseline=candidate)
    if replay.psr_drop > 0.02 or replay.q_total_drop > 0.03:
        return reject(replay.report)            # 对齐 4.6.6 发布门禁

    # 6. 原子切换 + 旧基线保毒（保留 N 天可回滚）
    promote(candidate)

    # 7. 回灌：受影响查询/诊断码写回质量队列，触发缺口回灌
    return report(impact, replay, new_hash)
```

七步中第 1 步影响分析与第 5 步影子重放是两条硬门禁：前者控制“改了多少”，后者控制“改完好不好”。两门禁都不通过则不切基线。

#### 3.5.4 修剪与停用（C4）

修剪不立即删：先停用，后观察，再删。观察期默认 30 天，期内查询命中为 0 且无实例引用才真删：

- 停用标记：定义加 deprecated=true 与停用日期，仍参与校验但新 spec 不允许再写入；
- 观察期指标：该类/关系在 PathQueryLog 的命中率、实例引用计数、下游动作模板引用数；
- 真删条件：三项全零且经 3.4.4 修剪工单确认；否则解除停用并记录原因；
- 删除动作：物理删只发生在下个大版本，当版本只做软删除，保证同版本内可回滚。

**到期判定的时间口径（v1.22）**：观察期按**当地日历日**计算，判据是 `(today - deprecated_on).days >= 30`，**不是**"停用时刻 + 30×24 小时"。理由有三条，都有实测支撑（报告 v3.3 实验 AF）：

1. **夏令时**：美东 2026-03-08 少 1 小时，用墙钟相加得到的"30 天后"那一瞬，真实经过只有 **719 小时**；按固定 720 小时门槛会晚 1 小时才到期，跨时区部署时同一批停用项会在不同时点被删。
2. **闰年**：2028-02-29 存在，"加 30 天"必须逐日推进；`02-01 + 30` 得 `03-02`，与"加 720 小时"在某些年份不同。
3. **跨年**：12-20 停用、次年 01-19 到期，年度任务重算不得重置观察期计数。

配套要求：

- **停机补跑必须幂等**：调度器停 3 天后恢复，错过的日切逐日补，但**不得重复评估、不得重复删除**；审计里每条停用项的评估记录必须唯一（按 `(object, eval_day)` 去重）。
- **安全阀优先于时长**：三项指标未全零或工单未关闭时，即使超过 30 天也不删，只记录 `blocked_by`。
- 时区以**业务所在时区**为准并写进配置；不同时区的实例各自按当地日期判定，不做 UTC 统一取整。

#### 3.5.5 与查询层的联动

本体更新的每一步都与 4.1 的四层参与模型联动：

- **L1 信号输入**：更新触发信号主要来自查询编译器的拒绝日志（E02/E10）与 4.6 的空置度量，而非人工直觉；
- **变更期间的一致性**：更新过程中查询仍绑定旧 tbox_hash；新版本发布后 3.3 的一致性规则拒绝旧快照请求并强制刷新，不存在“半新半旧”的中间态；
- **失败回退到 L4**：若某类查询在更新后持续失败，4.1.1 的 L4 重排/解释层会标注“本体版本变更导致”，避免把版本问题误判为语义问题。

本节算法与 3.1.6 的九项度量、3.2.8 的重建流程、3.4.4 的回灌协议互为入口与出口：度量发现空置 → 3.5.4 修剪；分歧回灌通过评审 → 3.5.2 或 3.5.3 落地；落地后新版本重新参与度量，闭环收敛。

### 3.6 记忆管理方案：上下文压缩主算法 + 图谱记忆补充

前文回答了“知识存哪里、怎么校验、怎么更新”，但没有回答“Agent 运行时的对话记忆怎么治理”。长任务的对话历史会无限增长：工具密集型任务每步追加一次调用与结果，上下文最终逼近窗口上限，模型要么中途截断、要么静默退化。本节给出完整记忆管理方案：**以 DeepSeek dsh harness 的上下文压缩算法为主算法**，负责对话流的压力监测、结构化检查点生成与溢出恢复；**以本体/实例图谱记忆更新与最短路径计算为补充**，负责把压缩丢弃的领域事实分流落图（写路径）、并在需要时按需解压回读（读路径）。主算法管住“当前工作集”，补充机制管住“长期可验证记忆”，两者在检查点锚点上对接。

#### 3.6.1 总体架构：压缩与解压的职责划分

**表 3-17 三层记忆的职责与机制**

| 层 | 载体 | 写入时机 | 读取时机 | 治理机制 |
|----|----|----|----|----|
| 工作记忆（L0） | 对话上下文 + 结构化检查点（八段基础 + Graph Memory State 锚点段） | 每步消息追加；压力触发时生成检查点 | 每次请求携带 | 压缩主算法（3.6.2–3.6.4） |
| 图谱记忆（L1） | 实例库实例图 + 影子边 | 压缩前事实分流（3.6.3）；运行期影子写入 | PathQuery 解压回读（3.6.5） | 三类约束校验 + 影子晋升门禁 |
| 本体记忆（L2） | 本体库 + 规则层 | 3.4.4 回灌评审通过后走 3.5 算法 | 查询编译校验 + 决策模板消费 | 六问门禁 + 版本化发版 |

三层记忆各自回答不同的问题：L0 回答“这个会话正在做什么”，靠主压缩算法控制体量与成本；L1 回答“这个会话发生过哪些可验证的事实”，靠 MERGE 语义与 provenance 保证可回放；L2 回答“整个企业跨会话一致的契约是什么”，靠 tbox_hash 保证可复现。压缩主算法与图谱补充机制的分工边界：**主算法从不写图，图谱从不承载对话流**。事实从 L0 到 L1 的迁移发生在压缩前的分流步骤，而不是压缩后的“回收”——摘要一旦生成，丢弃内容对主算法不可逆（这是压缩的定义），必须靠 L1 锚点找回。

#### 3.6.2 压缩主算法：压力触发与预算解析

主算法复用 dsh harness 的 compaction-basic 设计，四个工程决策直接采纳：

**（1）每步检查，而非每轮一次。** 压力检查在每个成功步骤结束后的下一个请求派发前运行，而不是等一轮结束。失控轮次内每步都追加“调用+结果”，只有逐步检查才能在步骤边界及时压缩早期已关闭的工具对；轮次中途不压缩未闭合的配对，配对平衡（见 3.6.4）是硬约束。

**（2）路由感知的预算解析。** 触发阈值不是全局常数，而是按当前路由模型的容量 W 解析：

$$
T_{threshold} = \min\big(\lfloor W \cdot r_{threshold} \rfloor,\ W - O_{reserved} - H_{headroom}\big)
$$

默认 $r_{threshold}=0.8$，保留尾部比例 $r_{retain}=0.16$，headroom 默认 65,536 token，$O_{reserved}$ 取请求输出上限。每次检查重新解析：模型切换、输出上限变化立即生效，不存在“用旧容量的阈值剪新模型的上下文”。同一部署可按精确 {provider, model} 组合覆盖策略（摘要模型、重试次数、阈值），策略校验在加载期失败而非运行期。

**（3）剪枝优先于摘要。** 压力达到阈值后，先跑工具结果剪枝（把超大 tool/result 重写为摘要+指针），重新计量；只有剪枝不足以缓解时才调用 LLM 生成检查点。剪枝是确定性、零 LLM 成本的，能独立解除压力时就不消耗摘要预算。

**（4）摘要调用复用 KV 缓存。** 摘要输入不是裸文本，而是重放被遮蔽区段的对话前缀（系统提示词 + 工具 schema + 区段消息），再把压缩指令作为尾部 user 消息追加。这使摘要调用是上一个真实请求的前缀，提供方热 KV 缓存直接命中，摘要成本从“整段重算”降到“尾部增量”。

溢出兜底：提供方返回规范化 CONTEXT_WINDOW_EXCEEDED 时，不依赖容量元数据，执行一次最大且平衡的头部缩减（先剪枝后摘要）；仅当表层替换真实发生（replaceGeneration 增加）才重试请求，最多 1 次；重试用尽保留原始错误，不做无限重试。

#### 3.6.3 压缩前事实分流：落图写路径（图谱补充一）

主算法生成检查点时，被遮蔽区段里的领域事实必须先分流落图，否则压缩后不可逆丢失。分流不是“把摘要写进图”，而是按 3.2 的映射流水线把区段中的实体、关系、属性值抽取为实例库 spec，走既有校验合并写库：

**表 3-18 分流四步与门禁**

| 步骤 | 动作 | 复用机制 | 失败处置 |
|----|----|----|----|
| 事实抽取 | 从待遮蔽区段抽取（实体，属性，关系）三元组候选 | 4.3.2 的 TaskFrame 抽取与实体链接（S1/S2） | 抽取失败不阻塞压缩，只降级为锚点 |
| 签名校验 | 类/属性/签名必须已在本体库快照声明 | 3.2.4 三类约束 | 未声明进待确认清单（3.2.5 红线） |
| 合并写库 | 按 MERGE 语义幂等写入，同义合并、same_as 对齐 | 3.2.6 校验合并写库 | 写库失败不阻塞压缩，补偿队列重试 |
| 锚点登记 | 检查点第九段记录写入实体的稳定 ID 与查询锚 | 3.6.4 检查点结构 | 无锚点则该段写 (none) |

分流的三条边界：**抽取不阻塞压缩**（主算法的延迟预算优先，分流失败不影响压缩吞吐，但会降低可回溯性——**v1.42 实测更正**：原文写“不影响正确性”，实测只在“检查点已保住绝大多数事实”的前提下成立，分流失败的可量化代价是锚点回读那部分收益归零，见 3.6.8）；**写图永不绕过门禁**（影子边走 4.4.5，未声明概念走 3.4.3 降级，不允许“为了保留事实而放松校验”）；**落图的是事实不是对话**（对话语气、试错过程、用户偏好仍留在 L0，只有可验证的三元组才进 L1）。

#### 3.6.4 检查点结构：八段基础 + 锚点扩展段与收缩证明（主算法核心）

检查点不是自由文本摘要，而是固定结构化 Markdown：八段基础段直接采纳 harness 设计，外加第九段锚点扩展段，每段有明确职责，空段写 (none)，不丢段：

```text
## Primary Request and Intent      ← 用户原始目标与演进（逐字引用关键表述）
## Key Technical Concepts          ← 技术栈、约定、模式
## Files and Code                  ← 精确路径 + 关键变更
## Errors and Fixes                ← 错误字符串 + 解法 + 用户反馈
## Pending Jobs                   ← 未完成的显式任务
## Current Work                    ← 检查点时刻正在进行的事
## Next Step                      ← 单一下一步动作
## Critical Context               ← 约束、偏好、开放问题
## Graph Memory State             ← [本设计扩展段] 落图事实的锚点清单
```

前八段直接采纳 harness 的设计；第九段 Graph Memory State 为本设计扩展，内容为 3.6.3 分流登记的锚点：每行一个「实体 ID / 类别 / 一句话摘要」，供 3.6.5 解压回读。锚点必须是落库后的稳定 ID（不是自然语言描述），因为检索走的是 PathQuery 而非全文匹配。

检查点生成的四条硬约束：

- **收缩证明**：框架化摘要的 token 估算必须严格小于被遮蔽内容的 token 估算，否则不提交任何内容，本轮放弃，继续积累后再压。压缩不能“越压越大”。
- **关键事实抽查（v1.42 新增）**：收缩证明只保证变短，不保证没丢关键信息。提交前从待遮蔽区段抽 n 条已知事实（优先取 `[RETRACTED]` 与 `[CONSTRAINT]` 条目），检查点回读能否仍答对；命中率低于阈值（建议 0.9）即视为失败尝试，保留原历史继续积累。实测该检查要挡的正是不可落图事实的静默丢失（3.6.8）。
- **配对平衡**：遮蔽边界永不切开一个步骤内的工具调用/结果对。截断点落在步骤内部时，边界回退到最近的平衡位置。进行中的轮次不享受特殊保留，但其未闭合尾部永不进入遮蔽区段。
- **增量合并**：检查点提示词要求“若上下文已有前一个检查点，不逐字复制，保留仍真的事实、丢弃过时的、合并新信息为单份检查点”。检查点始终只有一个，位于头部，不堆叠。
- **头锚定**：自动压缩始终从表层头部开始，把先前的检查点与新压缩的历史合并，保证前缀单调稳定：检查点之后的消息永不重写，KV 缓存只从检查点位置开始缺失。

#### 3.6.5 锚点解压：PathQuery 回读（图谱补充二）

压缩把 L0 中被遮蔽的事实移除，但 L1 保存了可验证版本。当后续步骤需要已被压缩的细节时，Agent 不重放历史，而是把检查点第九段的锚点交给最短路径计算，按需解压：

```python
def recall_from_checkpoint(anchor: EntityId, question: TaskFrame) -> Subgraph:
    """从检查点锚点出发，用最短路径查询按需回读。"""
    # 1. 锚点解析：实体 ID 在当前实例库快照中定位；
    #    已重建版本中 ID 不存在时，按 same_as 链解析
    node = abox_snapshot.resolve(anchor)          # 缺失 → E01 起点未接地；same_as 断链 → E09 对齐缺失

    # 2. 编译：问题走 4.3 八阶段流水线，起点集含锚点实体，
    #    终点/约束由 question 给出，输出形态 = 证据子图
    query = compiler.compile(question, start_nodes=[node])

    # 3. 求解：4.1 双阶段算法——LLM 划界 + 图引擎 k-best；
    #    深度限制 ≤ k_max、结果取 Top-K 截断（4.1.2/4.1.3 口径）
    result = engine.constrained_shortest_paths(query)

    # 4. 回读结果作为普通工具结果进入上下文尾部，参与下一轮决策；
    #    不重放原始对话，不把 L1 事实直接“写回” L0 摘要
    return result.as_observation()
```

解压的经济性：回读结果落在上下文尾部，不重写检查点，因此不破坏前缀缓存；每次回读有独立检索预算，不会“一次回读拉爆上下文”。解压的正确性边界：回读的是 L1 当前快照的事实，不是被压缩对话的原文——如果事实在压缩后已被 3.5 更新算法修订，回读返回的是修订后版本。这是设计意图而非缺陷：L1 是唯一权威源，对话原文的记忆职责在压缩时刻就已终止。

#### 3.6.6 三级一致性裁决：回读结果与检查点的冲突处理

回读事实可能与检查点叙述（前八段的自然语言记忆）发生冲突，裁决复用 3.4.3 的三级规则并具体化：

**表 3-19 回读冲突的三级裁决**

| 情形 | 判定 | 处置 |
|----|----|----|
| 一致 | 锚点回读与检查点叙述兼容 | 直接使用，置信度取路径 provenance |
| 叙述过时 | 回读事实更新（3.5 变更链或 4.4.5 影子晋升修订过） | 采纳回读，检查点下一轮合并时自然更新 |
| 叙述错误 | 回读与检查点叙述矛盾 | 采纳回读（L1 赢），分歧写日志；若同矛盾重复出现，进 3.4.4 回灌评审 |

裁决的默认方向永远是 L1 赢：图谱是可校验、可版本化的权威源，检查点是它的有损投影。**v1.42 补充**：只有**可落图事实**同时存在 L1 与检查点两个来源；用户硬约束、试错解法、已作废结论、待办这类事实压根不进 L1，此时检查点是唯一来源，**没有任何仲裁者**。因此检查点中这类条目必须显式标注 `authority=checkpoint`，不得作为对外证据引用（与 5.6.3 的证据忠实性要求一致）。唯一例外是回读本身失败（E02 本体沉默、E01 起点未接地、E09 对齐缺失或 E03 图不连通）时，按 4.4 补全阶梯处理，而不是用检查点叙述“顶替”事实。

#### 3.6.7 失败模式与恢复路径

**表 3-20 记忆管理方案的失败模式与恢复**

| 失败模式 | 影响 | 恢复路径 |
|----|----|----|
| 摘要生成失败（网络/限流） | 本轮不提交任何内容，表层不变 | 记录失败尝试，继续当前轮；积累后重试 |
| 摘要不收缩（≥被遮蔽内容） | 若提交会越压越大 | 拒绝提交，本轮放弃，积累更多历史后再压 |
| 分流写库失败 | 部分事实未落图，锚点缺失 | 压缩照常完成；写库进补偿队列重试；锚点段写 (none) |
| 锚点解析失败（实体已重建） | 回读无法定位 | same_as 链解析（E09）；实体消失按 E01；解析成功但路径不通按 E03，分别走 4.4 补全阶梯 |
| 回读与检查点叙述矛盾 | 决策依据不确定 | L1 采纳，分歧日志留痕；重复矛盾进回灌评审（3.6.6） |
| **检查点生成成功但失真（v1.42）** | 压缩照常提交，关键事实静默丢失 | **提交前关键事实抽查不达标即视为失败尝试**：不提交、保留原历史、打点告警 |
| 溢出重试用尽 | 请求被拒绝 | 保留原始提供方错误，转人工介入，不无限重试 |
| 压缩中途崩溃 | 未闭合事务留下孤儿标记 | 重放时检测孤儿标记，视为失败尝试，从持久表层恢复 |

所有恢复路径共享同一原则：**压缩永不因补充机制失败而阻塞**（分流失败只降级可回溯性），**图谱永不因压缩而放松门禁**（校验失败进待确认清单，不直写）。主算法与补充机制在失败时各自退化到独立可运行状态：主算法退化成纯摘要压缩（无锚点段），图谱退化成离线知识库（无运行时回读），两者互不为前提。

本节与全文的闭环关系：3.6.3 分流写库复用 3.2 的映射与校验；3.6.5 回读复用 4.1 的双阶段算法与 4.3 的编译流水线；3.6.6 裁决复用 3.4.3 的三级规则；回灌评审走 3.4.4，本体修订走 3.5。记忆管理不是新增的平行系统，而是把第 3、4 章既有机制组织到对话生命周期的压缩-解压路径上。

#### 3.6.8 实测边界与逐条裁决（v1.42）

依据报告 v3.24（`exp_63`）：12 段工程型长对话、84 个探针针（24 可落图 G / 60 不可落图 N）、四臂（全量 / 八段检查点 / 九段+锚点回读 / 锚点缺失）× 三档摘要提示词，共 1,008 次探针、零调用失败。压缩比 p50 = 0.29~0.33。

| 提示词 | 全量 | 八段检查点 | 九段+锚点回读 | 锚点缺失 |
|----|----|----|----|----|
| strict（要求保留精确值） | 0.952 | 0.774 | **0.845** | 0.786 |
| default（只要求保留仍真事实） | 0.952 | 0.857 | **0.857** | 0.833 |
| tight（硬压到 20%） | 0.952 | 0.821 | **0.810** | 0.821 |
| 三档均值 | 0.952 | — | **0.837** | — |

**四条结论**：

1. **锚点回读有效但增益小**：G 类 0.958 → 1.000（+4.2pp，等于 24 个针里救回 1 个），三档提示词完全一致。原因是检查点在 0.3 压缩比下已保住 95.8% 的精确数值，锚点是保险丝不是主力。
2. **最大损失在不可落图事实**：N 类 0.933 → 0.772（**−16.1pp**，三档分别 −15.0 / −13.3 / −20.0pp）。用户硬约束、错误解法、已作废结论、因果、待办没有 L1 兜底，压缩后只剩检查点这一份有损投影。
3. **摘要提示词不是关键变量**：三档整体保留率 0.845 / 0.857 / 0.810，差异在 n=84 的噪声内（±7pp）；把压缩比从 0.33 压到 0.29 的 tight 组反而最低。重点应放在“给不可落图事实安排容器”，而不是调 prompt。
4. **分流失败的实际代价**就是那 +4.2pp（G 类 0.958 vs 1.000），其余无显著差异；但该结论依赖“检查点已保住大多数事实”这个前提，真实长会话下会被放大（未测）。

**由此确定的三条实现要求**（已写进 3.6.3 / 3.6.4 / 3.6.6 / 3.6.7）：

- 检查点的 Critical Context 段必须用结构化条目承载不可落图事实：`- [CONSTRAINT] …`、`- [RETRACTED] …`、`- [ERROR_FIX] …`、`- [TODO] …`，并标 `authority=checkpoint`；这类条目不参与 L1 裁决，也不作为对外证据。
- 提交检查点前必须跑**关键事实抽查**（3.6.4），命中率 <0.9 不提交。抽查针优先从 `[RETRACTED]` 与 `[CONSTRAINT]` 取，因为这两类一旦丢就不可恢复，且后果最重（会让人重新启用已作废的结论）。
- 分流抽取的 G 类覆盖率当 **SLA 监控项**（实测 0.917），不当保证；低于阈值时锚点段写 (none) 并告警。

**本次评估暴露的内部矛盾与已处理方式**：

| 矛盾 | 原表述的问题 | 处理 |
|----|----|----|
| 3.6.3 说分流失败“不影响正确性” | 与 3.6.7“锚点缺失→回读无法定位”自相矛盾 | 改为“不影响吞吐但降低可回溯性”，并给出可量化代价 |
| 3.6.4 收缩证明只比 token | 可以“越压越错但更短”，无信息量校验 | 增补关键事实抽查 |
| 3.6.6 “L1 永远赢” | 对不可落图事实不存在 L1，实际是模型自述当唯一事实源 | 增补 `authority=checkpoint` 标注与证据禁令 |
| 5.6.3 证据忠实性 vs 检查点叙述 | 检查点是模型自述，报告 §20 已证模型会用参数记忆冒充事实 | 同上：检查点叙述不得作为证据外传 |

**不背书**：对话为构造数据（每段约 4.5 k 字符），真实会话长一个量级，N 类损失可能被低估；只用 glm-5.3 一个模型做压缩；锚点回读是直接注入落图事实，没有真走 PathQuery（省掉查询预算、超点代价与解析失败路径）；未测多次增量合并的累积损失；探针只测“能否说出事实”，不等于“能否据此正确决策”。

#### 3.6.9 任务契约库：不可落图事实的容器（v1.43）

3.6.8 测出九段检查点对**不可落图事实**（用户硬约束、错误解法、已作废结论、因果、待办）会掉 16.1pp，而 3.6.5 的锚点只能回读图里的事实，这类事实在压缩后没有任何兜底。本节给出容器方案并附实测。

**条目结构**：

| 字段 | 取值 | 说明 |
|----|----|----|
| `kind` | `RETRACTED` / `CONSTRAINT` / `ERROR_FIX` / `DECISION` / `TODO` | 决定注入优先级与失效方式 |
| `text` | **原文逐字片段** | 禁止改写、禁止总结；写入时做"能否在原文中命中"的校验 |
| `scope` | 租户 / 项目 / 会话 | 跨会话约束（如"不要动 kigo-*"）必须在项目级 |
| `status` | `active` / `superseded` / `expired` | superseded 不注入但保留，供审计 |
| `authority` | `owner`（用户原话）/ `operator`（系统推断） | 与 3.6.6 的裁决链对齐 |
| `provenance` | 会话 ID + 检查点版本号 | 支持回滚与重复条目合并 |

**四条硬规则**：

1. **逐字引用，禁止改写**。抽取提示词明确"不许改写、不许总结"，写入前校验条目文本能在原文中命中；实测 55 条条目改写 **0** 条。摘要正是丢信息的那一步，容器不能重犯。
2. **按 kind 优先级注入，`RETRACTED` 永远第一**。忘了"某结论已作废"会让人重新启用它，危害大于忘掉一个待办。默认注入上限 8 条，超出部分只存库。
3. **独立于检查点注入**。作为紧凑块加在上下文尾部，不塞回摘要；摘要每轮重写会二次丢失，容器只在新增时追加。
4. **抽查针必须取自不可落图事实**。抽查若从契约条目里取，检查点本来就会保住它们，门禁永远绿灯（首版实测 12/12 通过，等于没测）。应从 N 类事实（最可能被丢的那一类）里取。

**实测（报告 v3.25）**：

| 臂 | 全部 | 可落图 G | 不可落图 N |
|----|----|----|----|
| 全量上下文 | 0.952 | 1.000 | 0.933 |
| 仅检查点 | 0.798 | 0.958 | 0.733 |
| 检查点 + 契约库 | **0.893** | 0.958 | **0.867** |
| 仅契约库 | 0.559 | **0.000** | 0.783 |

**结论**：契约库把不可落图事实的损失从 −20.0pp 收回到 −6.6pp（+13.3pp），上下文只增加 29%。契约库单独用（243 字符）在 N 类上比检查点（830 字符）高 5pp，但对可落图事实是 0.000——**两者职责不同，必须并用**。

**抽查门禁是滑杆不是开关**：阈值 2/3 通过 → 11/12 对话可压缩、N 保留 0.867；阈值 3/3 → 5/12 可压缩、N 保留 0.917。建议默认 3/3，仅在历史已超阈值时启用，并把 2/3 作为降级档（须在检查点里标注"本次压缩未过严抽查"）。

**与 3.6 其他条目的分工**：检查点回到本职（叙事与工作集）；契约库负责不可落图条目；锚点负责可落图事实的回读。三者都在 3.6.7 的失败模式表里各自独立退化，互不为前提。

**不背书**：对话为构造数据；只用 glm-5.3 一个模型（弱模型能否守住"逐字不改写"未测）；契约库的去重与 supersede 只做了 kind 内排序，真正的版本链与冲突消解未实现；cap=8 是拍的值，多轮增量下的驱逐策略未测；探针只测"能否说出事实"，不测是否据此正确决策。

## 4. 检索层设计（Retrieval Layer）

### 4.1 LLM 引导的多图联合最短路径查询

#### 4.1.1 问题形式化与总体架构

给定：

- 起点实体集合 $S = \{s_{1}, s_{2}, ...\}$（从当前 Belief State 中提取）
- 目标实体集合 $T = \{t_{1}, t_{2}, ...\}$（从任务描述中解析）
- 本体图 $G_{o} = (V_{o}, E_{o})$ 和实例图 $G_{i} = (V_{i}, E_{i})$

求解：

$$
\min_{p} \sum_{(u,v)\in p} w(u,v) \quad \text{s.t.} \quad p \in \mathcal{P}_{\text{valid}}(G_{o}, G_{i}, S, T)
$$

其中 $w(u,v)$ 为边权重（见 4.3.3），$\mathcal{P}_{\text{valid}}$ 为同时满足本体约束与语义约束的路径空间。与纯图算法不同，这个路径空间本身由 LLM 与本体共同划定：本体给出硬约束（白名单、闭包、签名），LLM 常识给出软约束（语义相关、意图一致）。

**LLM 参与路径计算的四层角色**（与 3.4 的分工原则一致）：

**表 4-0 LLM 常识在最短路径计算中的参与层级**

| 层级 | 参与点 | LLM 输出 | 机器裁决 | 计算性质 |
|----|----|----|----|----|
| L1 搜索空间划定 | 概念层航点与关系候选 | 候选概念路径 + 关系白名单 | 本体图可达性校验，不通过则丢弃 | 查询前，一次 |
| L2 边权与启发式 | 语义距离、边类型代价 | 分数（连续值） | 分数只改权重不改拓扑，失败可回退到纯结构权重 | 查询中，每节点一次 |
| L3 路径候选集扩展 | k-best 之外的语义候选路径 | 补充候选路径（带理由） | 逐边校验后进入候选集，标注 provenance | 查询后，一次 |
| L4 路径重排与解释 | 结果解释、意图对齐 | 重排序后的 Top-k | 重排不改变代价，只调整展示顺序与解释；**按需触发**（判据见 4.1.2 表 4-0d） | 查询后，一次 |

L1 限定搜索空间，L2 影响代价，L3 扩展候选，L4 呈现结果（注意：4.4.2 补全阶梯的 L4 指“路径拼接”，与本层同名不同义）。L1/L2 是计算内参与（影响算法本身），L3/L4 是计算外参与（结果增强）。层级越深，LLM 判断的错误后果越重，因此裁决强度递增。

#### 4.1.2 核心算法：双阶段约束最短路径（LLM 划界 + 图引擎求解）

算法以两阶段为核心（LLM 划定搜索空间、图引擎求最优路径），第三段只做结果增强（候选扩展与重排），前两段严格分离“谁划定搜索空间”与“谁求最优路径”：

```python
def llm_constrained_shortest_path(task, G_o, G_i, belief):
    """LLM 划界 + Dijkstra 求解的双阶段联合最短路径。

    LLM 决定“在哪搜、给边打多少分”；
    图引擎决定“哪条最短”。两者不交叉。
    """
    # ---- 阶段一：LLM 划定搜索空间（L1）----
    spec = llm_plan_concept_paths(task, G_o, belief)
    #   -> {concept_paths: [...], relation_allow: [...],
    #      waypoints: [...], rationale: "..."}

    # 本体裁决（一）：概念路径可达性 + 关系白名单闭包校验
    validated = validate_against_ontology(spec, G_o)
    if not validated.ok:
        return retry_or_fallback(validated.errors, task)  # -> 4.4 补全

    # 本体裁决（二）：方向/顺序裁决（v1.10 方向、v1.11 顺序）——关系名由 LLM 给，
    # out/in 与排列由引擎按起点可遍历性判定
    validated, dir_stats = adjudicate_sequence(validated, G_i, S)
    #   1) 原链可遍历 -> kept；2) 按翻转位数递增找方向变体 -> flipped；
    #   3) 方向全失败再按逆序数枚举排列（n<=3 => 48 变体）-> permuted；
    #   4) 仍不可遍历 -> dropped；四态写入 provenance，permuted/flipped 在打分时降权
    if not validated.ok:
        return retry_or_fallback(validated.errors, task)  # 全部链不可执行 -> 4.4 补全

    # ---- 阶段二：图引擎在受限子图上求最短路（L2 提供权重）----
    subG = project_subgraph(G_i, validated)  # 白名单关系的导出子图
    weights = precompute_edge_weights(subG, validated.waypoints, task)
    #   LLM 语义分数在此注入，失败则回退纯结构权重

    paths = k_shortest_paths(subG, weights, S, T, k=K, depth=k_max)

    # ---- 阶段三：候选扩展与重排（L3 + L4）----
    if high_recall_enabled(belief, validated):   # v1.11，默认关闭：需语义重排可用且判定命中
        # 在 LLM 提案的关系并集上做深度=k_max 的受限 BFS（表 4-0e）
        paths += restricted_bfs(G_i, S, validated.relation_allow, depth=k_max)
    extra = llm_suggest_alternatives(task, paths, belief)
    for cand in extra.paths:
        if verify_edges_against_ontology(cand, G_o):  # 逐边校验
            cand.provenance = "llm_proposed"
            paths.append(cand)

    # L4 重排按需触发（v1.10，判据见表 4-0d）：候选已有区分度时不做重排
    if needs_llm_rerank(paths, task, weights):
        reranked = llm_rerank_by_intent(paths, task)  # 不改 cost，只改顺序
    else:
        reranked = sorted(paths, key=lambda p: path_cost(p, weights))
    return Observation(paths=reranked[:K], weights=weights,
                       spec=validated, provenance=track_all(paths, dir_stats))
```

阶段划分的意义：**LLM 从不直接操作图数据结构**。它的输出经过校验后变成“受限子图的定义”与“边权函数的参数”，而最短路径求解始终由确定性图算法（Dijkstra/Yen/kNN）完成，保证结果可复现、可审计。

**表 4-0b 双阶段算法的职责与失败回退**

| 阶段 | 执行者 | 输入 | 输出 | 失败时的回退 |
|----|----|----|----|----|
| 概念规划 | LLM | 任务 + 本体库快照投影 | 候选概念路径 + 关系白名单 | 回退到无航点全图 BFS（限深） |
| 本体校验 | 确定性代码 | LLM 输出 | 校验通过的 spec 或结构化错误 | 错误回 LLM 一次修复，仍失败转 4.4 |
| 方向裁决（v1.10） | 确定性代码 | LLM 链 + 实例子图 | 保留/翻转/丢弃三态后的链集 | 全链不可遍历则该题转 4.4 |
| 子图投影 | 确定性代码 | 校验后 spec | 受限实例子图 | 不可投影则报告空搜索空间 |
| 边权合成 | 确定性代码 + LLM 分数 | 子图 + 任务语义 | 边权函数 | LLM 分数不可用时用纯结构权重 |
| k-best 求解 | 图引擎 | 子图 + 边权 | Top-K 路径 | 超时熔断，返回已完成部分 |
| 候选扩展 | LLM | 路径 + 任务 | 语义候选路径 | 无候选则跳过此阶段 |
| 重排与解释 | LLM | 全部候选 | 排序后结果 + 理由 | 失败则按 cost 排序 |

**方向裁决（v1.10 新增）**：LLM 给出的概念路径常出现“视角错位”——按答案侧起笔，导致首跳在起点实体上零结果。真实数据上这不是个别噪声：MetaQA 3-hop 有 66% 的题目整条候选集都不可执行，召回直接为 0。因此把方向判定从 LLM 手里收回引擎，关系名与顺序仍由 LLM 给：

**表 4-0c 方向裁决的三态**

| 三态 | 触发条件 | 处理 | 审计字段 | 风险 |
|----|----|----|----|----|
| 保留 kept | 原链从起点可遍历 | 直接执行 | `dir_status="kept"` | 低 |
| 翻转 flipped | 原链不可遍历，但存在方向变体可遍历 | 按翻转位数递增取首个可遍历变体 | `dir_status="flipped"`, `dir_flips=[位图]` | 中：翻转会改变语义，须在重排与解释中显式标注 |
| 丢弃 dropped | 所有方向变体均不可遍历 | 不进入候选集，题目转入 4.4 补全 | `dir_status="dropped"`, `reason="unreachable"` | 低：不引入错误答案 |
| 换序 permuted（v1.11） | 方向变体均不可遍历，但存在排列变体可遍历 | 按“末关系与问句匹配度最高、逆序数最少”取首个可执行变体 | `dir_status="permuted"`, `perm=[位序]` | 中高：换序改变语义，须降权并在解释中标注 |

**裁决规则**：

1. **只判方向，不改关系名与顺序**：可遍历即照原样执行，避免过度纠正把正确链翻错。
2. **确定性优先**：变体按翻转位数从少到多、同位数按位置序枚举（链长 n 时上限 $2^{n}-1$，实践中 n≤3），取首个可遍历者，保证同一输入同一输出。
3. **翻转必须可审计**：翻转改变了语义（“A 导演的电影”与“导演了 A 的人”不同），凡 `flipped` 的链在 provenance 标注，4.1.4 的语义打分与 L4 解释不得把它当作 LLM 原意。
4. **全丢弃不得放行**：题目进入 4.4 补全阶梯，错误码沿用 4.4.1 的 E03（图不连通）与 E05（查询侧）口径；禁止以“LLM 认为有路”越过裁决。
5. **证据基线**：SUP-02 v1.3 的 399 题实测为 kept 805 / flipped 286 / dropped 560（共 1,651 条链），裁决使 hit1 0.667→0.827、提案召回 0.707→0.910；其中 3-hop 由 0.316 提到 0.632。
6. **顺序裁决只在方向失败后启用**：可遍历的原链一律不改顺序，避免把正确顺序改错；换序变体上限 $n!\times 2^{n}$（n≤3 → 48），排序键固定为（末关系关键词匹配降序，逆序数升序），保证确定性。
7. **换序与翻转都要降权**：两者都改变了 LLM 原意，L4 打分对 `permuted`/`flipped` 链按同一量级降权；解释阶段必须说明“该路径由引擎校正过方向/顺序”。

**L4 重排的触发判据（v1.10 新增）**：重排只在“候选集自身没有区分度”时才有价值。真实数据显示：候选排名已稳定时重排会引入噪声（同一候选集上 hit1 0.850→0.792，修正 7 例同时破坏 7 例）；候选几乎没有信号时重排显著有效（0.125→0.300）。因此把 L4 从“常开阶段”改为“按需触发”，判据如下：

**表 4-0d L4 重排的触发判据**

| 判据 | 观测对象 | 触发重排 | 不触发 |
|----|----|----|----|
| **候选来源标记**（v1.17 引入，v1.19 验证通过） | 候选集是否包含 `restricted_bfs` 扩展出的候选 | 含扩展候选（噪声高、答案被摊薄） | 仅来自 LLM 提案链 |
| 候选跨序列数 $m$ | 候选集中互异关系序列的条数 | $m \ge 2$（存在多义） | $m = 1$ |
| 答案表面类型一致性 | 问句期望类型与 top-1 答案类型的匹配 | 不一致或无法判定 | 一致 |

> **原"首位-次位分差 $\Delta \le \Delta_{th}$"判据已作废（v1.17）**：实测同一分差区间在两类候选上收益符号相反（E −3.88pp / F +4.94pp），合并搜索的最优净增益 +0.63pp、95% CI 跨 0。它测的是"排序是否稳定"，而重排收益取决于"候选是否被摊薄"，两者不是一回事。
>
> 表 4-0d 的"候选来源"判据在 3 个模型上复验（v1.20）：E 组恒负（−3.30 / −4.50 / −4.50pp）、F 组恒正（+3.38 / +5.63 / +3.38pp），来源判据全正（+1.74 / +2.91 / +1.74pp）且都优于"总是重排"。**判据与模型无关，与候选是否被扩展摊薄有关。**
>
> **"候选/链比 ρ" 判据已删除（v1.19）**：A/B 半样本验证中，A 上网格选出的 ρ ≥ 2.5 在 A 就已是 −0.29pp、在 B 上 −1.65pp；来源判据则 A +2.34pp / B +2.97pp。**判据要在留出集上验，现场提出的判据默认当假设。**

三项均不触发时按合成代价排序并直接返回。$\Delta_{\text{th}}$ 需按领域在验证集上标定（v1.10 只固化判据，不定死数值）；触发与未触发都要写入 `provenance`，以便事后比较两类查询的精度与成本。

**实测依据（v1.14 / v1.17 修订）**：MetaQA 399 题、top-8 候选上，同一批候选只换排序器的对照——干净候选（LLM 提案链，stub hit1 0.853）加 LLM 重排后 **−1.29pp / −2.07pp**（两次乱序种子）；噪声候选（叠加集合内受限 BFS，stub 0.742）加 LLM 重排后 **+5.05pp / +4.29pp**。方向稳、幅度随乱序摆动约 ±1pp，因此单点数字必须配区间读。另需注意：重排前必须打乱候选顺序（否则模型 5/5 全选下标 0），且乱序种子要用 sha256 这类稳定哈希，否则缓存跨进程失效、结果不可复现。

**高召回模式（v1.11 新增）**：当候选召回不足时，可以让引擎放弃 LLM 给的顺序，改为在 **LLM 提案的关系并集**上做深度 = hop 的受限 BFS——每一层只允许这组关系（双向）扩展，逐层剪枝，从而枚举所有可执行序列。它把“关系名”留给 LLM、“组合与顺序”交给引擎，召回显著提升，但候选集迅速变大，对重排器要求更高：

**表 4-0e 高召回模式的开关条件与实测代价**

| 模式 | 启用条件 | 提案召回 | hit1（离线重排） | 结论 |
|----|----|----|----|----|
| 默认（关闭） | — | 0.902 | **0.827** | 现行可交付链路 |
| 高召回（开启） | 关系集来自 LLM 提案 + 语义重排器健康 + 表 4-0d 判据命中 | **0.937** | 0.709（离线）/ 待验证（语义） | 仅在语义重排可用时启用 |

三条启用条件缺一不可：① 关系集必须来自 LLM 提案（全库穷举会让候选爆炸且偏离意图）；② 语义重排器可用且健康检查通过（离线 stub 只能把 0.709 拉回 0.737，仍低于默认模式）；③ L4 触发判据命中（候选确实缺乏区分度）。不满足时按默认链路执行，宁少召回也不牺牲精度。

#### 4.1.3 查询流程（五步）

```text
Step 1: LLM 概念路径规划（L1）
  输入：任务描述 + 本体快照投影（不是原始本体图）
  输出：候选概念路径（多条）+ 关系白名单 + 航点 + 理由
  约束：只能引用快照中存在的概念与关系（4.3.4 契约）

Step 2: 本体层裁决（确定性）
  2a 概念可达性与关系签名合法性（4.1.2 裁决一）
  2b 方向/顺序裁决：逐链判定起点可遍历性，保留/翻转/换序/丢弃四态入 provenance（4.1.2 裁决二）
  不通过的候选丢弃；全部失败则进入 4.4 补全流程

Step 3: 受限子图上最短路（确定性 + LLM 权重）
  以白名单投影出实例子图，边权由结构项 + LLM 语义项合成
  执行 k-best 加权最短路（Dijkstra/Yen），深度 ≤ k_max

Step 4: 项目级图增强（上下文层）
  在项目级图谱中查询与路径实体相关的动态状态
  输出：补充观测（如任务进度、资源占用、风险标记）

Step 5: 结果融合与重排（L3 + L4）
  语义候选并入候选集；L4 重排按需触发（判据见表 4-0d），未触发时按合成代价排序
  合并项目上下文为结构化观测 O_t
  每条路径携带代价分解与 provenance，支持事后审计
```

#### 4.1.4 边权合成：LLM 常识如何影响代价

LLM 常识不直接“选出路径”，而是合成到边权函数的语义项中。边权由结构、语义、Hub 和置信度四部分组成（与 4.3.3 共用定义）：

$$
w(u,v,r) = w_s + w_t \cdot c_{\text{type}}(r) + w_{\text{sem}} \cdot (1 - \cos(e_u,e_v)) + w_{\text{hub}} \cdot \log(1+\deg(v)) + w_{\text{conf}} \cdot (1 - p(r))
$$

其中语义项 $(1 - \cos(e_u,e_v))$ 的嵌入向量来源分两层：

- **基础层（离线）**：全库节点预计算嵌入（天级更新），供粗排与 A* 启发式使用；
- **任务层（在线）**：以任务文本为 query，对候选邻居做 LLM 语义相关性打分（4B 小模型，每次查询一次），打分改写语义项系数，不改拓扑。

LLM 打分与嵌入距离的关系不是简单加权，而是**分段修正**：

$$
c_{\text{sem}}(e_u, e_v, \text{task}) = \begin{cases} 1 - \cos(e_u, e_v) & \text{若 } s_{\text{LLM}} \in [\tau_{\text{lo}}, \tau_{\text{hi}}] \\ 1 - \cos(e_u, e_v) + \delta_{\text{bonus}} \cdot (s_{\text{LLM}} - \tau_{\text{hi}}) & \text{若 } s_{\text{LLM}} > \tau_{\text{hi}} \\ 1 - \cos(e_u, e_v) + \delta_{\text{pen}} \cdot (\tau_{\text{lo}} - s_{\text{LLM}}) & \text{若 } s_{\text{LLM}} < \tau_{\text{lo}} \end{cases}
$$

含义：LLM 分数处于中性区间时，嵌入距离主导边权；LLM 明确认为“该边与任务意图高度相关”时给奖励（降边权），明确认为无关时给惩罚（升边权）。默认 $\tau_{\text{lo}}=0.3$、$\tau_{\text{hi}}=0.7$、$\delta_{\text{bonus}}=0.5$、$\delta_{\text{pen}}=1.0$，系数在标注路径上校准。打分失败或超时则整项退回纯嵌入距离，路径计算不中断。

#### 4.1.5 启发式函数设计

受限 A* 使用的启发式函数沿用语义距离，并加入目标类型约束：

$$
h(n) = \lambda \cdot \text{cosine\_dist}(\text{emb}(n), \text{emb}(t)) + (1-\lambda) \cdot \text{LLM\_score}(n \to t) + \lambda_{\text{type}} \cdot \mathbf{1}[\text{type}(n) \notin T_{\text{types}}]
$$

其中 $emb(n)$ 为基础层嵌入，LLM_score 为小模型（4B）对“从节点 n 到达目标 t 的可能性”的打分，$\lambda$ 默认 0.7。与边权一样，启发式中的 LLM 分数只影响搜索顺序，不影响可达性判定；A* 的可采纳性无法严格保证，因此工程上保留 4.3.3 的有界次优策略（记录当前最优上界，超过 $(1+\varepsilon)$ 倍的路径剪枝，默认 $\varepsilon=0.2$）。

LLM 分数参与启发式时逐节点调用会拖慢搜索，工程上采用三级加速：

- **缓存**：同任务同节点的 LLM 打分缓存（TTL 随图谱更新频率），命中直接复用；
- **批量**：一次扩展的邻居集合批量打分，减少调用次数；
- **降频**：只在搜索进入“语义密集区”（嵌入距离梯度突变）时调用 LLM，其余用嵌入距离替代。

**搜索策略的选择依据（v1.13）**

在 DBP15K zh_en 的 34 万边真实图（15.9 万节点）上，对 300 个真实多跳查询（最短距离 2–4 跳，平均 3.82）做对照：

| 搜索 | 平均扩展节点数 | 相对 BFS |
|----|----|----|
| 双向 BFS | **20.3** | 0.014 |
| 无信息 BFS | 1,506 | 1.000 |
| A* + ALT（k=8） | 1,217 | 0.808 |
| A* + ALT（k=4） | 2,077 | 1.379 |
| A*（h=0） | 10,360 | 6.878 |

结论：

- **单条最短路用双向 BFS**，不要先上启发式：双向比 ALT 快约 60 倍（1,217 / 20.3），而本例的启发式只省 19%（h 的紧致度 0.47，地标距离差平均只能解释真实距离的一半不到）。
- **规模会反转结论（v1.18）**：同一套代码把图扩到 90 万边后，ALT 从"省 19%"变成"慢 4.2 倍"（3,366 vs BFS 800），双向 BFS 则基本不变（18.5）。所以"加启发式"不是通用优化，**上大图前必须与双向 BFS 对拍**。
- **对拍要跨规模**：本轮 off-by-one 就是 90 万边档的对拍暴露的（首轮 127/150 条路径长度不一致），单规模、只看平均扩展数发现不了。
- **k-best 枚举用单向搜索 + 度剪枝**：双向搜索不能直接产出 k-best，这正是本架构的主路径（4.1.1），启发式在这里才作为加速手段有意义。
- **注意终止判据**：A*(h=0) 比 BFS 慢 6.9 倍不是启发式的错，而是 A* 必须等目标出队、BFS 在生成目标时即返回。把“用 A* 替代 BFS”当优化而不动判据，实测会变慢。
- 本节的嵌入启发式不保证可采纳，必须配合 4.3.3 的有界次优（ε=0.2）；若改用可采纳启发式（如 ALT），路径长度可与真实最短路完全一致（本实验 300/300 一致、h 违反 0）。

### 4.2 动作剪枝与约束

为避免组合爆炸，在实例图上游走时施加以下剪枝策略：

1.  **本体约束剪枝**：下一步的关系类型必须在本体图谱中定义为当前节点类型的合法出边。**（v1.15：无类型层的数据集上无法执行，只能机制论证）**
2.  **语义相似度降权（v1.15 由"剪枝"改为"降权"）**：候选邻居与目标实体的嵌入余弦相似度**参与打分与排序**；只有当候选动作数超过上限时才启用带兜底的软门，且触发后必须先跑一次未剪枝分支。实测：按阈值硬剪时保留率 0.496、**48.0% 的题一个合法动作都不剩**（等价于把 0.3 相似度当硬门）。
3.  **深度限制**：单次查询最大跳数 $k_{\text{max}}$（默认 5），超过则触发 LLM 重新规划中间航点。**（v1.15：这是安全阀不是剪枝器——实测数据最长 3 跳，从未触发）**
4.  **超级节点降权**：对度数超过阈值的 Hub 节点，在路径评分中施加惩罚项，避免路径经过无信息量的中心节点。**（v1.15：若改为直接跳过，θ 不应低于 500——θ=500 保留 0.913 的合法动作、剪枝 0.092；θ=50 只保留 0.775 且 22.2% 的题全灭）**

**表 4-2a 剪枝规则的实测代价（v1.15）**

| 规则 | 合法动作保留率 | 剪枝率 | 全灭率 | 结论 |
|----|----|----|----|----|
| 语义阈值（词法 ≥1 代理相似度 0.3） | 0.496 | 0.772 | **0.480** | 不能做硬门 |
| 语义阈值（词法 ≥2） | 0.170 | 0.929 | **0.785** | 更差 |
| 超级节点 θ=50 | 0.775 | 0.214 | 0.222 | 过激 |
| 超级节点 θ=500 | 0.913 | 0.092 | 0.082 | 建议下限 |
| 超级节点 θ=1000 | 0.939 | 0.056 | 0.054 | 保守可用 |
| 深度限制 k_max=5 | 1.000 | 0.000 | 0.000 | 安全阀 |

### 4.3 自然语言任务到最短路径查询的编译（NL → PathQuery）

直接把自然语言交给大模型生成 Cypher 看似快捷，但会引入标签/关系幻觉、提示注入和不可复现三类问题。本节采用“两段式编译”：LLM 只负责语义解析、实体候选与航点建议，确定性编译器负责把结构化的 PathQuery IR 编译为图数据库物理查询。这样既保留 LLM 的语义能力，又能把查询约束收束到本体白名单内。

#### 4.3.1 查询中间表示与符号定义

一条自然语言任务被编译为如下结构化元组，其中每个分量都能被机器校验，而不是一段自由文本：

$$
Q = (\text{scope}, S, T, W, R^{+}, R^{-}, C, \text{obj}, k, \Delta, \tau_{\text{sem}}, \pi)
$$

**表 4-1 路径查询中间表示的符号定义**

| 符号 | 含义                                                         |
|----------|------------------------------------------------------------------|
| scope    | 查询图层：本体图 O、全局实例图 G、项目级实例图 P，可组合为 ALL。 |
| S / T    | 起点/目标节点模式集合，包含概念、属性过滤、候选实体与绑定名。    |
| W        | 中间航点模式集合，由 LLM 建议并经本体校验。                      |
| R⁺ / R⁻  | 允许/禁止的关系类型白名单，来源于本体关系签名。                  |
| C        | 硬/软约束集合，如属性阈值、时间窗口、合规状态。                  |
| obj      | 优化目标：最少跳数、最小代价、最大覆盖、最高置信度或综合评分。   |
| k / Δ    | 返回路径数与单次搜索最大深度。                                   |
| τ_sem    | 语义相似度阈值，用于邻居剪枝。                                   |
| π        | 溯源策略：是否允许假设边、是否要求证据、是否允许写回。           |

对应的 PathQuery IR 采用 JSON 表示，字段与上述元组一一对应：

```json
{
  "schema_version": "1.0",
  "query_id": "Q-IMPACT-01",
  "task_id": "TASK-2026-1116-01",
  "scope": ["project", "global"],
  "starts": [
    {"bind": "p", "concept": "Project", "match": {"id": "PRJ-A"}},
    {"bind": "r", "concept": "Resource", "match": {"name": "芯片"}}
  ],
  "targets": [
    {"bind": "t", "concept": "Task", "match": {"status": {"$ne": "done"}}}
  ],
  "waypoints": [
    {"bind": "cap", "concept": "Capability", "optional": true}
  ],
  "relations": {
    "allow": ["depends_on", "requires", "supplies"],
    "deny": ["same_as"]
  },
  "constraints": [
    {"expr": "supplier.certified == true", "hard": true},
    {"expr": "supplier.lead_time_days <= 30", "hard": true}
  ],

    "type": "max_coverage",
    "weights": {"hops": 0.3, "semantic": 0.4, "risk": 0.3}
  },
  "budget": {"max_depth": 5, "max_paths": 20, "timeout_ms": 1200},
  "semantics": {"min_edge_confidence": 0.6, "allow_hypothesized": false},
  "provenance": {"require_evidence": true}
}
```

IR 的字段不是自由文本，而是由本体库快照生成的枚举和 JSON Schema 约束。编译器必须同时满足五条正确性条件：

- **类型安全**：每个节点模式的概念存在，R⁺ 中每条关系满足 domain/range 兼容。
- **接地完整**：S/T 至少解析出一个候选实体或一个明确的未接地错误码。
- **约束保真**：任务中的每条硬约束都出现在 C 中，或被显式记录为丢弃及原因。
- **可执行**：物理查询通过 EXPLAIN、只读检查和成本上限。
- **可复现**：相同输入与相同图谱快照产生相同 IR，LLM 温度固定为 0。

**实现口径（v1.x）**：模型填 IR 走 `action=compile query_json=<object>`，由 `compile_path_query_json` 做受约束收口。它接受 `from/to`、`via`、`max_depth`、`max_results`、`min_conf`、`budget_ms`、`semantic_min` 等别名，统一映射到 `PathQuery`；未登记字段被丢弃并在 `dropped_fields`/`warnings` 中返回，不静默吞掉。关系名必须命中 EdgeKind 或调用方传入的本体关系白名单，否则整体拒绝；数值、布尔、枚举类型错误同样整体拒绝。通过后仍执行 `PathQuery::validate`，所以深度、数量、置信度范围与未接地锚点不会被模型绕过。

#### 4.3.2 八阶段编译流水线

```text
自然语言任务
  → S0 规范化 → S1 TaskFrame 抽取
  → S2 本体接地 → S3 意图到路径模式
  → S4 航点生成与本体校验 → S5 物理查询编译
  → S6 执行与观测归一化 → S7 一致性校验
                         └─失败→ 定向修复（≤2 次）
```

**S0 规范化**：拆分复合任务，消解指代与省略，统一时间、单位、项目编号和语言；保留原文 span 以便追溯。输出是规范化任务文本加对话上下文引用，不做任何图谱假设。

**S1 TaskFrame 抽取**：用带 JSON Schema 的 LLM 调用抽取意图、起止锚点、硬/软约束、成功判据、禁止项、图层范围与输出类型。TaskFrame 只描述“要什么”，不描述“怎么查”。

```json
{
  "task_id": "TASK-2026-1116-01",
  "intent": "impact_analysis_with_mitigation",
  "anchors": [
    {"role": "start", "mention": "A 项目", "span": [0, 4]},
    {"role": "start", "mention": "芯片供应", "span": [7, 11]},
    {"role": "target", "mention": "交付任务", "span": [18, 22]},
    {"role": "target", "mention": "替代供应商", "span": [28, 33]}
  ],
  "constraints": [
    {"expr": "supplier.certified == true", "hard": true},
    {"expr": "supplier.lead_time_days <= 30", "hard": true}
  ],
  "success_criteria": ["列出受影响任务", "给出替代供应商及证据路径"],
  "scope_hint": ["global", "project"],
  "output_type": "decision_support"
}
```

**S2 本体接地**：先做 mention detection，再检索候选概念与实体，最后做类型兼容检查。实体链接得分由五部分组成：

$$
\text{score}(e \mid m) = \alpha \cdot \text{sim\_emb} + \beta \cdot \text{sim\_lex} + \gamma \cdot \text{type\_match} + \delta \cdot \text{context} + \varepsilon \cdot \text{recency}
$$

默认权重 0.35/0.25/0.20/0.15/0.05，α+β+γ+δ+ε=1。接受阈值 0.75；0.50–0.75 保留 Top-k 候选并标记歧义；低于 0.50 进入未接地分支（4.4 的 E01）。类型检查使用本体 domain/range 与子类闭包，避免把“供应商”接到“客户”。

- 候选概念检索：别名表、标签嵌入、模糊匹配，三路召回后去重。
- 实体链接：别名索引 + 向量 ANN + 属性过滤 + 图上下文重排。
- 歧义处理：保留 Top-k 候选，不强行唯一化；由后续路径查询的兼容性做二次裁决。
- 跨语言与缩写：维护领域同义词表，缩写必须能展开到本体中的完整概念。

**S3 意图到路径模式**：不同问句对应不同的路径方向、端点和目标函数，不能统一按“起点到终点最短路”处理。表 4-2 给出映射。

**表 4-2 任务意图到路径查询模式的映射**

| 任务意图 | 路径方向与端点 | 目标函数 | 输出形态 |
|----|----|----|----|
| 归因 / 为什么 | 反向因果链：现象 ← 候选原因 | k-best + 对比 | 因果路径集合 |
| 影响 / 下游 | 正向可达：变更点 → 受影响实体 | 最大覆盖 | 影响子图 |
| 方案 / 如何 | 前向行动链：当前状态 → 目标状态 | 最小代价 | 可执行路径 |
| 合规 / 是否 | 存在性 + 约束路径：对象 → 规则 | 布尔判定 | 违反/满足证据 |
| 替代 / 最优 | k-best：约束资源 → 候选实体 | 排序 + 置信度 | Top-k 候选及评分 |

该映射同时决定是否需要反向边、是否允许多路径、以及是否要做对比解释。例如归因任务必须保留多条候选原因，不能只返回一条最短路径。

**S4 航点生成**：不让 LLM 直接给出实体 ID。先在本体图上枚举候选概念路径，再由 LLM 重排并建议属性过滤。航点效用函数为：

$$
u(w) = \lambda_1 \cdot \text{sem}(w, \text{goal}) + \lambda_2 \cdot \text{onto\_plausibility}(w) + \lambda_3 \cdot \text{selectivity}(w) - \lambda_4 \cdot \text{hub\_penalty}(w)
$$

- 候选概念路径由本体 A* 生成，beam 宽度默认 3，每条路径最多 3 个航点。
- LLM 只做重排与属性过滤建议，输出必须在概念白名单内。
- 未知概念映射到最近本体概念；相似度低于 0.60 则丢弃并记录。
- 航点选择性：高度数概念降权，优先能缩小搜索空间的概念。

**S5 物理编译**：把 IR 编译为分阶段查询计划：本体探测 → 分段实例搜索 → 项目级增强 → 结果融合。所有值参数化，关系类型来自白名单，禁止字符串拼接。

```text
PathQuery
 ├─ OntologyProbe(concept_path)          本体图：概念可达性
 ├─ InstanceSearch(segment_1..n)         实例图：A*/Dijkstra/Yen
 ├─ ProjectEnrichment(entity_ids)        项目图：状态与风险
 └─ Fusion(paths, context, provenance)   融合与打分
```

**S6 执行与观测归一化**：查询结果统一转换为 Observation，至少包含：节点与边、路径及代价分解、边级 provenance、诊断信息、质量标志。下游的 Reward 与 Belief State 只消费 Observation，不直接读数据库返回。

**S7 一致性校验与定向修复**：检查类型安全、约束保真、端点匹配、置信度阈值和假设边比例。校验失败返回结构化错误码，不直接重试整条查询；最多 2 次定向修复，仍失败则转 4.4 补全。修复记录写入审计日志，供质量评估归因。

#### 4.3.3 物理查询模板

以下模板以 Neo4j/Cypher 为例，其他图数据库可按相同语义改写为 Gremlin 或 SPARQL。模板只接受参数化输入，标签与关系类型来自服务端白名单。

**本体概念路径校验**：先确认航点序列在概念层可达，再下推到实例层。

```cypher
// C1: 概念路径校验（本体图）
MATCH p = (c0:Concept {name: $c0})-[:REL*1..4]->(cN:Concept {name: $cN})
WHERE all(r IN relationships(p) WHERE r.name IN $allowed_rel)
  AND all(n IN nodes(p) WHERE n.name IN $concept_allow)
RETURN [n IN nodes(p) | n.name] AS concept_path,
       reduce(s = 0.0, r IN relationships(p) |
              s + coalesce(r.weight, 1.0)) AS cost
ORDER BY cost ASC
LIMIT $k;
```

**实例加权最短路**：优先使用图数据库原生算法，避免在应用层全图遍历。

```cypher
// C2: 实例图加权最短路（Neo4j GDS）
MATCH (s:Entity {id: $sid}), (t:Entity {id: $tid})
CALL gds.shortestPath.dijkstra.stream('instance_graph', {
  sourceNode: s,
  targetNode: t,
  relationshipWeightProperty: 'w',
  relationshipTypes: $allowed_rel
})
YIELD totalCost, nodeIds, costs, path
RETURN totalCost,
       [n IN nodes(path) | n.id] AS node_ids,
       [r IN relationships(path) | type(r)] AS rel_types
LIMIT $k;
```

注意：部分 GDS 版本的 relationshipTypes 不接受参数化列表，应由服务端白名单生成字面量，绝不能拼接用户输入。需要 k 条次优路径时改用 Yen 算法；需要硬约束时在应用层做受限 A*。

**受限 A* 搜索**：当图数据库不支持带约束的加权最短路时，在查询服务内实现 A*：

```python
frontier = heap[(h(s), 0.0, s, [s])]
while frontier:
    f, g, u, path = heappop(frontier)
    if u in T and satisfies(path, C):
        return path
    if len(path) > Delta:
        continue
    for (u, v, r) in outgoing(u):
        if r.type not in R_plus or r.type in R_minus:
            continue
        if not type_compatible(u, r, v):
            continue
        if semantic_sim(v, T) < tau_sem:
            continue
        w = edge_weight(u, v, r)
        push(frontier, (g + w + h(v), g + w, v, path + [v]))
```

边权由结构、语义、Hub 和置信度四部分组成：

$$
w(u,v,r) = w_s + w_t \cdot c_{\text{type}}(r) + w_{\text{sem}} \cdot (1 - \cos(e_u,e_v)) + w_{\text{hub}} \cdot \log(1+\deg(v)) + w_{\text{conf}} \cdot (1 - p(r))
$$

默认 w_s=1.0、w_t=−0.2（优先本体声明的关系）、w_sem=0.8、w_hub=0.3、w_conf=1.5；所有系数需在标注路径上校准。p(r) 为边置信度，见 4.4.4。

启发式沿用 4.1.5 的语义距离，并加入目标类型约束：

$$
h(n) = \lambda \cdot \text{cosine\_dist}(\text{emb}(n), \text{emb}(t)) + (1-\lambda) \cdot \text{LLM\_score}(n \to t) + \lambda_{\text{type}} \cdot \mathbf{1}[\text{type}(n) \notin T_{\text{types}}]
$$

A* 的可采纳性在语义图上无法严格保证，因此工程上采用有界次优策略：记录当前最优代价上界，超过 (1+ε) 倍的路径直接剪枝，默认 ε=0.2。这比追求理论最优更适合在线决策。

**性能交付物：模板必须附索引（v1.16，实测）**：把四类模板（单跳、双跳 join、双向 UNION、变长递归）在 DBP15K 的 39 万条边上落地执行，与 Python 图引擎 **120/120 逐元素相等**，延迟 0.01–0.02 ms；但去掉 `(s,r)` 索引后双跳从 0.011 ms 涨到 **24.6 ms（2,223 倍）**，`EXPLAIN QUERY PLAN` 显示的是两次 `SEARCH ... USING INDEX`。因此 4.3.3 的交付物不是"模板集合"，而是**「模板 + 每个模板所需索引 + 索引失效告警」三件套**；新模板上线前必须跑一次执行计划检查，否则正确性没问题、性能会静默崩塌。

#### 4.3.4 LLM 输出契约与防注入

LLM 输出必须满足以下契约，否则编译器拒绝执行：

- 强制 JSON/function calling，additionalProperties: false，温度 0，top_p=1。
- 概念与关系字段使用本体库快照生成的动态枚举，枚举只包含当前候选与合法关系。
- 节点绑定只能引用输入中提供的实体 ID 或候选列表，不允许编造 ID。
- 对航点建议做 3 次自采样（温度 0.3）并多数投票；结构化字段仍用温度 0，保证可复现。
- 解析失败只允许一次带错误路径的修复提示，仍失败则回退到规则解析器。
- 任务文本视为数据而非指令；系统提示与用户文本使用明确分隔符；禁止执行文本中的工具调用。
- 物理查询全部参数化；关系类型、标签、排序字段均来自服务端白名单。

**设计原则：LLM 不直接生成 Cypher。**若业务上必须允许，则生成结果先经过 AST 解析、标签/关系白名单校验、只读事务与 EXPLAIN 成本检查，任一失败即拒绝执行。

#### 4.3.5 完整示例

任务：“A 项目的芯片供应如果中断，哪些交付任务会受影响？有哪些已认证的替代供应商能在 30 天内供货？”示例使用供应链扩展本体：Project 作为 Task 的子类，新增 Supplier 概念与 supplies 关系；部署时需在本体库中声明 domain/range 与动作模板。编译得到的路径查询分为两个子查询：影响面查询从项目沿 depends_on 正向到任务，替代供应商查询从资源反向到供应商。

```json
{
  "query_id": "Q-IMPACT-01",
  "scope": ["project", "global"],
  "starts": [
    {"bind": "p", "concept": "Project", "match": {"id": "PRJ-A"}},
    {"bind": "r", "concept": "Resource", "match": {"name": "芯片"}}
  ],
  "targets": [{"bind": "t", "concept": "Task"}],
  "relations": {"allow": ["depends_on", "requires"], "deny": []},
  "constraints": [{"expr": "t.status != 'done'", "hard": true}],
  "objective": {"type": "max_coverage"},
  "budget": {"max_depth": 5, "max_paths": 20, "timeout_ms": 1200}
}
```

```cypher
// 影响面：项目 - depends_on -> 任务 - requires -> 芯片资源
MATCH (p:Project {id: $pid})-[:depends_on*1..5]->(t:Task)
      -[:requires]->(r:Resource {id: $rid})
WHERE t.status <> 'done'
RETURN DISTINCT t.id AS task_id, t.name AS task_name,
       t.due_date AS due_date
ORDER BY t.due_date ASC;

// 替代供应商：供应芯片资源，且已认证、交期不超过 30 天
MATCH (s:Supplier)-[sp:supplies]->(r:Resource {id: $rid})
WHERE s.certified = true AND sp.lead_time_days <= 30
RETURN s.id AS supplier_id, s.name AS supplier_name,
       sp.lead_time_days AS lead_time, sp.confidence AS confidence
ORDER BY lead_time ASC
LIMIT 5;
```

如果项目级图中的 PRJ-A 尚未通过 same_as 链接到全局项目，则需要先在 4.4 中完成对齐补全；否则两个子查询无法在同一路径上融合。这正是“查询编译”和“图谱补全”必须成对设计的原因。

### 4.3.4 图库映射约束（nGQL）

物理模板不能只停在 SQL 上的对拍，上线多半落在图库。本节是报告 v3.2 在真实 NebulaGraph 3.8.0（159,240 顶点 / 391,159 边 / 3,734 个关系名）上的实测结论。

**四个模板的 nGQL 落法**（全部用 `GO` + 管道 + `UNION`，不需要 `MATCH`）：

| 模板 | nGQL |
|----|----|
| T1 单跳 | `GO FROM "v" OVER e_x YIELD dst(edge) AS n` |
| T2 双跳 | `GO FROM "v" OVER e_a YIELD dst(edge) AS mid \| GO FROM $-.mid OVER e_b YIELD dst(edge) AS n` |
| T3 双向邻居 | `(GO FROM "v" OVER e_x YIELD dst(edge) AS n) UNION (GO FROM "v" OVER e_x REVERSELY ...)` |
| T4 变长深度 3 | `GO ... AS v0 \| GO FROM $-.v0 ... AS v1 \| GO FROM $-.v1 ... AS v2 \| YIELD DISTINCT $-.v2 AS n` |

对拍结果：**120/120 × 4 = 480/480 逐元素等价**，p50 1.48–2.31 ms、p95 2.39–3.61 ms（含 Thrift RPC 与 10 分区，与进程内 SQLite 的 0.01 ms 不是同口径）。

**三条硬约束（都会改变 schema 设计）**：

1. **关系名必须是 edge type，不能存成属性**。Nebula 的边键是 `(src, rank, dst, edge_type)`，rank 默认 0；把关系名当属性时，"同一对实体存在多条不同关系"的后写会**静默覆盖**先写，无报错。实测 391,159 条边落在 361,205 个互异对上，25,901 对有多条关系，累计丢 **29,954 条（7.66%）**。定向对拍下通用边 schema 只有 **34.4%** 正确，类型化边 schema **100%**。用 rank 补救不可行：`GO` 不支持按 rank 过滤，会把一次遍历拆成 N 次。
2. **关系名 → edge type 需要生成器 + 映射表**。标识符只接受合法名字，3734 个关系名里 995 个是中文，必须哈希化并保留映射；DDL 本身很快（3,734 个边类型 2.8 s），但 **schema 变更要 10 s 级才在 storaged 生效**，期间写入会报 `Tag/Edge not found`。这与 3.2.5「关系即数据、可在线新增」冲突：**新增关系不是写一条边，而是一次 schema 变更**，必须走变更审批与灰度。
3. **没有跨语句事务**。3.3 的 `tbox_hash + abox_snapshot` 契约不能靠事务隔离实现，只能靠版本属性（每条边带 `valid_from/valid_to` 或版本号）+ 读时过滤。快照语义因此从"数据库事务"退化为"读时断言"，3.3 的验收口径要相应下调。

**容量与并发（实测，供选型）**：

| 指标 | 实测 |
|----|----|
| 单查询 p50 / p99 | 1.59 / 4.06 ms（100 万边）；1.99 / 3.89 ms（150 万边） |
| 规模弹性 | 边数 ×1.5，T1 p50 ×1.25（按 vid 定位分区，不做全图扫） |
| 读并发 | 1/8/32 线程 = 603 / 1,631 / 1,645 qps（8 线程到顶） |
| 写并发 | 1/8 线程 = 1,549 / 4,715 wps（3.05× 扩展） |
| 导入 | 25,347 边/秒（单会话满批）、53,366 边/秒（4 会话） |
| 内存 | 497 字节/边 → 10⁷ 边约 4.6 GB |

两条前提取自踩坑：**导入吞吐必须标注批处理方式**（同一 schema，按批拆类型只有 1,494 边/秒，分组满批 25,347 边/秒，差 17 倍，曾被误记为"类型化 schema 写不动"）；**尾部风险不能只看 p50**（100 万边档 T2 的 p99 冲到 50.82 ms，是双跳撞上高扇出节点，需靠超时与候选截断兜底）。

### 4.3.5 标注与金标的来源约束

系统精度最终取决于"什么算正确答案"由谁定义。这里把来源分成三类并给出不可越界的使用规则（实测见报告 v3.4 实验 AI）：

| 来源 | 可用于 | 不可用于 | 标记 |
|----|----|----|----|
| **业务专家** | L1 数字口径的分子分母、验收门禁 | —— | `source=expert` |
| **公开数据集标签**（MetaQA/DBP15K 等） | 方法可行性、机制验证（L2/L3） | 业务验收的 L1 数字 | `source=dataset` |
| **LLM 预标注** | 缩小专家工作量、L3 实现口径的辅助证据 | **L1 数字的任何分子分母** | `source=llm_preannotation` |

**为什么 LLM 不能当金标**：① 用模型标注去评测包含同一族模型输出的系统，是循环论证；② 目标业务领域的知识不在模型参数里，模型对该领域的"正确答案"没有任何依据。实测在**公开数据集**上，最强模型判「这条答案对不对」的准确率 0.811（全样本，覆盖率 0.879；只看已判定子集是 0.922，见 4.3.6）、假接受率 1.5%；hop3 在两套探针上分别是 0.625 与 0.865，长链上的结论不稳定，对外取保守值——**恰恰是最需要外部基准的长链推理，模型自己最不靠谱**。

**校准式预标注的强制流程**（三个条件缺一不可）：

1. **先校准**：用 100–150 题专家标注，量出该模型在**本领域、本任务**上的自动放行错误率，并给出 95% CI（bootstrap）。实测参考：n=100 半宽 5.0pp、n=150 半宽 4.0pp。
2. **审不确定 + 抽样复核**：模型判 `uncertain` 的全部进专家队列（实测约 12%）；模型判定的也按分层抽样复核，抽样比例由第 1 步的错误率决定。
3. **标记与分账**：预标注结果必须带 `source=llm_preannotation`；专家改动后改为 `source=expert`；报告里两类分开统计，禁止合并成"金标准确率"。

**退化检测**：模型可能在某个方向上退化成恒定输出。实测 `gpt-oss:120b` 决定率 100%、假接受 0%，但把真实答案全判为"否"（假拒绝 100%），准确率 0.6 完全是"全否"的产物。因此规定：**假拒绝率 > 0.5 或决定率 = 100% 直接判为不可用标注者，不看准确率**；每次换模型都要重跑校准集与扰动探针。

### 4.3.6 精度口径分级（v1.24 新增）

**问题**：同一个模型在不同口径下可以报出 0.68 到 0.92 的数字，都「真实」，但含义完全不同。实测：本地 glm-5.3 在 264 条扰动探针上，全样本准确率 **0.811**、已判定子集准确率 **0.922**、覆盖率 **0.879**——只报后者等于把 12% 的弃权洗成精度，差 11.1pp。

**三条口径，不可混用**：

| 口径 | 定义 | 能用来说什么 | 不能用来 |
|----|----|----|----|
| C1 对数据集标签的一致度 | 与 MetaQA/DBP15K 给定答案的一致率 | 方法间横向比较、复现性 | 说「正确率」；含 5–10% 标签噪声 |
| C2 对已知真值的准确率 | 扰动探针（真答案应判 yes / 同域错答案应判 no） | 判断器本身的可靠性 | 外推到开放问答；只覆盖单答案判断 |
| C3 对人工裁决的一致度 | 与专家标注的一致率 | 上线前唯一可信的精度声明 | 样本 <100 时外推（24 条只能作方向证据） |

**强制规则**：

1. 报 C2 必须同报**覆盖率**与 **acc_on_all**，禁止只报已判定子集。
2. 报 C1 必须写明「对数据集标签」，不得写成「准确率」「命中率」。
3. 报 C3 必须写样本量；n<100 标注「不作总体外推」。
4. 退化检测（假拒绝 >0.5 或决定率 =100%）优先于任何准确率数字，命中即判不可用。
5. **模型判定不得直接作为人工复核的分流依据**。按「模型说 reject 就派人复核」分流，会把 300 题里约 110–140 条本来正确的题派给人工。分流必须基于**可验证信号**（候选是否为空、路径是否完整、答案跨度是否超限），模型判定只能作为排序提示。
7. **模型预标注只能放行、不能拦截**。实测不对称（300 题全量核对）：无分歧集共识「接受」错误 **0/90（0%）**、共识「拒绝」错误 **29/48（60.4%）**、共识「拿不准」34.6%；金标接受率 **77.7%**，qwen-max 46.0%、glm-5.3 40.3%，偏严 31–37pp。两模型假接受 **1–3 条**、假拒绝 **53–83 条**（约 1:25）。凡以「模型判否」触发的降级、澄清、转人工路径，都作用在 23–36% 的正确样本上，必须重写。因此：模型说 accept 的可高比例自动通过（仍需保留抽样复核）；模型说 reject/uncertain 的**必须**回到结构化信号重判，不得直接判错或转人工。这条同时适用于 4.1.1 的候选来源判据、4.2 的语义剪枝阈值、3.4.2 的门禁自动判定率——三处凡是把「模型拒绝」当信号的阈值都必须按本口径重标。
6. **hop≥3 必须澄清后再答**。136 条分歧中 hop3 占 44 条，其中 20 条（45.5%）逐条核对后仍无法判定——不是模型能力问题，是题面本身指向不唯一（如「某片演员演过的片的导演的编剧」）。`六问门禁`的「问题是否可判定」一问，在 hop≥3 上不得自动判定通过。

**注意口径差异**：上表 C2 的准确率是在「单答案判断」任务上测的（探针），本节的 0%/66.7% 是在「答案集是否正确且完整」任务上测的（300 题标注）。两者任务不同、错误模式也不同，不可互相换算。

**为什么数据集标签不能当基准**：同一批 300 题，两个强模型分歧 **45.3%**。136 条分歧全量裁决的结果：应为 accept 105 条（77.2%）、应为 reject 8 条（5.9%）、题目本身歧义 23 条（16.9%）；坐实数据集事实错误 3 例（如把 Jocelyn Moorhouse 导的片算作 John Madden 的作品），占分歧 **2.21%**，300 题总体估计 **1–2%**。因此：① 以 C1 为基础的绝对精度不能作为对外承诺；② 但噪声量级是 1–2pp，不是"数据集不可用"——主要缺陷是**标签不完整与题目歧义**（16.9% 的分歧根本无法判定）。

### 4.3.7 容量与并发约束（v1.29 新增）

**实测背景**：单机 8 核，k-best 枚举深度 4、K=5，平均每条查询展开 18.2 万次边、单查询 96 ms。以下三条是硬约束，不是建议。

| 约束 | 实测证据 | 落地要求 |
|----|----|----|
| **禁止用线程扩吞吐** | 1→8 线程：QPS 5.2→4.7（**0.90×**），p99 3.0 s→20.2 s（**6.6×**） | 服务进程内单线程处理；线程只用于 I/O 与连接池 |
| **进程扩展以 4 为默认** | 2/4/8 进程 = 1.75×/2.48×/**2.73×**，效率 88%/62%/34% | 单机 4 进程起，按 p99 扩容；8 进程只在流量确定时启用 |
| **任务必须动态派发** | 4 进程：静态轮询 1.99×（效率 50%）→ 动态逐条 **2.74×（68%）** | 队列按查询逐条取任务（chunk=1），禁止 `qs[i::n]` 静态切分 |

**天花板在单查询关键路径，不在核数**：100 条查询里最慢一条独占总量 26%，即使无限并行加速比也不会超过 **3.78×**。因此"加机器"在 8 进程之后边际收益趋零，真正的杠杆是**限制单查询代价**——与 4.2 的剪枝、4.1.5 的深度上限是同一件事。查询内并行（把一条查询拆到多核）是唯一能突破该上限的路径，尚未实现，不得假设可用。

**容量规划口径**：

1. 按 **p99** 算机器数，不按均值（本压测 p50 44 ms、p99 3,038 ms，相差 69 倍）。
2. 单机容量 = 进程数 × 单进程 QPS × (1 − 尾延迟折损)；4 进程时按效率 0.62 折算。
3. 扩容告警触发条件：p99 连续 5 分钟超过 SLA 或队列积压持续增长——不是 CPU 利用率。

### 4.3.8 租户隔离与 PII（v1.30 新增）

**前提**：NebulaGraph 3.8.0 **没有行级安全（RLS）**，没有 `WHERE tenant_id = current_user` 这类原生机制。因此"租户隔离"不是配置项，是**必须自己实现的四道代码约束**，缺一道就有实测泄漏。

| 序号 | 约束 | 缺了会怎样（实测） |
|----|----|----|
| R1 | **vid 前缀由服务端拼**：模板只接受裸实体名，调用方传入带 `:` 的串一律拒绝 | 按名字跨租户查找 3/3 命中他租户 |
| R2 | **条件重写**：`LOOKUP`/过滤条件由服务端改写为 `Person.tenant == "<ctx>" AND (原条件)`，模型不得自带条件 | 全表扫描一次取走 720 条 PII |
| R3 | **写入校验**：写边时校验两端 vid 前缀相同，不同租户直接拒绝 | 跨租户脏边写入 3/3 成功，之后任何读取都会"合法"越界 |
| R4 | **投影白名单 + 脱敏**：对外只出 `name/age/city_level`，PII 字段脱敏后出 | PII 直取 9 条、全表 720 条；注意 R1+R2 齐备时 PII 仍是 729 条，**前缀管不住属性** |

**验收口径**：必须同时报两个指标，不能用其中一个代表另一个。

- `leak_runs`：跨租户越权运行数（目标 0）
- `pii_leaks`：未脱敏敏感字段条数（目标 0）

实测三档：裸图库 **10/24、PII 729**；只做 R1+R2 **3/24、PII 729**；四道齐备 **0/24、PII 0**。回归用例用 4.3.8 附录的 8 条攻击（前缀穿越、跨租户查找、注入、全表扫描、零宽伪造、PII 直取、跨租户写入、limit 越界）。

**PII 清单与脱敏规则**：

| 字段 | 处理 |
|----|----|
| email | `1***@c***` |
| phone | `138****34` |
| idcard | `1380**********34` |
| address | 整段替换为「已脱敏」 |
| name | 白名单保留（检索需展示）；若要求去标识化，改哈希 + 反向映射表 |

**架构取舍**：每租户独立 space 是强隔离，但 DDL 与 space 数随租户线性增长（建 1 space + 2 索引约 38 s），上千租户不可运维，且跨租户聚合查询不可能。**建议租户 < 50 用独立 space，更多用单 space + 前缀方案**，并把 R1–R4 收敛到唯一编译入口（业务代码不得直接拼 nGQL）。

**已知未覆盖**：注入面只测了"非法片段"（被 nGQL 语法拒绝），"合法片段改写投影/条件"未测；零宽伪造 vid 是负向测试，不构成前缀校验的正确性证据；跨租户统计视图与图库侧审计日志均未做。

### 4.3.9 规模上限与 storaged 资源配置（v1.31 新增）

**实测区间**：25 万 → 400 万边、7 个台阶、Zipf(α=1) 度数分布、`replica_factor=1`、4 partition。

| 边数 | T1 p50 / p99 | 属性检索 p50 |
|----|----|----|
| 2,000,000 | 1.14 / 2.17 ms | 0.75 ms |
| 4,000,000 | 1.15 / 2.03 ms | 0.63 ms |
| 8,000,000 | 1.61 / 3.00 ms | 0.84 ms |
| **10,000,000** | **1.39 / 3.05 ms** | **1.18 ms** |

**结论一：10⁷ 已实测通过，查询侧不随规模退化。** 40 倍规模（25 万→1000 万边），T1 p50 从 1.38 ms 到 1.39 ms，等于没变。1000 万边 / 333 万顶点在 1 GiB storaged 上灌入成功，峰值 RSS **552 MB**、**59,524 边/秒**。

**唯一需要盯的退化指标是 T2 p99**：10 ms → **25.8 ms**（深跳 + 高度数节点），应对手段是 4.1.5 的深度上限与超级节点剪枝，不是加内存或加机器。

**结论二：写入的成败由「单条语句批量」决定，不是容器上限，也不是数据量。** 实测 4 组对照：

| 单条 INSERT 批量 | 容器上限 | 结果 |
|----|----|----|
| 40,000 | 1 GiB | **50 万边失败**（RSS 880 MB 时被拒） |
| 40,000 | 3 GiB | **50 万边失败**（RSS 519 MB 时被拒） |
| 5,000 | 3 GiB | 灌满 **1000 万边**（峰值 555 MB） |
| **5,000** | **1 GiB** | **灌满 1000 万边**（峰值 552 MB） |

机制：`memory_tracker_limit_ratio=0.8` 约束的是**跟踪内存**而非 RSS；4 万边的单条语句会产生远超稳态 RSS 的瞬时分配，于是"RSS 还很空"就撞水位。**把上限从 1 GiB 提到 3 GiB 没有任何帮助，把批量降到 5 千就通了。**

**结论二附：水位参数不要动。**

| 参数 | 值 | 含义 |
|----|----|----|
| `memory_tracker_limit_ratio` | 0.8（默认） | 内存用到容器上限 80% 即**拒绝写入** |
| 容器内存 | 1 GiB | 水位 = 819 MB |
| `rocksdb_block_cache` | 4 MB/列族 | 边类型数直接乘进去（3,734 个关系名 → 上限空间 14.6 GB，**实际占用需实测**） |
| `memory_tracker_untracked_reserved_memory_mb` | 50 | 未跟踪内存预留 |

失败形态是**写入被拒**（`Used memory hits the high watermark`），不是变慢、不是 OOM 被杀。这个区别决定了运维处置方式：撞水位可恢复、可观测；OOM 会静默丢进程。

**结论三：驻留内存不随 `DROP SPACE` 归还，容量不可用边数描述。**

实测：清空 space 后等 45 s，RSS 从 702 MB 只回落到 399 MB。后果是同一容器、同一负载的"能灌多少边"差 **8 倍**（冷启 96 MB → 400 万边；热启 399 MB → 50 万边即失败）。**因此容量指标只能是"当前 RSS 与水位之间的距离 + ingestion 峰值"，不能是"最大边数"。**

**部署要求**：

1. storaged 容器内存 ≥ **2 GiB**（水位 1.6 GB），生产建议 **4 GiB**；1 GiB 下只能容纳 50 万–400 万边且不可预测，不满足 10⁷。
2. `memory_tracker_limit_ratio` **不要调低**去"多装数据"——它把失败变成显式拒绝；调高可能被 OOM Killer 杀掉。
3. 关系名数量（= edge type 数）必须计入内存预算；4.3.4 已要求"关系名必须是 edge type"，这两条会叠加放大资源需求。
4. **容量验收用"灌数到水位"**：连续写入直到拒绝，记录当时边数、RSS、报错；不把某个边数当静态容量。
5. 10⁷ 在 1 GiB 配置下**判不可行**；4 GiB 下是否可行**未验证**，不得在方案里写成"已验证支持 10⁷"。

### 4.4 路径缺失时的诊断、补全与防污染

在真实企业图谱中，“找不到路径”是常态而非异常：可能是实体未对齐、关系未抽取、约束过严，也可能是任务假设本身不成立。在 4.1.1 的 L1–L4 参与模型下，“缺失”分两种：本体里真没有（封闭世界拒绝），以及本体沉默但 LLM 常识认为“应当有”（语义缺口）。两者处置完全不同：前者走数据治理或向用户澄清，后者才允许 LLM 提议补全。补全机制因此必须回答四个问题：缺什么、是哪一类缺失、能不能安全补、补完之后如何防止假设污染事实。本节把补全分为诊断分级、分层修复、置信度传播和写回治理四部分，每个环节都定义 LLM 的参与边界与机器裁决。

#### 4.4.1 失败诊断与错误分级

查询失败后先诊断，不直接放宽条件重试。诊断器执行两组探针：**确定性探针**（节点存在性、类型与度数、弱连通分量、无约束最短路、关系签名、最近锚点、溯源完整性）给出结构性错误码；**语义探针**（LLM 对失败原因的解释性归因）区分“图里真没有”与“图里有但没查到”。

**表 4-3 路径缺失的错误码、缺失类别与首选修复**

| 错误码 | 判定条件 | 缺失类别 | 典型原因 | 首选修复 |
|----|----|----|----|----|
| E01 | 起点/终点未接地 | 语义缺口 | 实体不存在、别名缺失、跨语言 | 放宽实体候选；触发 L2 对齐 |
| E02 | 概念路径不可达 | 本体沉默 | 本体缺关系类型或中间概念 | LLM 提议概念补全，本体评审通过前拒绝（4.4.2）；回灌 3.4.4 |
| E03 | 实例图不连通 | 语义缺口 | ETL 缺边、跨库未对齐 | L2/L3；用 WCC 定位 |
| E04 | 约束过度剪枝 | 查询侧 | 硬约束太严、属性缺失 | L0 逐条放宽并记录 |
| E05 | 深度预算耗尽 | 查询侧 | 路径过长或图稀疏 | L0 增深度；L4 分段 |
| E06 | 语义阈值过高 | 查询侧 | 嵌入质量差、领域漂移 | L0 降阈值；重算嵌入 |
| E07 | 超时/资源限制 | 查询侧 | Hub、组合爆炸 | 剪枝、并行、缓存；L4 |
| E08 | 图层范围错误 | 查询侧 | 项目图/全局图混淆 | L0 scope union |
| E09 | 对齐缺失 | 语义缺口 | same_as/instance_of 未建 | L2 实体对齐 |
| E10 | 关系方向/类型不匹配 | 本体沉默 | 本体签名与实例不一致 | L1 逆关系/子属性；修数据 |

**语义探针的裁决规则**（对应 3.4.3 三级裁决）：LLM 对失败原因的解释只影响诊断报告的解释字段与修复建议，不影响错误码本身；错误码由确定性探针独立产生，两者并列写入诊断记录。语义探针失败时退化为纯确定性诊断，流程不中断。

诊断报告新增两个字段：missing_class（本体沉默/语义缺口/查询侧）与 llm_attribution（语义探针解释，可空）。查询侧缺失不进入补全阶梯的 LLM 提议环节，只改查询参数。

#### 4.4.2 分层补全阶梯：LLM 参与边界与裁决强度

补全按成本与风险从低到高排列。诊断码决定候选层级，不要求逐层执行；一旦得到通过校验的路径即停止。与 4.1.1 的四层参与模型对齐，每个补全层级都定义 LLM 的参与点与裁决规则：

**表 4-4 路径补全的六个层级与 LLM 参与边界**

| 层级 | 主要操作 | LLM 参与点 | 裁决规则 | 写图策略 | 风险 |
|----|----|----|----|----|----|
| L0 查询松弛 | 放宽深度/阈值/关系白名单/方向；多起点、k-best、scope union、BFS 兜底 | 无（确定性重参数） | 参数变更逐条记录为 relaxation | 否 | 低 |
| L1 本体推理 | 传递闭包、逆关系、子属性、domain/range、规则 | 无（本体与规则层推导） | 推理结果必须可由规则复算 | 可选 derived | 低–中 |
| L2 对齐补全 | 实体解析、same_as/instance_of、跨图桥接 | LLM 生成候选对（同 3.4.1 的提及检测） | 候选对逐条过签名校验；冲突进人工仲裁 | 是，需审核 | 中 |
| L3 链接预测/证据抽取 | 嵌入 kNN、GNN、关系分类、LLM 文档抽取 | LLM 提出候选边与可验证证据定位 | 逐边独立验证：签名兼容 + 证据定位 + 分数校准 | 影子图 | 中–高 |
| L4 路径拼接 | 双向搜索、最近锚点、共享邻居、虚拟桥 | 无（离线嵌入 ANN 召回，非在线 LLM） | 拼接边带 gaps 标记与 λ_bridge 惩罚 | 否，仅查询期 | 中 |
| L5 外部获取/澄清 | 问用户、调 API、抓文档、补录 | LLM 起草澄清问题与检索策略 | 用户提供的事实走正常入库门禁（3.2.6） | 是 | 高 |

> **命名提示**：本表的 L4 是补全阶梯里的“路径拼接”，与 4.1.1 的 L4“路径重排与解释”同名不同义；重排的触发判据见 4.1.2 表 4-0d，不要与本节 L4 混用。


**关键设计：LLM 只在 L2/L3/L5 提议，且提议不等于写入。**E02 类“本体沉默”错误走“LLM 提议概念补全 + 本体评审 + 回灌 3.4.4”路径，补全的是本体定义而不是实例边；评审通过前查询只能拒绝并报告缺口码，不得用 LLM 常识直接放行。

L0 的每次放宽都必须记录为 relaxation，包括放宽了哪条约束、放宽幅度和原因；否则无法区分“图里真的有路”和“把约束改松了”。

L1 的推理优先以虚拟边形式参与查询，避免物化推理污染主图；只有被高频复用且规则置信度高的推理结果才物化为 derived=true 的边。

**物化规模上限（v1.16，实测）**：在 schema.org 27.01（912 类 / 1,471 属性）上跑 RDFS 子类/子属性传递加 domain/range 下推，**3 轮收敛、推断 125,843 条**：`domainIncludes` 2,219 → 61,802、`rangeIncludes` 2,029 → 66,058，本体整体膨胀 **27 倍**（7.0s 算完）。因此物化不是"优化项"而是"必须设阈值"的动作：**先统计「被查询复用次数」分布，只物化复用次数 ≥ N 的推理边**，否则每次本体变更都要全量重算 12 万条并把主图噪声化。

L3 中 LLM 文档抽取的证据必须携带可验证定位（source、页码/行号、URL）；不可验证的“LLM 认为存在”不作为 evidence 项参与打分，只计入模型先验（4.4.4 的 freq 项）。

#### 4.4.3 路径拼接与双向搜索

当起点和终点位于不同连通分量时，单纯增加深度无效。采用双向搜索加锚点拼接，可以在不写图的前提下恢复部分路径：

- 从 S 和 T 各扩展 r 跳，优先找交集节点；交集为空时找“近邻对”。
- 近邻对由嵌入 ANN 召回，按类型兼容、关系签名、证据强度排序。
- 每个近邻对生成一个虚拟桥边，桥边权重加 λ_bridge 惩罚，默认 3.0。
- 多图场景通过 same_as / instance_of 跨层桥接；缺失时生成 SAME_AS_CANDIDATE 虚拟边。
- 用弱连通分量和 ALT 地标剪掉不可能的分量对，降低搜索成本。

拼接结果必须显式标记 stitched=true 与 gaps=[...]，下游规划器据此决定是否先做验证任务。

**实现口径（v1.x）**：L4 在常规搜索与跨库 bridge 拼接都无路径时触发，只在起终点全部解析成功且未被过滤时执行。它从两端各做半径 2、上限 64 个节点的双向邻域遍历，用嵌入余弦与词项 Jaccard 的较大值给邻域锚点对打分，取分数 ≥0.55 的前 3 对候选；每个候选只在两段路径无重叠节点时合成一条路径，并插入 `hypothesized(relation=same_as_candidate)` 虚拟边，桥代价为 `3.0 + 2.0 × (1 − score)`，不写主图。合成路径同时带 `stitched_path` 与 `hypothesized_edge` 质量标志，下游必须先验证 gap 才能执行副作用动作。

当查询显式设置 `auto_propose=true` 时，L4 gap 会被写成 `same_as` 影子边，`status=pending`、`source=completion_l4`，返回 `proposed_shadow_edges` 列表；pending 不进入主图，也不参与未开启 `include_hypotheses` 的查询。跨 store 候选不自动写成 bridge，因为 bridge 注册后立即可遍历，仍走人工 `bridge` 审核，避免把未验证对齐变成事实。

E09 的跨 store 对齐候选写入独立的 `bridge_candidates.json`：`status=pending`、`source=completion_e09`，不进入 `bridges.json`，因此不会参与任何路径遍历。审核入口为 `action=bridge bridge_action=candidates|cleanup|accept_candidate|reject_candidate`；只有接受时才调用 `link_bridge` 生成可遍历 bridge，拒绝只记录状态。批量评审用 `batch_review`：默认 `dry_run=true` 只返回将影响的候选列表，真正应用必须同时传 `dry_run=false` 与 `confirm=true`，并支持 `ids` 限定范围。`cleanup` 返回各状态计数、最老 pending 天数和阈值校准建议；校准只用已接受/已拒绝样本，在候选分数上网格搜索 F1，输出 `suggested_threshold` 与 `best_f1`，并给出精度 Wilson 95% 区间，不自动改线上阈值。指标变化时写入 `bridge_calibration_history.jsonl`，最多保留 200 条；报告返回 `previous_threshold`、`threshold_delta` 与最近 5 次快照，重复指标不重复记录。`best_f1` 下降超过 0.05 或建议阈值移动超过 0.10 时写入 `trend_alert`，供回归排查。pending 超过 30 天自动转为 `expired`，过期候选不可再接受。这样补全召回率的分母包含 E09，但精确率与可遍历性仍由显式审核控制。

```python
def complete_path(q, budget):
    diag = diagnose(q)   # 确定性探针 + 语义探针（可退化）
    for level in ladder_for(diag):
        if budget.exhausted():
            break
        if diag.missing_class == "query_side" and level.uses_llm():
            continue     # 查询侧缺失不消耗 LLM 提议预算
        q2, meta = apply_level(q, level, diag)
        res = search(q2)
        if res and verify(res, q, diag, meta):
            return res.with_provenance(meta)
        candidates.extend(collect_candidates(level, q, diag))
    return KnowledgeGap(diag, candidates, next_actions=...)
```

verify 至少检查：端点绑定匹配、硬约束满足、关系类型合法或已显式记录放宽、路径置信度达标、假设边数量不超过阈值、无禁止节点与环。LLM 提议的候选边在 verify 之外还要逐边过签名兼容检查，任一边被拒则整条候选路径丢弃，不做部分采纳。

**实现口径（v1.x）**：no-path 结果中的 `knowledge_gap.completion_plan` 按本次诊断码生成有序 `L0-L5` 步骤，每步返回动作、`llm_role`、验证要求和 `write_policy`。`L4` 与 `L5` 作为剩余缺口的兜底始终排在末尾；`L2/L3/L5` 的 `llm_role` 非 `none` 且 `write_policy` 不是 `no graph write`，下游执行器必须走评审或正常入库门禁，不能把计划当成已执行事实。

#### 4.4.4 补全边打分与置信度传播

候选边的可信度由语义相似、链接预测、类型兼容、外部证据和共现频率共同决定：

$$
s(e) = \sigma(\alpha \cdot \cos(e_u,e_v) + \beta \cdot P_{\text{link}}(u,r,v) + \gamma \cdot \text{type\_compat}(u,r,v) + \delta \cdot \text{evidence}(e) + \varepsilon \cdot \text{freq}(e))
$$

默认权重 0.30/0.35/0.20/0.10/0.05；在标注的正负样本上用等渗回归校准，输出校准后的概率而不是原始分数。默认 τ_link=0.7，高风险决策提高到 0.85。**LLM 提出的边不因来源是 LLM 而加分或减分**：打分函数只看五项客观特征，evidence 项只认可可验证定位（4.4.2 的 L3 规则），“模型很确定”本身不构成证据。

路径置信度采用安全优先的最小值，同时报告几何平均：

$$
p(p) = \min_{e \in p} p(e)
$$

$$
p_{\text{geo}}(p) = \exp\left(\frac{1}{|p|} \cdot \sum_{e \in p} \ln p(e)\right)
$$

边按溯源分为四级：

- ASSERTED：源系统直接断言，p=1.0。
- DERIVED：规则或本体推理得到，p=rule_confidence，默认 0.95。
- HYPOTHESIZED：模型或文档抽取提出，p=model_score，默认上限 0.9。
- VIRTUAL：仅查询期存在的桥边，不落库。

为抑制补全边，路径代价加入惩罚项：

$$
w'(e) = w(e) + \lambda_h \cdot (1-p(e)) + \lambda_v \cdot \mathbf{1}_{\text{virtual}} + \lambda_u \cdot \mathbf{1}_{\text{unverified}}
$$

默认 λ_h=2.0、λ_v=3.0、λ_u=1.5。当 $p(p) < 0.5$ 或假设边比例超过 0.3 时，Agent 不得自动终止，必须先执行验证任务或请求人工确认。

#### 4.4.5 写回策略与防污染

补全边默认写入影子图或候选边表，而不是主图。写回遵循以下规则：

- 影子边字段：confidence、evidence、model_version、created_by、status、expires_at。
- 晋升条件：外部证据确认、N 个独立来源一致、或人工审核通过；默认 N=2。
- 晋升后写入主图，保留完整 provenance 链，状态改为 ASSERTED。
- 未确认边 TTL 默认 30 天，到期软删除；被驳回的边进入负样本集。
- 任何决策证据路径若包含未晋升边，必须带 hypothesized_edge 质量标志。
- **LLM 提议边永不自动晋升**：晋升必须由非 LLM 证据（外部系统、人工、N 个独立来源）触发；LLM 只能提议、只能提供证据线索，不能自我确认。

引入“补全债务”指标：completion_debt = 未确认假设边数 / 决策使用边总数。该指标进入 4.6 的质量看板，超过 0.1 触发治理任务。

```cypher
MERGE (u:Entity {id: $uid})
  -[e:HYPOTHESIZED {relation: $rel}]->
      (v:Entity {id: $vid})
ON CREATE SET e.confidence = $p,
              e.evidence = $evidence,
              e.model = $model,
              e.status = 'pending',
              e.created_at = datetime(),
              e.expires_at = datetime() + duration('P30D');
```

写回必须幂等：用 MERGE 加唯一约束；边版本化保留历史；删除采用软删除，避免审计断链。

#### 4.4.6 示例：跨图对齐缺失

任务仍为“A 项目芯片供应中断的影响与替代供应商”。执行发现 PRJ-A 与全局项目未对齐（E09），且芯片资源与候选供应商之间没有 supplies 边（E03）。补全过程：

- L2：LLM 从 ERP 编号规则生成候选对齐（同 3.4.1 提及检测），实体解析与签名校验通过后建立 PRJ-A -same_as-> G-PRJ-A，置信度 0.93。
- L3：LLM 从认证文档抽取 S-77 -supplies-> CHIP-X，证据定位到认证清单第 3 页，链接预测分数 0.81，写入影子边。
- 验证：调用采购 API 确认 S-77 具备该料号供货资格，置信度提升到 0.98，晋升为主图边。
- 融合：得到路径 PRJ-A -same_as-> G-PRJ-A -depends_on-> T-42 -requires-> CHIP-X <-supplies- S-77，路径置信度 0.93。

该路径包含 1 条对齐边和 1 条已验证的供应边，均带 provenance；若采购 API 无法确认，则路径置信度保持 0.81，Agent 只能输出带不确定性的建议，不能直接下单。注意晋升由采购 API（外部证据）触发，LLM 的抽取结果只提供证据线索，不参与自我确认。

#### 4.4.7 全部失败时的知识缺口报告

如果 L0–L5 均失败，返回结构化的 KnowledgeGap，而不是编造答案：

```json
{
  "status": "no_path",
  "diagnosis": ["E03", "E09"],
  "missing_class": {"E03": "semantic_gap", "E09": "semantic_gap"},
  "llm_attribution": "芯片资源与供应商的供应关系在两个数据源中均未出现，建议接入采购系统",

  },

```

missing_class 与 llm_attribution 把“图里真没有”与“没查到”分开报告：本体沉默与语义缺口进入 3.4.4 的回灌评审队列，查询侧缺失进入查询优化任务。该报告同时写入 4.6 的质量问题队列，作为本体或数据治理的输入。

### 4.5 知识推理路径到下一步任务规划的转换（Path → Plan）

最短路径给出的是“事实之间的连接”，不是“下一步做什么”。从路径到计划需要补齐动作语义、前置条件、责任主体、成功判据和审批门禁。本节定义 PathPlan 中间表示和编译算法，把路径边转换为可执行的任务 DAG，并接回 5.1 的 POMDP 动作空间。

#### 4.5.1 转换原则

- 路径方向即因果/依赖方向；反向边必须先归一化，不能把“被依赖”当成“依赖”。
- 每条边要么绑定一个动作模板，要么绑定一个验证步骤；不能默默丢弃。
- 动作必须由本体类型和实体属性接地，禁止生成“处理一下”这类不可执行任务。
- 每个任务必须有可观测的成功判据，最好是一条验证查询。
- 有副作用的动作按不可逆程度分级，必要时加人工审批。
- 假设边必须先验证，再允许后续副作用动作。
- 计划是 DAG 而非线性列表；无数据依赖的任务可并行。
- 每个任务保留 evidence_ref 指回路径边，保证可解释性。
- 计划置信度取路径置信度与任务置信度的最小值，不用平均值掩盖短板。

#### 4.5.2 PathPlan 中间表示

PathPlan 的 JSON 结构如下，任务字段与 5.2.4 的规划动作一一对应：

```json
{
  "plan_id": "PLAN-2026-1116-01",
  "source_path_id": "PATH-2026-1116-07",
  "goal": "在 30 天内为 CHIP-X 建立替代供应",
  "path_confidence": 0.93,
  "tasks": [
    {
      "id": "T1",
      "action_type": "verify",
      "title": "核验 S-77 的供应商认证",
      "depends_on": [],
      "preconditions": ["Supplier(S-77) 存在"],
      "postconditions": ["Supplier(S-77).certified == true"],
      "inputs": {"supplier_id": "S-77"},
      "outputs": {"certificate_valid_until": "date"},
      "owner": "procurement",
      "due": "2026-11-20",
      "success_check": {"query_ref": "VQ-1", "expr": "certified == true"},
      "evidence_ref": "PATH-2026-1116-07/edge/2",
      "risk": "low",
      "approval": false
    }
  ],
  "verification_queries": ["VQ-1", "VQ-2"],
  "approval_gates": [],
  "rollback": ["T3: 释放预留产能"]
}
```

动作类型限定为 query、verify、acquire、execute、notify、decide、await_human、monitor 八类，避免动作空间无限扩张。

#### 4.5.3 关系类型到动作模板的映射

映射表可以由本体直接驱动：在关系类型上增加 plan:actionTemplate、plan:precondition、plan:postcondition、plan:sideEffect 注解。表 4-5 给出默认映射。

**表 4-5 路径关系类型到任务动作模板的默认映射**

| 关系类型 | 规划语义 | 默认动作模板 | 成功判据 |
|----|----|----|----|
| depends_on | 前置依赖 | ensure_predecessor / schedule | predecessor.status == done |
| requires | 资源需求 | reserve_resource / validate_capacity | resource.available >= qty |
| constrained_by | 约束合规 | check_constraint | constraint.status != violated |
| mitigates | 风险缓解 | execute_mitigation | risk.score 降到阈值内 |
| leads_to | 因果预期 | monitor_outcome | metric 在预期区间 |
| supplies | 供应关系 | procure / contact_supplier | delivery_confirmed |
| same_as | 身份对齐 | verify_alignment | confidence >= 0.85 |
| instance_of | 类型归属 | validate_type | type 与概念匹配 |
| owns / responsible_for | 责任归属 | assign_owner | owner 非空 |

没有映射的关系默认绑定 verify_relation，只做证据核验，不产生副作用；这样新关系类型不会导致计划器静默越权。

表中 supplies、owns、responsible_for 属于领域扩展关系，部署时同样通过本体注解注册动作模板，不应在计划器代码中硬编码。

#### 4.5.4 编译算法

编译分为七步：

- 归一化：合并重复边、去除身份边、按依赖方向重排，保留原始边 ID。
- 模板绑定：按关系类型查动作模板，用实体属性填充参数；模板缺失时降级为验证动作。
- 前置条件闭包：在当前 Belief State 上评估前置条件，未满足的生成前驱任务，递归深度不超过 2。
- 依赖图构建：叠加路径顺序、数据依赖和资源冲突，检测环并拆解。
- 验证查询生成：为每个后置条件生成可执行查询，挂到 success_check。
- 风险与审批：按副作用等级、金额、不可逆性分配审批门禁。
- 动作发射：把 DAG 映射为 a_query、a_reason、a_execute、a_terminate 的偏序序列。

```python
def path_to_plan(path, belief, templates):
    path = normalize(path)
    tasks = []
    for edge in path.edges:
        tpl = templates.lookup(edge.relation) or templates.verify_relation
        tasks.append(tpl.bind(edge, belief))
    tasks = close_preconditions(tasks, belief, max_depth=2)
    dag = build_dependencies(tasks, path.order)
    dag = break_cycles(dag)
    for task in dag.tasks:
        task.success_check = make_verification_query(task)
        task.approval = requires_approval(task)
    task_conf = min((t.confidence for t in dag.tasks), default=1.0)
    confidence = min(path.confidence, task_conf)
    return PlanGraph(tasks=dag, confidence=confidence)
```

close_preconditions 必须带预算：新增任务超过 20 个或深度超过 3 层时停止扩展，转为人工分解，避免计划爆炸。

#### 4.5.5 示例：从供应路径到采购计划

路径为 PRJ-A -same_as-> G-PRJ-A -depends_on-> T-42 -requires-> CHIP-X <-supplies- S-77，约束为供应商已认证且交期不超过 30 天。编译得到的任务 DAG 如下：

```text
T1 认证 ─┐
T2 交期 ─┼→ T3 询价 ─→ T4 分配 ─→ T5 监控 ─→ T6 备选
```

其中 T1 与 T2 并行；T3 依赖 T1、T2；T4 依赖 T3；T5 依赖 T4；T6 是条件任务，仅当 T5 观测到延迟风险超过阈值时触发。

对应任务片段：

```json
[
  {
    "id": "T1",
    "action_type": "verify",
    "title": "核验 S-77 供应商认证",
    "depends_on": [],
    "success_check": {"query_ref": "VQ-1", "expr": "certified == true"},
    "evidence_ref": "PATH-2026-1116-07/edge/4",
    "approval": false
  },
  {
    "id": "T3",
    "action_type": "execute",
    "title": "向 S-77 询价并预留 30 天产能",
    "depends_on": ["T1", "T2"],
    "success_check": {"query_ref": "VQ-3",
                      "expr": "reservation.status == 'confirmed'"},
    "evidence_ref": "PATH-2026-1116-07/edge/4",
    "approval": true
  }
]
```

T3 有资金与产能承诺，设为审批门禁；T4 修改资源分配，属于中风险；T5 只读监控；T6 是条件任务，由 T5 的观测触发。

#### 4.5.6 计划质量门禁

- 每个任务必须有 success_check 和 evidence_ref，否则不允许进入执行队列。
- 有副作用的动作必须有责任人和截止时间；不可逆动作必须有审批门禁。
- 路径含 HYPOTHESIZED 边时，验证任务必须是该边下游副作用任务的前驱。
- 计划置信度低于 0.6 时，只允许查询和验证，不允许执行副作用动作。
- 单计划任务数不超过 20，依赖深度不超过 3；超出则拆分为子计划。
- 高风险计划先在影子模式执行，观测通过后再切换真实执行。

这些门禁把 4.4 的补全风险与 4.5 的执行风险串起来：补全越不确定，计划越偏向验证而不是行动。

#### 4.5.7 执行反馈与重规划

计划执行不是单向的。每个动作完成后，用 success_check 生成观测并更新 Belief State；失败时按以下顺序处理：

- 任务级失败：重试一次；仍失败则标记该任务失败，尝试同一路径上的替代动作模板。
- 路径级失败：切换到 k-best 中的下一条路径；若都失败，回到 4.4 触发补全。
- 事实冲突：新观测与本路径边矛盾时，立即失效该边并重新规划，不能继续沿用旧证据。
- 计划级失败：记录计划与实际执行的偏差，进入过程挖掘，反哺动作模板和边权校准。

所有失败与重规划事件写入决策链路日志，作为 4.6 质量评估的输入。

### 4.6 基于最短路径结果的图谱质量评估

最短路径查询是图谱的端到端探针：一次查询同时检验概念是否可达、实体是否可接地、实例是否连通、跨图是否对齐、约束是否可满足、编译器是否保真。把生产查询日志、基准任务和抽样探针结合起来，可以持续度量本体图与实例图的质量，并把失败归因到具体的建模或数据问题。本节给出指标体系、评分方法、评估协议和治理闭环。

#### 4.6.1 评估框架与数据来源

- 基准集 B：领域专家维护的任务与可接受路径集合，覆盖主要意图和高风险场景。
- 探针集 P：按概念类型、度数分桶、图层范围抽样的节点对/概念对，用于测可达性与连通性。
- 生产日志 L：真实查询的动作、观测、诊断码、延迟、用户反馈与最终决策。
- 人工反馈 H：对抽样路径的正确性、可解释性和补全边可信度的评审。

所有指标在固定图谱快照上计算并版本化，避免图更新导致指标不可比。评估分为本体层、实例层、对齐层和查询编译层四层；每层指标都可以从路径查询结果直接或间接计算。

#### 4.6.2 本体图指标

本体层关注“概念骨架是否够用、关系签名是否完整、约束是否可满足”。

**表 4-6 本体图质量指标**

| 指标 | 定义 / 公式 | 建议阈值 | 失败时的动作 |
|----|----|----|----|
| 概念接地率 CGR | 成功接地的 mention 数 / 全部 mention 数 | ≥0.90 | 扩充别名与术语 |
| 概念可达率 SR | 可达概念对 / 抽样概念对 | ≥0.95 | 补关系或中间概念 |
| 关系签名完备率 RSR | 合法签名数 / 任务需要的签名数 | ≥0.98 | 修 domain/range |
| 规则推理增益 RIG | 仅靠推理得到的成功路径 / 全部成功路径 | 0.10–0.40 | 过高说明缺直接关系 |
| 约束可满足率 CSR | 满足硬约束的成功路径 / 成功路径 | ≥0.90 | 修约束建模或数据 |
| 概念歧义率 CAR | 多候选 mention 数 / 全部 mention 数 | ≤0.05 | 消歧与别名治理 |

RIG 不是越高越好：适度推理说明本体规则在补充直接关系，过高则说明本体缺少显式关系，长期会放大推理成本和不一致性。

#### 4.6.3 实例图指标

实例层关注“实体是否找得到、路径是否连得通、证据是否可信”。

**表 4-7 实例图质量指标**

| 指标 | 定义 / 公式 | 建议阈值 | 失败时的动作 |
|----|----|----|----|
| 实体接地率 EGR | 成功链接的实体 mention / 全部实体 mention | ≥0.90 | 实体解析与主键治理 |
| 路径成功率 PSR | 成功查询数 / 总查询数 | ≥0.85 | 按诊断码分流修复 |
| 连通覆盖率 CCR | 最大弱连通分量节点数 / 总节点数 | ≥0.95 | 补 ETL 边与跨库 join |
| 跳数偏差 HPD | median(\|实际跳数−金标准跳数\| / 金标准跳数) | ≤0.20 | 检查捷径边与缺失边 |
| 约束违反率 CVR | 违反硬约束的路径数 / 成功路径数 | ≤0.05 | 修约束或数据 |
| Hub 集中度 HCR | 经过 Top 1% 高度数节点的路径数 / 全部路径数 | ≤0.20 | 拆概念、边权惩罚 |
| 证据覆盖率 ECR | 带完整 provenance 的路径数 / 全部路径数 | ≥0.95 | 补溯源管道 |
| 时效性 Freshness | SLA 内更新的边数 / 全部边数 | ≥0.90 | 加 ETL freshness 监控 |

HPD 用中位数而非均值，避免少数超长路径拉偏；HCR 与 4.2 的超级节点降权直接相关，过高说明路径依赖无信息量的 Hub。

#### 4.6.4 对齐层与查询编译层指标

**表 4-8 对齐层与查询编译层质量指标**

| 指标 | 定义 / 公式 | 建议阈值 | 失败时的动作 |
|----|----|----|----|
| 对齐覆盖率 ALR | 有 same_as 的项目实体 / 全部项目实体 | ≥0.95 | 跑实体对齐任务 |
| 对齐冲突率 ACR | 冲突 same_as 数 / 已对齐实体数 | ≤0.02 | 主键校验与人工仲裁 |
| 跨图查询成功率 XSR | 跨图层成功查询 / 跨图查询总数 | ≥0.90 | 修对齐与桥接 |
| 编译成功率 QCS | 通过 Schema 与 EXPLAIN 的查询 / 总编译请求 | ≥0.98 | 修 IR 或编译器 |
| 查询松弛率 RLR | 需要重写过滤条件的查询 / 总查询数 | ≤0.10 | 放宽默认过滤或补图覆盖 |
| 约束保真度 Faithfulness | 保留的任务约束数 / 任务约束总数 | ≥0.95 | 修抽取与编译 |
| 置信度校准 ECE | Σ_m (\|B_m\|/N)·\|acc(B_m)−conf(B_m)\| | ≤0.05 | 校准分数与阈值 |
| 补全精确率 CPR | 验证为真的补全边 / 提出的补全边 | ≥0.80 | 提高 τ_link、加证据 |
| 补全召回率 CRR | 成功恢复的 no-path / 可恢复 no-path | ≥0.60 | 扩展补全层级与数据源 |

**实现映射（v1.x）**：`action=quality` 的 `query_metrics` 已落地上表可在线计算的部分。PSR 对应 `success_rate`，XSR 对应 `cross_graph_success_rate`，ECR 对应 `evidence_coverage`，HCR 对应 `hub_path_ratio`，QCS 对应 `compile_success_rate`，RLR 对应 `relaxation_rate`，ALR 对应 `alignment_coverage`。CPR 对应 `completion.precision`，分子是已接受的影子边，分母是已裁决（接受或拒绝）的影子边，pending 只计数不计入分母，避免未审核候选被当成误报。跨 store 候选单独用 `completion.bridge_precision` 统计，分母是已接受与已拒绝的 bridge 候选，`expired` 与 `pending` 不计入分母；校准趋势出现回退时 `completion.bridge_trend_alert` 非空。CRR 对应 `completion_recall`，分母是首次查询即失败且诊断属于 `E01/E02/E09/E10` 的可恢复 no-path，分子是同一次查询经 L1-L5 阶梯恢复出路径的数量；纯查询侧放宽（E03+E04/E06）不计入分母，避免把参数松弛误算成语义补全。编译尝试由 `action=compile` 在成功或失败时写入同一条 `query_audit.jsonl`（`kind=compile`，失败时携带诊断信息），不混入路径查询总数；阈值越过内置门限时分别生成 `Q08`（PSR）、`Q09`（XSR）、`Q11`（ECR）、`Q12`（HCR）、`Q13`（QCS）、`Q14`（RLR）、`Q15`（CPR）、`Q16`（CRR）、`Q17`（bridge_precision）、`Q18`（bridge_trend_alert），并进入同一份 `quality_debt.json` 债务队列，供责任人、SLA 与回归验证复用。

ECE 衡量“说 0.8 置信度时是否真的有 80% 正确”，比单纯准确率更适合决策场景。CPR 可由影子边的接受/拒绝记录在线派生；CRR 由查询审计的首次失败与最终恢复状态在线派生，人工标注集仍建议每季度加入回归，防止诊断码漂移。

#### 4.6.5 综合质量分与阈值

各层指标先归一化到 [0,1]，再用加权几何平均聚合，避免某一维极差被其他维平均掉：

$$
Q_{\text{layer}} = \exp\left(\sum_i w_i \cdot \ln(\max(q_i, \varepsilon))\right), \quad \sum_i w_i = 1
$$

总分为四层加权和：

$$
Q_{\text{total}} = 0.20 \cdot Q_{\text{ont}} + 0.45 \cdot Q_{\text{inst}} + 0.20 \cdot Q_{\text{align}} + 0.15 \cdot Q_{\text{query}}
$$

初始阈值建议：绿色 Q_total≥0.85 且各层 ≥0.75；黄色 0.70≤Q_total<0.85；红色 Q_total<0.70 或任一层 <0.60。阈值必须在领域基准集上校准，不应直接照搬。

质量门禁：高风险决策要求 Q_total≥0.80、实例层与对齐层均 ≥0.70，且证据路径不含未晋升的假设边；否则强制人工复核或降级为建议。

#### 4.6.6 评估协议

评估分为离线、在线和发布门禁三部分：

- 离线基准：每次图谱快照运行 ≥200 个任务、≥1000 个分层探针；金标准使用“可接受路径集合”，不要求唯一最短路。
- 在线抽样：抽取 1%–5% 生产查询做影子评估，记录成功率、延迟、诊断码、用户反馈与补全边使用情况。
- 分层统计：按意图、概念类型、度数桶、图层范围和项目分组；每组至少 100 个样本，报告 Wilson 置信区间。
- 归因分析：每个失败路径分配诊断码，区分本体缺口、实例缺口、对齐缺口、编译器缺口和任务假设错误。
- 消融实验：分别关闭 L1 推理、L3 补全，测量成功率与精确率变化，防止“补全掩盖了数据缺口”。
- 反事实探针：删除一条关键边，检查查询是否按预期失败，用于验证指标对真实缺口的敏感度。
- 发布门禁：新图版本导致 PSR 下降超过 2 个百分点、CVR 上升超过 1 个百分点或 Q_total 下降超过 0.03，则阻止发布并回滚。

基准集构建可以采用三种方式：专家标注、从图中采样路径反向生成自然语言问题、以及 known-item retrieval（选一个实体生成问题，检查能否找回该实体）。合成问题只能用于补充，不能替代专家金标准。

#### 4.6.7 指标计算示例

以下 Cypher 假设查询日志写入 PathQueryLog，路径结果写入 Path 与 Entity 节点。

```cypher
// 按意图统计路径成功率
MATCH (l:PathQueryLog)
WITH l.intent AS intent,
     count(*) AS total,
     sum(CASE WHEN l.status = 'success' THEN 1 ELSE 0 END) AS ok
RETURN intent, total, ok,
       toFloat(ok) / total AS psr
ORDER BY total DESC;
// 失败原因分布
MATCH (l:PathQueryLog)
WHERE l.status = 'no_path'
RETURN l.diagnosis_code AS code, count(*) AS n
ORDER BY n DESC;
// Hub 依赖：被最多路径经过的实体
MATCH (l:PathQueryLog)-[:RETURNED]->(p:Path)-[:CONTAINS]->(n:Entity)
WITH n, count(DISTINCT p) AS path_count
ORDER BY path_count DESC
LIMIT 20
RETURN n.id AS entity_id, n.name AS name, path_count;
```

指标快照写入 QualitySnapshot 节点，字段包括 timestamp、graph_version、layer、metric、value、sample_size、ci_low、ci_high，便于趋势分析和发布对比。

指标只有转化为治理动作才有价值。表 4-9 给出常见症状、原因、修复动作和责任方。

#### 4.6.9 路径级质量标志与决策联动

除了全局指标，每条返回路径都应携带局部质量标志，供规划器即时决策：

- stale_edge：边更新时间超出 SLA，要求先刷新或降权。
- hypothesized_edge：包含未晋升的补全边，禁止直接执行副作用动作。
- high_degree_hub：路径经过 Top 1% 高度数节点，要求补充旁证。
- ambiguous_entity：实体链接存在多候选，要求消歧后再行动。
- low_provenance：证据链不完整，降低终止置信度。
- stitched_path：路径由多段拼接，需检查 gap 处的桥接假设。

规划器读取这些标志后，可以自动插入验证任务、请求人工确认或选择替代路径。这样 4.6 的质量评估不只是报表，而是进入 5.2 动作选择和 4.5 计划门禁的运行时信号。

#### 4.6.10 冷启动与持续运营

- 金标准从 20–50 个高价值任务开始，按意图逐步扩展，不追求一次性覆盖全图。
- 每周抽样 50 条生产路径做人工评审，累积补全边正负样本与歧义实体样本。
- 每月发布质量报告，按层展示趋势、Top 缺口和治理进度，并把质量债务纳入迭代计划。

**闭环关系**：4.3 把任务编译为查询，4.4 在查询失败时诊断与补全，4.5 把成功路径转换为可执行计划，4.6 用查询结果反向评估并治理图谱；治理后的图谱又改善下一轮查询与计划质量。四者共享同一套 PathQuery IR、provenance 与质量标志，构成可观测、可回溯的决策闭环。

## 5. 决策层设计（Decision Layer）

### 5.1 POMDP 形式化

将 Agent 的决策过程建模为 **部分可观测马尔可夫决策过程（POMDP）**，七元组定义为：

$$
\langle \mathcal{S}, \mathcal{O}, \mathcal{A}, \mathcal{T}, \Omega , R, \gamma \rangle
$$

| 组件 | 定义 | 说明 |
|----|----|----|
| $\mathcal{S}$ 状态空间 | 环境的真实完整状态 | 包括所有图谱中的实体、关系、动态属性 |
| $\mathcal{O}$ 观测空间 | 多次最短路径查询的返回结果 | 结构化子图 + 路径权重 + 项目上下文 |
| $\mathcal{A}$ 动作空间 | 查询动作 + 推理动作 + 终止动作 | 见 5.2 节 |
| $\mathcal{T}$ 转移函数 | $P(s_{t + 1}\mid s_{t}, a_{t})$ | 由图谱拓扑和外部环境动态决定 |
| $\Omega$ 观测函数 | $P(o_{t}\mid s_{t + 1}, a_{t})$ | 查询引擎返回结果的概率分布 |
| $R$ 奖励函数 | $R(s_{t}, a_{t}, o_{t})$ | 见 5.3 节 |
| $\gamma$ 折扣因子 | $\gamma \in [0, 1)$ | 默认 0.95 |

### 5.2 动作空间设计

#### 5.2.1 查询动作（Query Action）

$$
a_t(\text{query}) = \langle \text{graph\_type}, \text{start\_nodes}, \text{end\_nodes}, \text{constraints} \rangle
$$

- `graph_type`：本体图 / 全局实例图 / 项目级实例图
- `start_nodes` / `end_nodes`：查询的起点和终点实体集合
- `constraints`：关系类型过滤、最大跳数、语义阈值等

#### 5.2.6 动作选择辅助：历史决策步检索（v1.41）

5.2.1 的 `constraints` 里没有"用历史经验辅助选关系"这一项，本节补上，并给出实测边界。

**做法**：把已验证的决策步 `(问题, 起始节点, 选中关系, 方向)` 建成向量索引，按当前问题检索 top-k 作为 few-shot 注入 5.6.1 所指的"候选关系重排"环节。索引属于"记忆"侧，命中结果必须连同 `provenance`、`score`、`model_version` 一起记录，且**只写 `source=verified` 的轨迹**（未通过评测的轨迹入库会把错误当范例传染）。

**实测（报告 v3.23，MetaQA 150 题 × 3 臂 × 2 口径 × 2 模型）**：

| 模型 | 无示例 | 检索 top-6 | 随机示例 | 判定 |
|----|----|----|----|----|
| 强（glm-5.3） | 0.853 | 0.873 | 0.840 | 不启用：+2.0pp，p=0.45，prompt ×1.9 不划算 |
| 弱（minimax-m3） | 0.707 | **0.847** | 0.780 | 启用：+14.0pp，p<0.0001 |

**启用规则（硬）**：

1. **按单步准确率门槛决定是否启用**：单步准确率 ≥ 0.85 的模型不挂检索（收益不可证实、成本翻倍）；< 0.80 的模型挂检索。
2. **必须报随机示例对照**。随机示例单独就有 +7.3pp，没有 C 组会把"prompt 变长"记成"检索有用"。
3. **必须报 LOTO 口径**：剔除所有同模板示例后收益仍有 +11.3pp（弱模型），说明收益不是同模板背诵；若某次 LOTO 收益归零，按"模板记忆"陈述，不许称语义理解。
4. **`k` 默认 6，未调优**（3/6/12 未扫）；嵌入模型当前只有 MiniLM 384 维，换模型必须整库重建并重测。
5. **不得把检索结果直接当动作**：命中只作为候选提示，仍要走 5.6.2 的校验与本体约束。

#### 5.2.2 推理动作（Reasoning Action）

$$
a_t(\text{reason}) = \langle \text{operation}, \text{target\_entities}, \text{logic\_rule} \rangle
$$

- `operation`：推导新事实 / 更新 Belief State / 生成假设
- `target_entities`：参与推理的实体
- `logic_rule`：使用的本体规则或 LLM 生成的推理链

#### 5.2.3 终止动作（Terminate Action）

$$
a_t(\text{terminate}) = \langle \text{final\_decision}, \text{confidence}, \text{evidence\_path} \rangle
$$

- `final_decision`：最终输出的决策或答案
- `confidence`：置信度（0~1）
- `evidence_path`：支撑决策的图谱路径（用于可解释性）

#### 5.2.4 规划动作（Planning Action）

$$
a_t(\text{plan}) = \langle \text{path\_id}, \text{plan\_graph}, \text{verification\_queries}, \text{approval\_gates} \rangle
$$

- path_id：被转换的推理路径标识，用于保持证据可追溯。
- plan_graph：由路径边绑定的任务 DAG，包含前置条件、后置条件、责任人与截止时间。
- verification_queries：验证每个任务完成状态的查询集合，供下一步观测使用。
- approval_gates：不可逆或高成本动作的人工审批门禁。

#### 5.2.5 补全动作（Completion Action）

$$
a_t(\text{complete}) = \langle \text{diagnosis\_code}, \text{repair\_level}, \text{candidate\_edges}, \text{write\_policy} \rangle
$$

- diagnosis_code：来自 4.4.1 的失败诊断码，决定可用的补全层级。
- repair_level：L0–L5 的补全层级，按成本与风险从低到高选择。
- candidate_edges：待验证的候选边或对齐关系，默认写入影子图而非主图。
- write_policy：是否写图、写入的溯源等级、TTL 与晋升条件。

### 5.3 奖励函数设计（Reward Shaping）

为解决稀疏奖励问题，采用**密集奖励塑造**：

$$
R_{t} = \alpha \cdot R_{\text{accuracy}} + \beta \cdot R_{\text{efficiency}} + \gamma \cdot R_{\text{semantic}} + \delta \cdot R_{\text{constraint}}
$$

| 奖励项 | 计算方式 | 权重建议 |
|----|----|----|
| $R_{\text{accuracy}}$ | 终止时：最终决策正确 = +10，错误 = -10；中间步：命中关键实体 = +1 | $\alpha = 0.4$ |
| $R_{\text{efficiency}}$ | 每步查询惩罚 -0.1；路径跳数越少奖励越高 | $\beta = 0.2$ |
| $R_{\text{semantic}}$ | LLM 评估观测结果与任务目标的语义契合度（0~1） | $\gamma = 0.2$ |
| $R_{\text{constraint}}$ | 违反本体约束 = -5；满足约束 = +0.5 | $\delta = 0.2$ |

在上述四项奖励之外，补充设计新增三项密集奖励，用于约束路径补全与计划生成的质量：

- R_completion：被外部证据或人工确认的补全边比例；提出但未验证的假设边按数量和停留时长惩罚。
- R_plan：计划任务可执行率与验证查询覆盖率；缺少成功判据、责任人或审批门禁的任务扣分。
- R_quality：对路径质量标志（陈旧边、Hub 节点、歧义实体、假设边、低溯源）加权惩罚，鼓励高质量证据路径。

建议初始权重为 R_completion=1.0、R_plan=1.5、R_quality=1.0，并在离线回放中按决策正确率与人工审核成本做网格搜索校准。

### 5.4 Belief State 更新

Agent 维护一个**信念状态** $b_{t}$，表示对真实状态 $s_{t}$ 的概率分布估计。工程上采用**结构化缓存 + 向量索引**近似：

```python
class BeliefState:
    def __init__(self):
        self.entity_cache: Dict[str, Entity] = {}      # 已观测实体
        self.path_history: List[Path] = []              # 历史查询路径
        self.hypothesis_set: List[Hypothesis] = []      # 当前假设
        self.vector_index: VectorStore                  # 语义检索索引

    def update(self, observation: Observation, action: Action):
        # 1. 合并新观测到的实体和关系
        self.entity_cache.update(observation.entities)
        self.path_history.append(observation.path)

        # 2. 基于本体规则推导新事实
        new_facts = self.apply_ontology_rules()
        self.entity_cache.update(new_facts)

        # 3. 更新假设集的置信度
        for hyp in self.hypothesis_set:
            hyp.confidence = self.recalculate_confidence(hyp)

        # 4. 淘汰低置信度假设和过时实体
        self.prune()
```

### 5.5 决策循环伪代码

```python
def agent_decision_loop(task: Task, max_steps: int = 10) -> Decision:
    # 初始化
    belief_state = BeliefState()
    belief_state.initialize(task)

    for step in range(max_steps):
        # 1. 感知：从 Belief State 提取当前观测
        observation = belief_state.get_current_observation()

        # 2. 规划：LLM Planner 生成候选动作
        candidate_actions = llm_planner.plan(
            task=task,
            belief_state=belief_state,
            observation=observation
        )

        # 3. 选择：策略网络或 LLM 选择最优动作
        action = policy.select(candidate_actions)

        # 4. 执行：执行动作
        if action.type == "query":
            result = query_engine.execute(action)
            observation = Observation.from_query_result(result)
        elif action.type == "reason":
            observation = belief_state.apply_reasoning(action)
        elif action.type == "terminate":
            # 评估是否真正可以终止
            confidence = reward_evaluator.assess_confidence(belief_state)
            if confidence > THRESHOLD:
                return Decision(
                    result=action.final_decision,
                    confidence=confidence,
                    evidence=belief_state.path_history
                )

        # 5. 更新：更新 Belief State
        belief_state.update(observation, action)

        # 6. 评估：计算奖励（用于在线学习或离线优化）
        reward = reward_evaluator.evaluate(belief_state, action, observation)

    # 超时强制终止
    return Decision(
        result=belief_state.best_hypothesis(),
        confidence=0.5,
        evidence=belief_state.path_history,
        timeout=True
    )
```

> **实现约束（v1.34）**：上面第 4 步的 `confidence > THRESHOLD` 与"由策略决定是否终止"这两个写法，
> 在实测里都是负收益，见 5.6。生产实现必须以 5.6.2 的结构化终止判据为准，`THRESHOLD` 只保留为
> "输出置信度"的标注用途，不作为"是否继续查"的开关。

### 5.6 决策闭环的实测边界（v1.34）

依据报告 v3.16（`exp_53`/`exp_54`/`diag_exp54_steps`）：在真实 KB（1.6 万主体 / 9 关系 / 39 万三元组）上做图内受控闭环，
动作空间 18 个（9 关系 × 出入方向），每步 oracle 合法动作数均值 1.0。**这不是 ALFWorld/WebShop 基准分数**
（TextWorld 1.7.0 要求 Python < 3.13，本机 3.14 装不上），只用于判定三个环节各自的边际贡献。

#### 5.6.1 三条实测结论

| 结论 | 数字 | 含义 |
|----|----|----|
| **计划本身是有效环节** | hop2 上"只查一次"0.000 → "按跳数走"0.700；hop3 0.075 → 0.225 | 多跳任务必须出计划，不能单步直查 |
| **"模型自判信息够了"是负收益** | 比固定步数低 **3.8pp**，调用多 **39%**，4 例把已检索到的正确答案丢掉 | 终止判断不能交给模型自由裁量 |
| **瓶颈在单步选关系，不在步数规划** | 单步 0.625、hop3 实测 0.225 ≈ $0.625^3=0.244$；首步就选错占 **37.5%** | 多跳准确率是单步准确率的连乘，重规划救不回来 |

由此确定 **重规划不是重点，单步动作质量才是**。对应到设计上：投入应放在 5.2.1 查询动作的候选关系重排
（字面 → 关系的映射、同义关系合并、方向裁决），而不是在 5.5 里加"反思/重试"轮次。

#### 5.6.2 终止与校验的结构化判据（替代模型自判）

| 判据 | 触发即终止 / 触发校验 | 说明 |
|----|----|----|
| 达到估计跳数 | 终止 | 跳数来自 4.1.1 的检索层估计，不由模型自由生成 |
| 结果为空 | 触发校验（1 次） | 空结果是**可观测**的失败信号，与模型自评不同 |
| 约束违反 | 触发校验（1 次） | 由 3.1.x 本体约束检查给出，可审计 |
| 候选数异常（> 阈值 或 = 1） | 触发校验（1 次） | 超级节点或退化情形，见 4.2 |
| 预算用尽 | 终止并降级 | 返回当前最佳假设 + `timeout=true`，不得谎报置信度 |

**硬规则**：

1. **重规划预算 ≤ 1 次**，且只在上述"触发校验"的情形下使用。轨迹回放显示，走错路径后继续展开无意义——
   第 4 步时 oracle 合法动作数已经是 0.0，再查 17 例全为空转。
2. **不允许"模型说够了"作为终止条件**。模型自判既不提高准确率，也不减少调用。
3. **ANSWER 只能在已检索到的候选集内挑选**，不得新造实体。评测侧必须按此归一口径计分，
   否则会把"复述格式差异"误判成"计划能力差异"（报告 v3.16 记录了这个自伤案例）。

#### 5.6.3 证据忠实性：图必须能覆盖记忆（v1.35）

实测（报告 v3.17）：**实体匿名化**后 P1 0.817→0.000、P2 1.000→0.967；**反事实替换** 21/21 跟随编辑、0 例记忆覆盖、原图正控 1.000。

| 硬规则 | 原因 | 违反后果 |
|----|----|----|
| 准确率必须报**匿名化后**的数字 | 记忆会把「参数里就有答案」伪装成能力 | 把 96.7pp 的真实增益报成 18.3pp |
| 必须报**反事实跟随率** | 只有它能证明读了图，而不是猜对了 | 无法声称路径证据可审计 |
| 图扰动构造必须过干跑校验 | 浅拷贝泄漏、同一答案多关系来源、大小写不一致，都会让反事实失效**且不报错** | 得到看似合理但完全错误的忠实性数字 |

**归因顺序**：任何「图没用」或「模型不忠实」的结论，先证明扰动真的生效（正控），再下结论。

### 4.3.10 edge type 基数与 `OVER *` 禁用（v1.38）

v3.2 已确定"关系名必须成为 edge type"（关系名放属性会静默丢 7.66% 的边）。DBP15K 有 **3,734 个关系名**，实测这条约束的代价（1 万顶点 / 10 万边，只改类型数）：

| edge type 数 | 导入（边/秒） | T1 单跳 p50 | T2 两跳 p50 | `OVER *` p50 | storaged RSS |
|----|----|----|----|----|----|
| 1 | 62,681 | 1.21 ms | 2.15 ms | 1.22 ms | 197 MiB |
| 100 | 62,832 | 1.14 ms | 1.08 ms | 2.31 ms | 200 MiB |
| 1,000 | 42,135 | 1.49 ms | 1.47 ms | 11.08 ms | 212 MiB |
| 3,734 | 14,868 | 1.32 ms | 1.52 ms | **32.13 ms** | 242 MiB |

**两条硬约束**：

1. **主链路禁止 `OVER *`**。跨全部关系遍历必须由查询计划显式给出关系集合（来自本体或 LLM 提案），否则每次遍历多付约 30 ms，且随本体扩张线性恶化（每 1,000 类型约 +8 ms）。
2. **导入必须按 edge type 分组批量**。3,734 类型下吞吐只有单类型的 1/4.2；10⁷ 边约需 **11 分钟**（单类型 2.7 分钟），导入超时与排期按最坏情况设。

附带结论：schema 创建不是瓶颈（3,734 条 `CREATE EDGE` 共 2.5 s），内存只多 22%，不需要预置空类型。

### 4.3.11 副本系数：写入代价、切换窗口与客户端超时（v1.39）

实测环境：隔离集群 1 metad + 3 storaged + 1 graphd（同机三容器），1 万顶点 / 10 万边 / 批 200，4 次运行取中位数。

| 配置 | 导入（边/秒） | 单批写入 p50 | T1 p50 | T2 p50 |
|----|----|----|----|----|
| `replica_factor=1` | 83,740 | 2.10 ms | 1.14 ms | 1.93 ms |
| `replica_factor=3` | 60,215 | 3.00 ms | 1.20 ms | 1.95 ms |

**硬约束**：

1. **容量换算**：写入吞吐按 **×0.72**、单批延迟按 **×1.43** 折算；导入排期同样乘 1.39（10⁷ 边 11 分钟 → 约 15 分钟，再叠加 §4.3.10 的类型基数代价）。
2. **切换窗口 48 秒**：停 1 个 storaged 后，第一次写成功要等 **48.1 s**（两次一致）；之后写入与延迟恢复正常。这段窗口内必须按"写入不可用"降级，不能假设副本瞬时接管。
3. **客户端超时与熔断是上线前置条件**：丢 quorum 时写路径**挂住而不返回错误**（200 次探针 4 分钟只完成 136 次）。上层必须自带超时（建议 ≤ 单查询预算）与熔断，不能依赖服务端报错。
4. **读扩展不能靠副本系数**：读取延迟与副本数无关（读走 leader），要读扩展只能加 storaged 节点或调整 `partition_num`，属部署约束。

另外记录两条部署事实（文档不写、报错不指路）：单 storaged 时 `replica_factor≥2` 会被拒（`Host not enough!`）；新增 storaged 不会自动注册，必须 `ADD HOSTS`。

### 4.3.12 超点与 LIMIT 的位置（v1.40）

真实图谱的度数是重尾的：本项目 KB（43,234 实体 / 唯一三元组 133,582）里**最大度 4,176**（`Drama`），度 > 1,000 的 4 个顶点（0.01%）扛着 3.9% 的边，平均度只有 6.18。这类顶点是查询预算最容易被击穿的地方，实测结论是**代价由返回行数决定，不由度数决定**。

| 写法 | 50,000 度超点上的 p50 | 说明 |
|----|----|----|
| `GO FROM v OVER *` | 471.62 ms | 全量 5 万行 |
| `GO FROM v OVER * \| LIMIT 10` | **1.52 ms** | 真正的早停，310 倍 |
| `GO FROM v OVER rel_a` | 93.05 ms | 指定类型仍有 1 万行 |
| `GO v\|GO v\| LIMIT 10`（末尾） | 494.25 ms | **末尾 LIMIT 不早停** |
| `GO v \| LIMIT 10 \| GO v`（中间） | **3.67 ms** | 134.7 倍 |

**硬规则**：

1. **`LIMIT` 紧跟 `GO`**：T1 类查询一律 `GO ... | LIMIT n`，此时延迟与起点度数无关（六个度数档全部 1.0–1.6 ms）。
2. **多跳禁止末尾 `LIMIT`**：`GO | GO | LIMIT` 的执行器要先把 hop1 全部物化才截断，50k 度下 494 ms；必须在 hop1 之后立刻 `| LIMIT n` 再进 hop2。
3. **超点阈值 = 度 1,000**：查询编译期若已知起点度数 > 1,000（可缓存度数），强制注入裁剪，并把该步标记为 `truncated=true` 上报，禁止静默截断。
4. **行数预算公式**：`T ≈ 1.3 ms + 10 µs × 返回行数`。100 ms 查询预算 ≈ 1 万行；执行器按此反推单步 `LIMIT` 上限。
5. **内存**：一次全量 5 万行返回让 graphd RSS 47.77 → 452.90 MB（×9.5）且不归还，所以行数上限也是内存约束，不只是延迟约束。

未验证：`REVERSELY` 反向遍历在大**入度**顶点上的行为（真实 KB 最大的两个超点恰是入度超点）；`EXPLAIN` 计划树在本版本客户端取不到，早停是延迟推断而非计划级证据。

## 6. 工程实现建议

### 6.1 技术栈选型

### 6.2 性能优化策略

1.  **预计算嵌入**：对所有图谱节点预计算嵌入向量，离线更新（天级），在线查询时直接查表。
2.  **分层查询**：先在本体图上做轻量级概念规划（毫秒级），再在实例图上做受限搜索，避免全图遍历。
3.  **小模型蒸馏**：将大模型的航点生成和语义打分能力蒸馏到 4B 参数小模型，用于高频调用场景，降低延迟和成本。
4.  **查询缓存**：对相同起点-终点-约束的查询结果进行缓存（TTL 根据图谱更新频率设定）。
5.  **并行查询**：多个候选路径查询可并行执行，取最优结果。

### 6.3 可观测性与调试

- **决策链路日志**：记录每一步的动作、观测、奖励、Belief State 变化，支持回放和根因分析。
- **图谱可视化**：将查询路径和证据子图渲染为交互式图谱，便于人工审核。
- **A/B 测试框架**：支持不同策略（如不同奖励权重、不同剪枝阈值）的在线对比。

- 图谱质量看板：按 4.6 节指标每日生成快照，支持按查询意图、项目、概念类型和度数分桶下钻。
- 路径溯源审计：每条决策证据路径记录边级 provenance、补全层级、置信度与质量标志，支持逐边回放。
- 补全边审计队列：集中展示 HYPOTHESIZED 边的证据、TTL、晋升或驳回记录，避免假设边长期污染主图。
- 知识层快照看板：展示 tbox_hash、abox_snapshot、规则层版本、影子边数量与最近重建时间，支持查询拒绝与回滚审计。

### 6.4 LLM 依赖的降级契约

检索层只有两处 LLM 依赖（提案、重排），但它们的失效模式比"出错重试"复杂得多。实测（报告 v3.1 实验 Z）把七类故障逐个造出来，结论是**错误必须先分类，再决定重试**：

| 错误类 | 判定依据 | 重试 | 退避 | 失败动作 |
|----|----|----|----|----|
| `dns` | `gaierror`（域名不解析） | **否** | — | 立即降级到规则提案 + stub 打分 |
| `refused` | `ConnectionRefusedError` | **否** | — | 同上 |
| `timeout` | socket/URL 超时 | 1 次 | 1.0 s | 仍失败则降级 |
| `429` | HTTP 429 | 是 | 按 `Retry-After`，下限 0.5 s | 用尽则降级 |
| `5xx` | HTTP 5xx（含代理包装的 502） | 是 | 1.0 s | 用尽则降级 |
| `parse` / `empty` | 响应体截断、`content` 为空、下标越界 | 1 次 | 0.5 s | 用尽则降级 |
| `retired` | HTTP 410（模型已下线） | **否** | — | 走模型替换表，不重试 |

四条硬规则：

1. **不可恢复错误（`dns` / `refused` / `retired`）不重试**。实测这几个类重试只是白等一个退避周期（1.5 s → 0.0 s）。
2. **空响应等于失败**。`content=""` 若被当成成功，会让"全部调用失败"在指标上看起来像"重排没效果"——这是踩过的坑，判定必须显式（`None` 或空白串都算失败）。
3. **熔断按连续失败计数，不按时间窗口**。连续 3 次失败即打开，冷却 30 s，半开时只放 1 个探针。实测连续 10 次打向 502：前 3 次各 2.0 s，后 7 次全部 0.0 ms，总耗时 6.51 s（不熔断 ≥ 20 s，含超时故障则 40 s+）。熔断期间请求**立即**走降级路径，不得排队等待。
4. **降级路径必须是确定性的**。LLM 全挂时仍要出答案：规则提案（关系白名单 + 深度限制的受限 BFS）+ stub 打分，实测样本题仍给出非空答案。**禁止"等 LLM 恢复"式阻塞**，也禁止静默返回空结果。

运维约束：

- **模型名是外部契约**。`minimax-m2.7:cloud` 在压测期间返回 410 Gone（已退役），说明"名字一直在"是错误假设。配置必须记录 {模型名 → 供应商 → 退役日期 → 替代模型}，并在启动时做一次可用性预检。
- **缓存键必须带模型前缀**（`model|qid|cand_hash`）。不带前缀时换模型会命中旧缓存，跨模型对比会"全部一致"地假通过。
- **成本按 token 熔断，不按调用次数**。实测 157 token/查询（提案 81、重排 75），单请求 cap 取 3× 均值（469 token）；超 cap 即截断候选数而非截断提示词。

降级时必须在响应里显式标注（`degraded: true` + 原因码 `llm_dns` / `llm_retired` / `llm_timeout` / `llm_parse`），因为**同一份答案在"重排生效"和"重排降级"两种状态下可信度不同**，下游不得混用。

## 7. 风险评估与缓解

| 风险 | 影响 | 缓解措施 |
|----|----|----|
| **LLM 规划错误** | 生成无效航点，导致查询失败 | 设置回退机制：LLM 规划失败时降级为传统 BFS；对 LLM 输出做 Schema 校验（6.4） |
| **LLM 依赖整段失效** | DNS/网关/模型退役导致两处调用全挂 | 错误分类 + 不重试不可恢复类 + 连续 3 次熔断 30s；降级到规则提案 + stub 打分并标注 `degraded`；启动预检模型可用性（6.4） |
| **图谱数据不一致** | 本体与实例对齐错误，推理结果不可靠 | 建立数据质量监控管道；关键决策前做一致性校验 |
| **组合爆炸** | 实例图查询超时 | 严格施加动作剪枝和深度限制；设置查询超时熔断 |
